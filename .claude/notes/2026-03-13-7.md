# Canto Storage System — In-Depth Reference

This note provides a comprehensive description of how Canto stores, structures, and secures user data on-device.

---

## 1. Storage Technology Stack

| Layer              | Technology                             | Purpose                                      |
| ------------------ | -------------------------------------- | -------------------------------------------- |
| Filesystem         | `expo-file-system` (DocumentDirectory) | Journal, page, and attachment persistence    |
| Secure key storage | `expo-secure-store`                    | Device encryption key and biometric keys     |
| Ephemeral state    | `AsyncStorage`                         | Rate-limit counters, app preferences         |
| Crypto primitives  | `@noble/ciphers`, `@noble/hashes`      | AES-256-GCM, PBKDF2-SHA256                   |
| Biometrics         | `expo-local-authentication`            | Fingerprint/face gating on SecureStore reads |

There is no SQLite or relational database. All data lives as encrypted JSON files on the filesystem, managed by `LocalStore` (`src/lib/storage/local.ts`).

---

## 2. On-Disk Directory Layout

All app data lives under `{DocumentDirectory}/canto/`. The full tree:

```
{DocumentDirectory}/canto/
│
├── journals.json                        # Encrypted index of all journals
│                                        #   (device-encrypted only, never password-encrypted)
│
├── {journalId}/                         # One directory per journal (UUID)
│   │
│   ├── metadata.json                    # Encrypted journal metadata
│   │                                    #   (device + optional password layer)
│   │
│   ├── pages/                           # One file per page
│   │   ├── {pageId}.json                # Encrypted page content
│   │   ├── {pageId}.json                # Each page is its own file
│   │   └── ...
│   │
│   └── attachments/                     # Binary attachments for this journal
│       ├── img-{pageId}-{hash}.jpg      # Device-encrypted image
│       ├── eimg-{pageId}-{hash}.jpg     # Device + password-encrypted image
│       ├── img-{pageId}-{hash}.png      # Different formats supported
│       ├── fl-{pageId}-{hash}.pdf       # Device-encrypted file
│       ├── efl-{pageId}-{hash}.pdf      # Device + password-encrypted file
│       └── ...
│
├── {journalId}/                         # Another journal...
│   ├── metadata.json
│   ├── pages/
│   │   └── ...
│   └── attachments/
│       └── ...
│
└── ...                                  # Additional journals follow same pattern
```

### File naming conventions for attachments

The prefix encodes the attachment type and encryption status:

| Prefix  | Type  | Encryption        |
| ------- | ----- | ----------------- |
| `img-`  | Image | Device-only       |
| `eimg-` | Image | Device + password |
| `fl-`   | File  | Device-only       |
| `efl-`  | File  | Device + password |

The full pattern is `{prefix}{pageId}-{hashCode}.{ext}`, where `hashCode` is derived from the original filename to prevent collisions when multiple attachments share the same name.

## 3. Data Models

### Journal (stored in `journals.json` index and `metadata.json`)

```typescript
Journal {
  id: string              // UUID v4
  title: string           // User-visible name
  icon: string            // Feather icon identifier
  date: string            // ISO 8601 creation timestamp
  secure: boolean         // Whether password-protected
  salt?: string           // Base64-encoded 16-byte PBKDF2 salt
  biometric?: boolean     // Whether biometric unlock is enabled
  kdfIterations?: number  // PBKDF2 iteration count (omitted = legacy 20k)
  themeOverride?: string  // Per-journal color theme
}
```

### Page (stored individually in `pages/{pageId}.json`)

```typescript
Page {
  id: string              // UUID v4
  text: string            // Markdown body
  date: string            // ISO 8601 creation timestamp
  thumbnail?: string      // Preview image URI
  location?: {            // Optional geolocation
    latitude: number
    longitude: number
    altitude?: number
    accuracy?: number
  }
  tags: string[]          // User-defined tags
  files: Attachment[]     // Non-image attachments
  images: Attachment[]    // Image attachments
  comments: Comment[]     // Threaded comments
  modified: number        // Unix timestamp (ms) — used for sync conflict resolution
  deleted: boolean        // Soft-delete flag (propagated via sync)
}
```

### Attachment (embedded in Page, file stored in `attachments/`)

```typescript
Attachment {
  id: string              // UUID v4
  path: string            // File URI on disk
  name: string            // Original filename
  type: 'image' | 'file'  // Determines prefix (img/fl vs eimg/efl)
  encrypted: boolean      // Whether password-encrypted (in addition to device)
  size?: number           // File size in bytes
  deleted: boolean        // Soft-delete flag
}
```

### JournalContent (the full in-memory representation)

```typescript
JournalContent extends Journal {
  pages: Page[]
  settings: JournalSettings
  version: number         // Schema version (currently 1)
}
```

## 4. Encryption Architecture

Canto uses a **two-layer encryption model**. Every piece of persisted data passes through at least one encryption layer; password-protected journals add a second.

### Layer diagram

```
┌──────────────────────────────────────────────────────────┐
│                      PLAINTEXT                           │
│              (JSON string or binary data)                │
└──────────────────────┬───────────────────────────────────┘
                       │
            ┌──────────▼──────────┐
            │  PASSWORD LAYER     │  ← Only if journal.secure && derivedKey present
            │  AES-256-GCM       │
            │  Key: PBKDF2(      │
            │    password,        │
            │    journal.salt,    │
            │    iterations       │
            │  )                  │
            └──────────┬──────────┘
                       │
            ┌──────────▼──────────┐
            │  DEVICE LAYER       │  ← Always applied
            │  AES-256-GCM       │
            │  Key: 256-bit key   │
            │  from SecureStore   │
            └──────────┬──────────┘
                       │
┌──────────────────────▼───────────────────────────────────┐
│                    CIPHERTEXT                            │
│           base64([12B nonce][ciphertext][16B GCM tag])   │
│                   Written to filesystem                  │
└──────────────────────────────────────────────────────────┘
```

### What each layer protects against

| Layer          | Key source                                                  | Protects against                                                                                                 |
| -------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Device layer   | 256-bit CSPRNG key in `expo-secure-store`                   | File-level access (e.g. backup extraction, filesystem browsing). Tied to device hardware keychain.               |
| Password layer | PBKDF2-SHA256 derived from user password + per-journal salt | Device compromise. Even with the device key, password-protected journals require the user's password to decrypt. |

### Ciphertext format

Each encrypted blob is stored as a base64 string encoding:

```
[12 bytes: random nonce][N bytes: AES-GCM ciphertext][16 bytes: GCM authentication tag]
```

The nonce is generated fresh for every encryption operation via CSPRNG (`crypto.getRandomValues`).

## 5. Key Management

### Device key (`src/lib/encryption/device.ts`)

- **Generation**: 256-bit random key via CSPRNG on first app launch
- **Storage**: `expo-secure-store` under alias `canto_device_encryption_key`
- **Caching**: Held in a module-level variable after first retrieval for performance
- **Clearing**: `clearKey()` zeros the cached copy (called on app background)
- **Rotation**: `rotateKey()` generates a new key and triggers full re-encryption of all data

### Password-derived keys (`src/lib/encryption/password.ts`)

- **Derivation**: PBKDF2-SHA256 with per-journal 16-byte salt
- **Iterations**: Configurable per journal. Presets:
  - Legacy (pre-0.8.2): 20,000 (used if `kdfIterations` field missing)
  - Default (0.8.2+): 50,000
  - User-selectable: 50k, 100k, 200k, 600k, 800k, 1M
- **Session caching**: `JournalKeyContext` (React Context) holds derived keys in memory
- **Auto-lock**: Keys are cleared from context after configurable inactivity timeout (30s polling interval)

### Biometric authentication (`src/lib/biometric.ts`)

Biometric acts as a **gate only** — it does not store or restore the derived key. The flow:

1. User taps a journal with `biometric: true`
2. `authenticateBiometric()` prompts fingerprint/face via `expo-local-authentication`
3. If biometric fails → access denied (user cannot proceed)
4. If biometric succeeds → user is shown the password prompt (if `secure`)
5. The derived key is **always** calculated from the password via PBKDF2

Note: `biometric.ts` exports `storeBiometricKey()` and `getBiometricKey()` functions that store/retrieve derived keys in SecureStore with `requireAuthentication: true`. However, these functions are **currently unused** — no component or hook calls them. The actual unlock flow in `app/index.tsx` uses biometric purely as a gate before the password prompt. The key storage functions may be intended for future use.

- Graceful fallback if biometrics unavailable on device
- Per-journal toggle in journal settings (`journal.biometric` flag)

### Key lifecycle diagram

```
App Launch
    │
    ├── Device key loaded from SecureStore → cached in memory
    │
    ├── journals.json decrypted (device layer only) → journal list shown
    │
    └── User opens secure journal
            │
            ├── Biometric enabled? ──yes──→ Biometric prompt
            │       │                         │
            │       no                   ┌────┴────┐
            │       │                  fail     success
            │       │                   │         │
            │       │                 BLOCKED      │
            │       │                   (return)   │
            │       ▼                              ▼
            │   Password-protected? ───────────────┤
            │       │                              │
            │      yes                            no (has salt, auto-derive from "")
            │       │                              │
            │       ▼                              ▼
            │   Password prompt            PBKDF2("", salt, iterations)
            │       │                              │
            │       ▼                              ▼
            │   PBKDF2(password, salt, iterations) → derivedKey
            │       │
            │       ▼
            │   Trial decrypt metadata.json
            │       │
            │   ┌───┴───┐
            │  fail    success
            │   │        │
            │   ▼        ▼
            │  Rate    derivedKey cached
            │  limit   in JournalKeyContext
            │  check
            │
    ─── Inactivity timeout ──→ derivedKey cleared from context
                                (re-auth required)
```

## 6. Encryption Scope per File Type

| File                 | Device-encrypted | Password-encrypted | Notes                                                           |
| -------------------- | :--------------: | :----------------: | --------------------------------------------------------------- |
| `journals.json`      |       Yes        |       **No**       | Must be readable without password for journal discovery/listing |
| `metadata.json`      |       Yes        |    If `secure`     | Contains journal title, settings, page list                     |
| `pages/{id}.json`    |       Yes        |    If `secure`     | Each page encrypted independently                               |
| `img-*` attachments  |       Yes        |       **No**       | Standard image attachments                                      |
| `eimg-*` attachments |       Yes        |      **Yes**       | User explicitly chose "encrypted image"                         |
| `fl-*` attachments   |       Yes        |       **No**       | Standard file attachments                                       |
| `efl-*` attachments  |       Yes        |      **Yes**       | User explicitly chose "encrypted file"                          |

This means within a password-protected journal, users have granular control: the journal structure is always password-gated, but individual attachments can be additionally password-encrypted (prefix `eimg-`/`efl-`) or left with device-only encryption (prefix `img-`/`fl-`).

## 7. Write Safety — Atomic Operations

All write operations in `LocalStore` use an atomic write pattern to prevent data corruption on crashes or power loss:

```
1. Serialize + encrypt data
2. Write to temporary file:  {target}.tmp
3. Atomic rename:            {target}.tmp → {target}
```

The filesystem rename is an atomic operation — the file either exists with the old content or the new content, never a partial write.

### Crash recovery for re-encryption

During key rotation or password changes, many files must be re-encrypted. If the process is interrupted:

1. On next startup, `LocalStore` scans for `.tmp` files
2. If a `.tmp` file exists alongside its target, the rename is completed
3. If a `.tmp` file exists without a target, it becomes the target
4. This guarantees re-encryption either completes fully or can be resumed

## 8. Attachment Storage Flow

### Saving an attachment

```
User picks image/file
        │
        ▼
AddAttachmentPopup.tsx
  ├── Option: "Image" or "File"          → encrypted: false
  └── Option: "Encrypted Image/File"     → encrypted: true
        │
        ▼
useAttachment().save(journalId, pageId, data, filename, type, encrypted, derivedKey)
        │
        ▼
LocalStore.saveAttachment()
  1. Compute hash from filename
  2. Determine prefix: img|eimg|fl|efl based on type + encrypted flag
  3. Build path: attachments/{prefix}-{pageId}-{hash}.{ext}
  4. If encrypted && derivedKey: password-encrypt data
  5. Device-encrypt data (always)
  6. Atomic write to filesystem
        │
        ▼
Returns Attachment object with { id, path, name, type, encrypted, size }
  → Embedded in Page.images[] or Page.files[]
  → Page saved separately
```

### Reading an attachment

```
LocalStore.getAttachment(journalId, path, derivedKey?)
  1. Read raw base64 from filesystem
  2. Device-decrypt
  3. If path starts with "eimg-" or "efl-" && derivedKey: password-decrypt
  4. Return plaintext data
```

### Deleting an attachment

Attachments use soft deletion:

1. `Attachment.deleted` set to `true` in the parent Page
2. Physical file left on disk (for sync propagation)
3. Actual file deletion happens during sync cleanup or journal deletion

## 9. Rate Limiting (`src/lib/encryption/ratelimit.ts`)

Failed password attempts are tracked with escalating lockouts:

| Attempts | Lockout duration |
| -------- | ---------------- |
| 1–4      | None             |
| 5–9      | 30 seconds       |
| 10–14    | 5 minutes        |
| 15+      | 30 minutes       |

State is persisted in AsyncStorage (`canto_unlock_rate_limit`) as `{ attempts, lockedUntil }`. The counter resets on successful unlock.

---

## 10. Sync System Overview

The sync engine (`src/lib/sync/engine.ts`) operates on top of the encrypted storage:

- **Granularity**: Per-page sync (each page is a separate encrypted file)
- **Conflict resolution**: Last-write-wins based on `Page.modified` timestamp
- **Data in transit**: Remains encrypted — sync uploads/downloads ciphertext
- **Soft deletes**: `deleted: true` pages propagate deletion to remote
- **Per-journal opt-in**: Controlled by `JournalSettings.remoteSync`

## 12. Security Summary

| Property               | Implementation                                                                                        |
| ---------------------- | ----------------------------------------------------------------------------------------------------- |
| Encryption at rest     | AES-256-GCM, always-on device layer                                                                   |
| Password protection    | Optional per-journal, PBKDF2-SHA256 with configurable iterations                                      |
| Key storage            | Hardware-backed SecureStore (device key, biometric keys)                                              |
| Nonce reuse prevention | Fresh 12-byte CSPRNG nonce per encryption                                                             |
| Authentication         | GCM tag provides integrity + authenticity                                                             |
| Brute force resistance | Escalating rate limits (30s → 5m → 30m)                                                               |
| Key material hygiene   | In-memory keys zeroed on app background (JS GC caveat noted)                                          |
| Write integrity        | Atomic rename prevents partial/corrupt writes                                                         |
| Crash resilience       | `.tmp` file detection completes interrupted re-encryption                                             |
| Biometric gating       | Gate-only via `expo-local-authentication` — blocks access if biometric fails, password still required |
| Sync security          | Data remains encrypted in transit and at rest on remote                                               |
