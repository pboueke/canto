# Security Architecture Review

**Date:** 2026-03-13

## Overview

Canto uses a two-tier encryption model where all data is encrypted at rest with no plaintext storage:

```
plaintext -> [password encrypt (if secure journal)] -> [device encrypt] -> disk
```

## Tier 1: Device Encryption (always active)

- **Algorithm**: AES-256-GCM via `@noble/ciphers`
- **Key**: 256-bit, generated once via CSPRNG (`crypto.getRandomValues`)
- **Storage**: `expo-secure-store` (platform Keychain/Keystore) under alias `canto_device_encryption_key`
- **Ciphertext format**: `base64([12-byte nonce][ciphertext][16-byte GCM tag])`
- Key cached in memory, clearable via `clearKey()`

## Tier 2: Password Encryption (optional, per-journal)

- **KDF**: PBKDF2-SHA256, 20,000 iterations, 16-byte random salt per journal
- **Algorithm**: AES-256-GCM (same as device layer)
- **Key zeroing**: Derived keys explicitly zeroed with `Uint8Array.fill(0)` after use
- Salt stored in journal metadata (correct -- salt is not secret)

## Authentication

- **Password**: Trial decryption to verify correctness; strength meter (weak/fair/strong, 6-point scale)
- **Biometrics**: `expo-local-authentication` -- acts as a gate layer before password prompt, not a replacement
- **Rate limiting**: 5 failed attempts -> 30-second lockout (in-memory)

## Key Management

- **Device key**: CSPRNG, generated once per install, stored in `expo-secure-store`, permanent lifetime, `clearKey()` zeros cache
- **Password-derived key**: PBKDF2 on each unlock, stored in React Context (`JournalKeyContext`), session lifetime, cleared on home screen focus

## Data at Rest

All files under `$DocumentDir/canto/` are encrypted:

- `journals.json` -- index (device-encrypted)
- `/{id}/metadata.json` -- journal metadata (both tiers)
- `/{id}/pages/*.json` -- page content (both tiers)
- `/{id}/attachments/` -- attachment files (both tiers if secure)

No network sync is active -- data is local-only.

## Crypto Dependencies

- `@noble/ciphers` ^2.1.1 -- audited AES-GCM
- `@noble/hashes` ^2.0.1 -- audited PBKDF2
- `react-native-get-random-values` -- CSPRNG polyfill
- No custom crypto, no MD5/SHA1, no hardcoded secrets

## Issues Found

### Critical

1. **PBKDF2 iteration count is low** (`src/lib/encryption/password.ts`). 20,000 iterations meets the 2023 OWASP floor but is weak by current standards. OWASP recommends 600,000 iterations for PBKDF2-SHA256. At 20k iterations, a GPU-based attacker can test millions of passwords/second. Argon2id would be significantly stronger and is the preferred KDF for password hashing.

2. **No device key rotation** (`src/lib/encryption/device.ts`). The device encryption key is generated once and never rotated. If the key leaks (e.g., via backup extraction or secure store vulnerability), all historical and future data is compromised with no recovery path.

### High

3. **Rate limiter resets on app restart** (`src/lib/encryption/ratelimit.ts`). The in-memory rate limiter (5 attempts / 30s) is trivially bypassed by force-closing and reopening the app. A persistent rate limiter (using AsyncStorage or SecureStore with timestamps) would be necessary for real brute-force protection.

4. **No session timeout**. Derived password keys persist in `JournalKeyContext` for the entire foreground session. If a user opens a secure journal and hands their phone to someone, the journal remains unlocked until they navigate home. There is no inactivity-based auto-lock.

5. **Biometric bypass concern**. Biometric is a gate before showing the password prompt, but if biometric fails, the user can still see the password prompt. This means biometric adds friction but not a true second factor.

### Medium

6. **JavaScript memory model limitations**. `Uint8Array.fill(0)` zeroes the key buffer, but JavaScript does not guarantee the GC won't have copied the data elsewhere (e.g., during V8 optimizations, closures, or string conversions). Plaintext content in memory is never explicitly zeroed. This is an inherent limitation of React Native.

7. **No integrity verification of the journal index**. The `journals.json` index is device-encrypted but there is no separate HMAC or signature. GCM's auth tag helps, but the app should handle decryption failures gracefully.

8. **Password change re-encryption is not atomic** (`src/components/journal/JournalSettings.tsx:147-208`). When changing a password, all pages are re-encrypted sequentially. If the app crashes mid-operation, some pages could be encrypted with the old key and others with the new key, leaving the journal in an inconsistent state. A transaction-based approach (write to temp files, then atomic swap) would be safer.

### Low

9. **No export encryption**. No export/backup feature exists yet, but the sync engine interfaces are already defined (`src/lib/sync/engine.ts`). When implemented, must ensure data never leaves the device unencrypted.

10. **Password strength threshold is permissive**. The app allows creating secure journals with weak passwords without blocking, only warning.

## Verdict

The fundamentals are solid: audited crypto libraries, AES-256-GCM, proper nonce management, key zeroing, dual-layer design, no custom crypto. This is better than most mobile apps.

The main gaps are operational: low PBKDF2 iterations (should be 600k+ or switch to Argon2id), ephemeral rate limiting, no key rotation, no session timeout, and non-atomic re-encryption.
