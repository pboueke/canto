### Phase 2: Minor Bug Fixes (Issues #25, #28, #15, #20, #21)

Small behavioral fixes with localized impact.

#### Issue #25 — Fix bidirectional debounce sync

**File:** `src/components/journal/FilterBar.tsx` lines 45-48

The useEffect only clears `localQuery` when `filter.query` becomes empty. If an external component sets `filter.query` to a non-empty value, `localQuery` stays stale.

**Fix:**

```typescript
useEffect(() => {
  if (filter.query !== localQuery) {
    setLocalQuery(filter.query);
  }
}, [filter.query]);
```

Note: This syncs in both directions. The debounce timer in the `onChange` handler still prevents rapid external→local→external loops since `setFilter` is debounced.

**Test:** `src/components/journal/__tests__/FilterBar.test.tsx` — update filter.query externally, assert localQuery updates.

#### Issue #28 — Add try-catch to attachment save handlers

**File:** `app/page/[id].tsx` lines 209-238 and 240-289

Both `handleAddImage` and `handleAddFile` call `saveAttachment()` without try-catch. If the save fails, the attachment is added to the draft with an empty path.

**Fix:** Wrap `saveAttachment` and `updateDraft` in try-catch, show an Alert on failure, and don't add the attachment to the draft:

```typescript
try {
  const path = await saveAttachment(journalId!, id!, attachment, base64Data);
  attachment.path = path;
  updateDraft({ images: [...draft.images, attachment] });
} catch (err) {
  Alert.alert(t.common.error, err instanceof Error ? err.message : String(err));
}
```

Same pattern for `handleAddFile`.

**Test:** `app/__tests__/page.test.tsx` — mock `saveAttachment` to throw, assert draft is not updated and Alert is shown.

#### Issue #15 — Resilient cloud import attachments

**File:** `src/components/home/NewJournalModal.tsx` lines 192-206

`Promise.all` for attachment downloads means one failure aborts all. Metadata may already be partially saved.

**Fix:** Switch to `Promise.allSettled` and collect failures:

```typescript
const results = await Promise.allSettled(
  attachments.map(async (att) => {
    const filename = att.path.split('/').pop() ?? att.path;
    const remotePath = `gdrive://${journal.id}/attachments/${filename}`;
    const data = await store.downloadAttachment(remotePath);
    if (data) {
      const localPath = await localStore.saveAttachment(journal.id, page.id, att, data);
      att.path = localPath;
    }
    return att;
  }),
);

const failures = results.filter((r) => r.status === 'rejected');
if (failures.length > 0) {
  importWarnings.push(`${failures.length} attachment(s) failed to download for page ${page.id}`);
}
```

Show a toast/alert after import completes if there were any warnings.

**Test:** Mock `downloadAttachment` to reject for one attachment, assert import completes and warnings are collected.

#### Issue #20 — Preserve original attachment encryption flag

**File:** `src/lib/backup/import.ts` lines 194-206 (and `import.web.ts`)

The `encrypted` flag is recalculated as `owner.encrypted && !!derivedKey`. If importing without the password, encrypted attachments are marked as unencrypted.

**Fix:** Preserve the original flag from the backup. The encryption state of the data doesn't change just because we don't have the key at import time:

```typescript
// Before:
const reEncrypt = owner.encrypted && !!derivedKey;
// ...
encrypted: reEncrypt,

// After:
encrypted: owner.encrypted,
```

The actual encryption/decryption of attachment data during import should remain gated on `derivedKey` availability — but the metadata flag should reflect the true state.

**Test:** `src/lib/backup/__tests__/import.test.ts` — import an encrypted backup without providing derivedKey, assert attachment `encrypted` flag is `true` (not `false`).

### Phase 3: Data Safety Hardening (Issues #16, #22, #23, #30)

Fixes that make data handling more robust against corruption and edge cases.

#### Issue #16 — Consistent folder cache key format

**File:** `src/lib/sync/gdrive/store.ts` line 114

The cache key omits parentId when it's falsy, creating collision risk for same-name folders in different parents.

**Fix:** Always include parentId in the key (use `'root'` as default):

```typescript
// Before:

// After:
const cacheKey = `folder:${parentId ?? 'root'}/${name}`;
```

**Test:** `src/lib/sync/gdrive/__tests__/store.test.ts` — create two folders with same name but different parents, assert they get distinct cache entries.

#### Issue #22 — Use safeJsonParse consistently

**Files:** `src/lib/storage/local.ts`, `src/lib/storage/local.web.ts`, `src/lib/backup/import.ts`, `src/lib/backup/import.web.ts`

`safeJsonParse` exists in `gdrive/store.ts` but isn't used elsewhere. Unguarded `JSON.parse` calls crash on corrupted data.

**Fix:**

1. Extract `safeJsonParse` to a shared utility: `src/lib/utils/json.ts`
2. Replace all bare `JSON.parse(x) as T` calls in storage and import files with `safeJsonParse<T>(x, label)`

The utility:

```typescript
export function safeJsonParse<T>(content: string, label: string): T {
  try {
    return JSON.parse(content) as T;
  } catch (err) {
    throw new Error(
      `Invalid JSON in ${label}: ${err instanceof Error ? err.message : String(err)}`,
    );
  }
}
```

**Locations to update:**

- `local.ts` lines 161, 195, 206
- `local.web.ts` lines 203, 224, 233
- `import.ts` lines 111-113
- `import.web.ts` corresponding lines
- `gdrive/store.ts` lines 10-15 (replace local definition with import)

**Test:** Existing tests cover the happy path. Add a test for `safeJsonParse` itself in `src/lib/utils/__tests__/json.test.ts`.

#### Issue #30 — IndexedDB timeout and abort handling

**File:** `src/lib/storage/local.web.ts` lines 84-107

All IDB transaction helpers lack timeout and abort handlers. A hung transaction leaves a promise that never settles.

**Fix:** Add `tx.onabort` handler and wrap in a timeout:

```typescript
const IDB_TIMEOUT_MS = 10_000;

async function idbGet(path: string): Promise<string | null> {
  const db = await openDB();
  return new Promise((resolve, reject) => {
    const timeout = setTimeout(
      () => reject(new Error(`[IDB] Timeout reading ${path}`)),
      IDB_TIMEOUT_MS,
    );
    const tx = db.transaction(STORE_NAME, 'readonly');
    const store = tx.objectStore(STORE_NAME);
    const req = store.get(path);
    req.onsuccess = () => {
      clearTimeout(timeout);
      const result = req.result as { path: string; data: string } | undefined;
      resolve(result?.data ?? null);
    };
    req.onerror = () => {
      clearTimeout(timeout);
      reject(req.error);
    };
    tx.onabort = () => {
      clearTimeout(timeout);
      reject(tx.error ?? new Error('[IDB] Transaction aborted'));
    };
  });
}
```

Apply the same pattern to `idbPut`, `idbDelete`, `idbDeletePrefix`, and `idbListKeys`.

**Test:** `src/lib/storage/__tests__/local.web.test.ts` — mock a transaction that never completes, assert the promise rejects after timeout.

### Phase 4: DRY Refactors (Issues #17, #18, #19, #27)

Larger refactors that extract shared logic. These reduce maintenance burden and make future fixes single-site.

#### Issue #27 — Extract download helper in page component

**File:** `app/page/[id].tsx` lines 345-374

`handleOpenFile` duplicates the web download logic from `downloadAttachment` utility.

**Fix:** Extract the base64→blob→download logic to a shared helper (or reuse the existing `downloadAttachment` from a utility module if one exists). Both `handleOpenFile` and `handleDownloadImage` should call it.

```typescript
// In a utility, e.g. src/lib/utils/download.ts (or inline if only used here):
function downloadBase64(data: string, filename: string): void {
  const byteChars = atob(data);
  const byteNumbers = new Uint8Array(byteChars.length);
  for (let i = 0; i < byteChars.length; i++) byteNumbers[i] = byteChars.charCodeAt(i);
  const blob = new Blob([byteNumbers]);
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = filename;
  a.click();
  URL.revokeObjectURL(url);
}
```

**Test:** Existing download tests should cover. Add unit test for the utility if extracted.

#### Issues #17, #18, #19 — Platform code deduplication

These three issues share the same pattern: business logic is duplicated between `.ts` (native/Expo) and `.web.ts` (browser) files, with only the IO layer differing.

**Strategy:** For each pair, extract shared business logic into a `.shared.ts` file that accepts an IO adapter interface. The platform files become thin wrappers that inject their IO implementation.

##### Issue #17 — Storage deduplication

**Files:** `src/lib/storage/local.ts` (~500 lines) + `local.web.ts` (~500 lines)

**Shared logic:** index read/write, journal CRUD, re-encryption, attachment path calculation, readEncrypted/writeEncrypted orchestration.

**IO adapter interface:**

```typescript
interface StorageIO {
  readFile(path: string): Promise<string | null>;
  writeFile(path: string, data: string): Promise<void>;
  deleteFile(path: string): Promise<void>;
  deletePrefix(prefix: string): Promise<void>;
  listFiles(prefix: string): Promise<string[]>;
  fileExists(path: string): Promise<boolean>;
}
```

**New files:**

- `src/lib/storage/local.shared.ts` — all business logic, parameterized by `StorageIO`
- `local.ts` — provides `ExpoFileIO` implementing `StorageIO` via Expo `Directory`/`File`
- `local.web.ts` — provides `IndexedDbIO` implementing `StorageIO` via IDB helpers

**Estimated reduction:** ~300 lines of duplicated code eliminated.

##### Issue #18 — Export deduplication

**Files:** `src/lib/backup/export.ts` + `export.web.ts`

**Shared logic:** ZIP construction, manifest generation, journal/page/attachment serialization.

**IO adapter interface:**

```typescript
interface ExportIO {
  saveAndShare(zipBlob: Blob, filename: string): Promise<void>;
}
```

**New files:**

- `src/lib/backup/export.shared.ts` — ZIP building logic
- `export.ts` — provides native save+share via `expo-sharing`
- `export.web.ts` — provides browser download via anchor element

##### Issue #19 — Import deduplication

**Files:** `src/lib/backup/import.ts` + `import.web.ts`

**Shared logic:** ZIP parsing, attachment handling, page creation, journal saving.

**IO adapter interface:**

```typescript
interface ImportIO {
  loadZipData(uri: string): Promise<Uint8Array>;
}
```

**New files:**

- `src/lib/backup/import.shared.ts` — all import logic
- `import.ts` — provides native file reading via Expo `File`
- `import.web.ts` — provides web file reading via `fetch`

**Tests for all three:**

- Existing tests should pass with no changes (the shared logic is identical)
- Add adapter-level unit tests for each IO implementation

## Risk Assessment

- **Phase 1 (cleanups):** Negligible risk — removing dead code and unused deps
- **Phase 2 (bug fixes):** Low risk — localized behavioral changes with clear boundaries
- **Phase 3 (hardening):** Low-medium risk — adding validation could reject previously-accepted data. Need to verify no existing data uses edge cases (empty tokens, malformed JSON that happens to work)
- **Phase 4 (DRY refactors):** Medium risk — significant file restructuring. Must run full test suite on both native and web. No logic changes, but import path changes could break things if not updated everywhere.

## Dependencies

- Phase 3 Issue #22 (safeJsonParse) should land before Phase 4 Issues #17-19, as the shared modules should use the safe variant
- Phase 3 Issue #23 depends on 17.2 Issue #13 (validatePage in deserializePages) being complete for consistent validation coverage
- Phase 2 Issue #20 (encryption flag) interacts with 17.1 Issue #4 (import error handling) — coordinate to avoid merge conflicts

## Execution Order

1. Phase 1 — zero risk, quick wins
2. Phase 2 — independent bug fixes
3. Phase 3 — hardening (depends on nothing)
4. Phase 4 — refactors last (biggest blast radius, benefits from earlier fixes being in place)

## Questions for Review

1. **Issues #17-19 (deduplication):** This is a significant refactor touching core storage/backup code. Should this be deferred to a dedicated release (e.g., 0.18.0) rather than bundled with bug fixes? The duplicated code is a maintenance burden but not a user-facing issue.

2. **Issue #25 (FilterBar sync):** The bidirectional sync could cause a render loop if the parent and child disagree on the query value. Should we add a guard (e.g., only sync if the component isn't actively editing)?

3. **Issue #20 (encryption flag):** Preserving the original `encrypted: true` flag when importing without a key means the attachment metadata claims encryption but the app can't decrypt it. Should we instead mark it as `encrypted: true` but add an `inaccessible: true` flag to surface this in the UI?
