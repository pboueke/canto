# Plan: 9.4 Async Native Crypto via expo-crypto

## Problem

AES-GCM decryption via `@noble/ciphers` is pure JavaScript — each call blocks the JS thread synchronously. For image attachments (2MB+), this freezes the UI for hundreds of milliseconds per image, even with the queue/yield mitigations from 9.3.

## Goal

Replace synchronous `@noble/ciphers` AES-GCM calls with `expo-crypto`'s native `aesEncryptAsync` / `aesDecryptAsync`, which run on a native thread and are genuinely non-blocking. **No dev build required — expo-crypto works with Expo Go.**

## Analysis

### expo-crypto AES-GCM API (available since SDK 55)

```typescript
import { aesEncryptAsync, aesDecryptAsync, AESEncryptionKey, AESSealedData } from 'expo-crypto';

// Key management
const key = AESEncryptionKey.import(existingUint8Array);
const bytes = await key.bytes();
const hex = await key.encoded('hex');

// Encrypt → AESSealedData
const sealed = await aesEncryptAsync(plaintext, key);
const combined = sealed.combined(); // Uint8Array: [iv][ciphertext][tag]

// Decrypt
const decrypted = await aesDecryptAsync(sealed, key, { output: 'bytes' });

// Reconstruct from stored bytes
const sealed = AESSealedData.fromCombined(storedBytes);
```

### Current crypto usage (all synchronous, `@noble/ciphers`)

| Function                                         | Files using it                                                                | Current call pattern            |
| ------------------------------------------------ | ----------------------------------------------------------------------------- | ------------------------------- |
| `aesGcmEncrypt(plaintext, key): string`          | `device.ts`, `password.ts`, `local.ts` (×3), `SecuritySettingsModal.tsx` (×2) | Sync, returns base64 string     |
| `aesGcmDecrypt(ciphertext, key): string`         | `device.ts`, `password.ts`, `local.ts` (×2), `SecuritySettingsModal.tsx` (×1) | Sync, returns plaintext string  |
| `aesGcmEncryptBytes(plaintext, key): Uint8Array` | `export.ts` (×4)                                                              | Sync, returns raw bytes for ZIP |
| `aesGcmDecryptBytes(data, key): string`          | `import.ts` (×2)                                                              | Sync, returns plaintext string  |

### Dependencies not affected

- `@noble/hashes` — PBKDF2 in `password.ts`. Keep as-is (runs once at unlock, not per-image).
- `crypto.getRandomValues()` — Hermes native, no change.
- `bytesToHex` / `hexToBytes` in `device.ts` — currently from `@noble/ciphers/utils.js`, will move to local helpers or `AESEncryptionKey.encoded('hex')`.

## Wire format compatibility

The current format is `[12-byte nonce][ciphertext][16-byte GCM tag]` encoded as base64 (string variants) or raw Uint8Array (bytes variants).

`expo-crypto`'s `AESSealedData.combined()` produces the same `[iv][ciphertext][tag]` layout. We need to verify the exact byte order matches, and if so, existing encrypted data can be read without migration via `AESSealedData.fromCombined()`.

**If the formats differ**, we add a version byte or try expo-crypto first, fall back to `@noble/ciphers` for legacy data. This must be verified in Step 2.

### Step 3: Rewrite `src/lib/encryption/utils.ts`

Replace the 4 core functions with async expo-crypto equivalents:

```typescript
import { aesEncryptAsync, aesDecryptAsync, AESEncryptionKey, AESSealedData } from 'expo-crypto';

export async function aesGcmEncrypt(plaintext: string, key: Uint8Array): Promise<string> {
  const aesKey = AESEncryptionKey.import(key);
  const sealed = await aesEncryptAsync(textEncoder.encode(plaintext), aesKey);
  return uint8ToBase64(sealed.combined());
}

export async function aesGcmDecrypt(ciphertext: string, key: Uint8Array): Promise<string> {
  const data = base64ToUint8(ciphertext);
  const sealed = AESSealedData.fromCombined(data);
  const aesKey = AESEncryptionKey.import(key);
  const result = await aesDecryptAsync(sealed, aesKey, { output: 'bytes' });
  return textDecoder.decode(result);
}

export async function aesGcmEncryptBytes(plaintext: string, key: Uint8Array): Promise<Uint8Array> {
  const aesKey = AESEncryptionKey.import(key);
  const sealed = await aesEncryptAsync(textEncoder.encode(plaintext), aesKey);
  return sealed.combined();
}

export async function aesGcmDecryptBytes(data: Uint8Array, key: Uint8Array): Promise<string> {
  const sealed = AESSealedData.fromCombined(data);
  const aesKey = AESEncryptionKey.import(key);
  const result = await aesDecryptAsync(sealed, aesKey, { output: 'bytes' });
  return textDecoder.decode(result);
}
```

Keep `uint8ToBase64`, `base64ToUint8`, `generateSalt` unchanged.

### Step 4: Replace `bytesToHex` / `hexToBytes` in `device.ts`

Replace `@noble/ciphers/utils.js` imports with local implementations:

```typescript
function bytesToHex(bytes: Uint8Array): string {
  return Array.from(bytes, (b) => b.toString(16).padStart(2, '0')).join('');
}

function hexToBytes(hex: string): Uint8Array {
  const bytes = new Uint8Array(hex.length / 2);
  for (let i = 0; i < hex.length; i += 2) {
    bytes[i / 2] = parseInt(hex.substring(i, i + 2), 16);
  }
  return bytes;
}
```

## Risks & Considerations

1. **Wire format mismatch** — If expo-crypto's `[iv][ciphertext][tag]` layout differs from noble's, we need a migration or dual-read strategy. Step 2 catches this early.

2. **Jest/testing** — expo-crypto may not work in Jest (Node.js, not native). May need a mock that delegates to `@noble/ciphers` for testing only, or use `expo-crypto`'s web/JS fallback.

3. **No Expo Go breakage** — expo-crypto is part of Expo's standard module set, included in Expo Go. No dev build or prebuild required.

4. **Performance** — The main benefit is non-blocking (async/native thread), not raw speed. `@noble/ciphers` may actually be faster for small payloads. The win is UX: the JS thread stays free to render during 2MB+ image decrypts.

5. **`@noble/hashes` stays** — Only `@noble/ciphers` is removed. PBKDF2 via `@noble/hashes` remains for key derivation.
