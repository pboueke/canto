## Part A — Lock-screen privacy

### A.1 Incident and evidence

User report: after leaving the app while on the editor, Canto asked for the password on return, but part of the typed text was still visible. The user asked for a full-screen lock or masked text, and wanted the typed text to require the password as well, without being shown.

Source-verified causes:

1. **The lock prompt is translucent.** `src/components/common/AutoLockModal.tsx:29` renders `<Modal transparent>` over a `rgba(0,0,0,0.5)` overlay with a card capped at 400px. It is mounted globally beside the `<Stack>` (`app/_layout.tsx`). Every screen underneath shows through.
2. **Screens do not react to the lock in their render.** `app/page/[id].tsx` reads `locked` from `useKeyLease` but only checks it in `handleSave`/`handleDelete`. `draft.text`, tags, comments and location keep rendering. The journal and calendar screens redirect only when the journal is missing, not when it is locked.
3. **The discard guard traps the user in a locked editor.** `AutoLockModal.handleDismiss` calls `router.replace('/')`. The editor's `beforeRemove`/`BackHandler` guards (`app/page/[id].tsx`) intercept this when the page is dirty and show "Discard changes?". "Keep" leaves the full plaintext on screen in an editor that can neither save nor unlock.
4. **`replace('/')` leaves the stack mounted.** The journal list (with its decrypted overview) stays mounted under the new top route.
5. **The resume order exposes content.** On `background`/`inactive`, `JournalKeyContext` only purges the encrypted attachment cache and records a timestamp. The lock decision runs after the app is `active` again, behind `await getAutoLockTimeout()`, so the editor paints before the modal appears.
6. **The app switcher shows content.** No `FLAG_SECURE`, `setRecentsScreenshotEnabled`, `expo-screen-capture` or privacy overlay exists. `/android` is generated, so native changes must go through `plugins/` and `app.config.js`.
7. **Plaintext stays in memory after the lock.** The editor's `draft`/`page` state and `useJournalOverview` keep decrypted content. Only keys and the attachment display caches are cleared.

### A.2 Product and safety contract

1. When an auto-lock fires, no journal content (text, title, tags, comments, location, previews, thumbnails) may be visible or reachable on any screen until the journal is unlocked again.
2. While the app is not `active`, Canto shows an opaque privacy cover. The OS app-switcher thumbnail must not show journal content on Android 13+ (API 33) or on iOS.
3. On resume, content stays covered until the lock decision has been made.
4. Unsaved typing is never left on screen after a lock, and is not silently lost. It is stored encrypted with the journal key and shown again only after the user unlocks that journal.
5. Locking drops references to decrypted page and overview state. JS strings cannot be zeroed; dropping references is the guarantee.
6. Screenshots remain allowed by default. Blocking them (`FLAG_SECURE`) is an explicit user setting.
7. No change to the `canto-data` format, schema version, export, sync or import. Drafts are app-local records.

### A.3 Scope

**In scope**

- `src/components/common/AutoLockModal.tsx` → opaque lock screen.
- New `src/components/common/PrivacyCover.tsx`, mounted in `app/_layout.tsx`.
- `src/contexts/JournalKeyContext.tsx`: resume ordering, cached timeout, a `privacyCovered` state.
- `app/page/[id].tsx`, `app/journal/[id]/index.tsx`, `app/journal/[id]/calendar.tsx`: a locked render state and lock-aware navigation guards.
- `src/hooks/useStorage.ts` (`usePage`), `src/lib/journal-overview.ts` / `useJournalOverview`: drop decrypted state when the key goes away.
- Encrypted draft storage in `src/lib/storage/local.ts`, `local.web.ts` and `types.ts`.
- New `plugins/withAndroidRecentsPrivacy.js`, registered in `app.config.js`.
- `src/components/home/SecuritySettingsModal.tsx`: "Block screenshots" toggle.
- i18n strings for every supported language.

**Out of scope**

- In-place unlock from inside the editor. The lock still returns to home, and the draft is offered again when the page is reopened. This can be a follow-up.
- Changes to `canto-data`.
- Changing the auto-lock timeout options or the behavior of passwordless journals (see A.6, question 3).

### A.4 Design

#### A.4.1 Opaque lock screen

1. Replace `<Modal transparent>` with a full-screen opaque view in the theme background colour: no dim overlay, `statusBarTranslucent`, and on web a fixed full-viewport layer. Keep the lock icon, title, message and button.
2. Order on lock: show the lock screen (synchronous listener, already first in `triggerAutoLock`) → `clearAll()` → screens switch to their locked render state.
3. On dismiss: `router.dismissAll()`, then `router.replace('/')`, so no journal or page route stays mounted.
4. Android hardware back on the lock screen behaves like dismiss. It must never reveal the previous screen.

#### A.4.2 Locked render state on content screens

1. Add a shared `LockedPlaceholder` (icon + "Journal locked") component.
2. `app/page/[id].tsx`:
   - When `locked` is true and the journal is secure, render `LockedPlaceholder` instead of the editor or viewer.
   - Make the `beforeRemove` and `BackHandler` guards return early while locked, using a ref so the listener sees the current value, so a lock always passes navigation through.
   - In the `onJournalLocked` path, after flushing the draft (A.4.4), call `setDraft(null)`, `setIsDirty(false)` and `setIsEditing(false)`.
3. `app/journal/[id]/index.tsx` and `calendar.tsx`: render `LockedPlaceholder` instead of the page list or calendar when the journal is secure and locked.
4. `usePage` and `useJournalOverview`: when `derivedKey` becomes null for a secure journal, reset the held `page`/`overview` to null instead of keeping the last value.

#### A.4.3 Privacy cover and resume ordering

1. `PrivacyCover` is an opaque, theme-coloured full-screen view at the root of `app/_layout.tsx`, above the `Stack` and below `AutoLockModal`. It shows the app icon or wordmark only.
2. `JournalKeyContext` exposes a `privacyCovered` boolean:
   - It becomes true synchronously on `background`/`inactive`. On iOS, `inactive` precedes the system snapshot.
   - On `active`, it stays true until the lock decision completes; then the lock fires or the cover lifts.
3. ~~Cache the auto-lock timeout.~~ _Implemented differently:_ the cover stays up until the (async) `getAutoLockTimeout()` decision and any due lock finish, so no cache is needed and content is never shown first.
4. Android app switcher, via `plugins/withAndroidRecentsPrivacy.js`, which patches `MainActivity.onCreate` idempotently:
   - On API 33+, call `setRecentsScreenshotEnabled(false)`. This hides the thumbnail and keeps screenshots working.
   - Below API 33, rely on `PrivacyCover`, which is best effort on Android because the snapshot can be taken before JS re-renders. Users who need a guarantee there can enable "Block screenshots".
5. "Block screenshots" setting:
   - Persisted alongside the auto-lock timeout.
   - Applied via `expo-screen-capture` (`preventScreenCaptureAsync` / `allowScreenCaptureAsync`). On Android this sets `FLAG_SECURE`, which covers recents on all API levels. On iOS it blocks screen recording and protects the app switcher.
   - Default off. Re-applied on app start. No-op on web.
   - Check exact API names and the iOS app-switcher option against the `expo-screen-capture` version that matches SDK 55 before implementing.

#### A.4.4 Encrypted unsaved drafts

1. **Storage API.** Add to `StorageAdapter` (native and web):

   ```ts
   saveDraft(journalId: string, draft: Page, derivedKey?: Uint8Array): Promise<void>;
   getDraft(journalId: string, pageId: string, derivedKey?: Uint8Array): Promise<Page | null>;
   listDrafts(journalId: string, derivedKey?: Uint8Array): Promise<DraftSummary[]>; // ids + modified only
   deleteDraft(journalId: string, pageId: string): Promise<void>;
   ```

2. **Encryption.** Drafts use the same layering as page records: device layer, plus the password layer for secure journals. They go through the existing write barrier and key-lease checks, including the all-zero-key assertion.
3. **Location.** Drafts live in a per-journal `drafts/` directory on native, or a separate key prefix on web. They are explicitly excluded from:
   - catalog rebuild and integrity checks;
   - local-page recovery scans;
   - export and backup manifests;
   - sync;
   - import verification.

   Deleting a journal or page deletes its drafts. Saving a page deletes its draft.

4. **When to write.** Flush while the lease is still valid:
   - on AppState `background`/`inactive` while the editor is dirty;
   - before `clearAll` zeroes keys, via a pre-lock hook (`onAutoLock` listeners run before `clearAll`, so the editor registers a flush there);
   - debounced while typing (about 3s idle) to survive the process being killed.

   Writes are serialized per page; the last write wins.

5. **Restore.** When the page opens with a valid key and a draft exists, load the draft instead of the saved page, mark it dirty, and show a localized "Unsaved changes restored" banner with a "Discard draft" action. A draft is offered even if the saved page changed since (e.g. sync); unsaved typing is never discarded silently.
6. **Finding drafts.** "New page" saves an empty page before the editor opens, so every draft belongs to an existing page. After unlocking, the journal screen lists an "Unsaved draft" row for each page that has a stored draft, which opens it for editing.
7. **Discard semantics.** "Discard changes" in the editor deletes the draft.
8. **Failure.** If the flush fails (no lease, storage error), the draft is still dropped from memory on lock. A lock never leaves plaintext on screen. Record a localized, content-free diagnostic.

## Part B — Device-key rotation lockout

**Status:** Proposed

### B.1 Incident and evidence

**Version mapping.** There are no git tags after `v0.19.2`; versions are tracked in `app.json`.

- 0.20.0 = `59de067`. It still contains the original bug.
- 0.20.1 = `ddd5d8e`, `47f8233`, `49fbd32`; versionCode 28.
- 0.20.2 = `4b3c3aa`, `17a31d3`; versionCode 29, R8 off.
- HEAD `b149acc` is also labelled 0.20.2 but is versionCode 30 with R8 on. Two different builds share the name "0.20.2", so the reporter's versionCode is needed.

#### B.1.1 Original corruption (≤ 0.20.0)

1. Auto-lock zeroes the cached password key in place (`releaseAndZeroAesKey`). An editor that was already mounted kept that zeroed buffer.
2. `savePage` then:
   - read the catalog with the zero key; the read fell back to the password ciphertext, which failed to parse, so the catalog came back null;
   - rebuilt the catalog with `skipMalformedPages=true`, which skipped every page;
   - committed a catalog containing only the edited page, with its page and catalog password layers encrypted under **32 zero bytes**.
3. Separately, `readIndex` mapped an unreadable index to `{journals: []}`, so a later index write could drop journals and leave their directories orphaned.

#### B.1.2 The 0.20.1 fix (`ddd5d8e`)

What it adds:

- epoch key leases;
- an all-zero-key rejection in `encryptForStorage` (`src/lib/storage/integrity.ts:79-97`, called at `local.ts:686`);
- strict three-state reads;
- transactional writes;
- a write barrier;
- the device-key bootstrap.

Assessment:

1. It stops new zero-key writes. The effective protection is the storage-layer zero check. The second "re-check the lease" in `handleSave` (`app/page/[id].tsx`) reads a stale `locked` closure value and does nothing.
2. It does not repair existing zero-key records. Under the strict reader they block access with `CATALOG_UNREADABLE`.
3. `handleUnlock` (`app/index.tsx:155-180`) maps a null result _and any thrown error_ to `t.home.wrongPassword`. A correct password on a zero-key journal is therefore reported as "Wrong password".
4. `readEncryptedDetailed` (`local.ts:162-180`) falls back to device-only content when the password layer fails. A wrong password is distinguishable from corruption only by a JSON parse failure.
5. "Recover local pages" (`49fbd32`) is non-destructive but cannot recover zero-key pages:
   - with the real key, the record fails to decrypt;
   - with the zero key, `assertUsableDerivedKey` rejects it with `JOURNAL_LOCKED`.

   It also cannot reach orphaned journal directories.

#### B.1.3 Device-key rotation (`src/components/home/SecuritySettingsModal.tsx:57-115`)

Order of operations:

1. `prepareKeyRotation`.
2. `beginKeyRotation`: PREVIOUS = old key, CURRENT = new key.
3. `reencryptAll`: stages every indexed journal, the index and a completion marker, then applies the transaction.
4. `commitKeyRotation`: deletes PREVIOUS.
5. Clear the completion marker.
6. `clearSession`.

Restart recovery after a process kill is correct at every step. The defects are in the in-app error and concurrency paths:

- **Bug A — critical.** If `applyStorageTransaction` throws after it has started overwriting files but before the completion marker lands (EIO, ENOSPC), the catch block calls `abortKeyRotation()`. That restores CURRENT = old key and **deletes PREVIOUS**. The new key now exists only in JS memory, but some files are already encrypted with it. On restart, `recoverTransactions` replays the `committing` transaction and publishes the whole library under the lost key. The result is `INDEX_UNREADABLE`/`DEVICE_DECRYPT_FAILED` (the home recovery card), and "Wrong password" before restart. The bug has existed since `88f2d97` (0.19.2).
- **Bug B.** `reencryptAll` rotates only indexed journals. Orphaned journal directories from the bad era, and journals mid-import, stay on the old key, which is then deleted. They become permanently unreadable.
- **Bug C.** The device provider's `cachedKey` still holds the old key when the write barrier releases queued writers; it is cleared only at `clearSession`. A queued attachment write lands under the destroyed key. Index and catalog writers fail closed, so this loses attachments but does not cause a lockout.
- **Rotation over zero-key data.** Zero-key password layers are re-wrapped unchanged. Rotation neither causes nor fixes the zero-key lockout.

All four scenarios were reproduced in jest. The repros are ported as regression tests in `src/lib/__tests__/deviceKeyRotationSafety.test.ts` (native) and `deviceKeyRotationSafetyWeb.test.ts` (web):

- A: failure during apply → total lockout;
- B: orphaned directory left on the deleted key;
- C: queued write under the stale key;
- D: zero-key journal plus correct password → `CATALOG_UNREADABLE` → "Wrong password".

> **Update (2026-10-21, Android device testing):** rotation in 0.19.2–0.20.2 never re-encrypted journal records on Android. Directory uris end with `/`, so the journal prefix (`${dir.uri}/`) matched nothing. Only the index was rotated before the old key was deleted. If the reporter rotated on Android, this, not the zero-key bug, is the most likely cause of her lockout, and her data is recoverable only from Drive or an export. See `.claude/notes/2026-10-21-1.md`.

### B.2 Hypotheses, ranked

1. **High — zero-key legacy records**, combined with the strict reader and the "Wrong password" mislabel. This applies if she sees "Wrong password". It matches the original incident (only the edited page visible, export failing). Rotation was probably a coincidence or an attempted fix. **Recoverable on the device.**
2. **Medium-low — Bug A.** Requires that she saw an error alert during rotation. She would then see the index recovery card after a restart. **Not recoverable on the device**; only Drive sync or a `.canto.zip` export can restore the data.
3. **Low — device key unavailable** (Keystore invalidated, reinstall, restore). This shows its own card and is unrelated to rotation.
4. **Low — R8/SecureStore record conversion on the versionCode 30 build.** It would block startup, so she could not have rotated at all.
5. **Low for the lockout — Bugs B and C.** They destroy orphaned journals or attachments, not her main journal.
6. **Last — forgotten password.** It cannot be told apart from (1) until unlock reports real error codes (B.4.3).

### B.3 Product and safety contract

1. A device-key rotation never deletes a key that any on-disk ciphertext still needs. The fallback key is deleted only after the index and a sample of every rotated file trial-decrypt with CURRENT.
2. Rotation covers every journal directory on disk, or refuses to start.
3. No write can land under a key that is about to be retired.
4. The unlock screen says "Wrong password" only when the password verification itself fails. Integrity conditions show their own localized state and safe next actions.
5. Legacy zero-key records are recoverable in place: re-encrypted with the real key in one crash-recoverable transaction, with no data loss on failure.
6. The fail-closed guarantees from 0.20.1 stay intact; no tolerant fallback is reintroduced.

### B.4 Design

#### B.4.1 No separate hotfix release

Store releases take more than a week to become available, so there is no 0.20.3. Every fix in Parts A and B ships together in 0.21.0, and rotation stays available in its fixed form (B.4.2).

#### B.4.2 Safe rotation

1. Move the begin/commit/abort orchestration from the UI into `LocalStore` (for example `rotateDeviceKey()`), so the commit point is decided where the transaction state is known.
2. Abort and restore the old key **only** if no rotation transaction has reached `committing`. Once committing, failures must leave both keys in SecureStore and surface a "rotation interrupted: restart to finish" state. Restart recovery completes or rolls forward.
3. Before `commitKeyRotation` deletes PREVIOUS, trial-decrypt the index, every journal's metadata and catalog, and a sample of page records with CURRENT.
4. Enumerate journal directories on disk:
   - re-encrypt unindexed directories as well;
   - or refuse to rotate (with a localized message) while unindexed directories or `.imports` markers exist.

   **Decision: refuse.** Unindexed directories are already an integrity condition that recovery should handle first.

5. Free-space preflight. Staging roughly doubles the library's size, so refuse rotation if free space is below that plus a margin.
6. Write barrier: swap or clear the device provider's cached key **inside** the barrier, before queued writers are released.
7. Web parity: `local.web.ts` (around `:1929`) has the same index-scoped design. Apply the same changes and tests.

#### B.4.3 Truthful unlock errors

1. Verify the password strictly against `metadata.json`'s password layer, with no device-only fallback. Only a password-layer authentication failure on metadata maps to `wrongPassword`.
2. `handleUnlock` classifies errors:
   - `StorageIntegrityError` codes (`CATALOG_UNREADABLE`, `INDEX_UNREADABLE`, `DEVICE_DECRYPT_FAILED`, `LEGACY_ZERO_KEY`, …) open the integrity/recovery state for that journal, with localized text and next actions;
   - anything else shows a generic "Couldn't open journal" with the opaque code.
3. Log the cause codes, with opaque record IDs only, never content, paths or keys.
4. Fix the stale-closure lease re-check in `handleSave`: call `isLeaseValid(lease)` at each check point.

#### B.4.4 Legacy zero-key recovery

1. When a catalog or page fails the password layer with the real (verified) key, the scanner retries that record with the 32-zero-byte key through a dedicated read-only legacy path. `assertUsableDerivedKey` stays strict for writes.
2. Records that decrypt with the zero key and validate are reported as `LEGACY_ZERO_KEY`.
3. "Recover local pages", reachable from the integrity state:
   - re-encrypts those records with the real key in one transaction;
   - then performs the strict catalog rebuild;
   - leaves raw files untouched on any failure.
4. Cloud import applies the same zero-key retry to Drive copies, since sync may have uploaded zero-key content during the bad era. This is unverified, so it ships behind tests only.

#### B.4.5 Support diagnostics

Add a "Copy diagnostics" action on the integrity state. It produces counts only:

- app version and versionCode;
- index state;
- per journal, the count of files at each stage: device-layer ok/fail → password layer real key / zero key / neither → JSON valid/invalid;
- unindexed directories present;
- pending rotation or transaction markers.

It contains no content, titles, paths or keys.

### B.5 Affected-user support steps

**Tell her now:** do not reinstall, do not clear app data, do not retry rotation, and do not create or edit journals until the recovery build is out.

**Ask her, with no content involved:**

1. App version and versionCode (Settings / About, or Play Store).
2. The exact message she sees: "Wrong password", the index recovery card, the device-key card, or a startup error.
3. Whether rotation ended with a success alert or an error, and the error text.
4. Whether she could open the journal on 0.20.x _before_ rotating.
5. Whether the journal is password-protected, whether Drive sync is on, and whether any `.canto.zip` exports exist.
6. The result of "Recover local pages", if she reached it.

**Then:**

- If (1) applies (zero-key): the 0.21.0 recovery flow restores her pages on the device.
- If (2) applies (Bug A): restore from Drive or an export. Device data is not recoverable.

### B.6 Tests

1. Port repros A–D as regression tests (native storage).
2. Fault injection at every apply index of the rotation transaction, including the final marker:
   - through the UI path (`rotateDeviceKey` throws), assert both keys remain and the data is readable after restart;
   - through restart recovery.
3. Trial-decrypt gate: a corrupted file after apply blocks `commitKeyRotation`, and PREVIOUS is retained.
4. An unindexed directory or `.imports` marker → rotation refused, nothing changed.
5. Free-space preflight refuses when there is not enough space.
6. A writer queued during rotation writes under the new key, never the retired one.
7. Unlock classification:
   - correct password on a zero-key journal → `LEGACY_ZERO_KEY` integrity state, not `wrongPassword`;
   - wrong password → `wrongPassword`;
   - `INDEX_UNREADABLE` → recovery card;
   - component test for `handleUnlock` mapping.
8. Zero-key recovery:
   - scan reports `LEGACY_ZERO_KEY`;
   - recovery re-encrypts with the real key and rebuilds the catalog;
   - an injected failure leaves raw files byte-identical;
   - `assertUsableDerivedKey` still rejects zero-key writes.
9. Cloud import of zero-key remote records.
10. `handleSave` uses a live lease check: a lock during thumbnail generation blocks the save.
11. Diagnostics output contains no content, paths or keys (snapshot of the structure).
12. Web parity for 2–8.
13. **Manual (maintainer, on device):**
    - rotate a multi-journal library on Android API 29 and 33+, then restart;
    - inject low storage, then rotate → refused;
    - restore a zero-key fixture library, then unlock → recovery → all pages visible.

### B.7 Decisions (2026-10-21)

1. No 0.20.3 hotfix. All fixes ship in 0.21.0.
2. When unindexed journal directories or pending imports exist, rotation refuses and points the user to recovery.
3. Rotation ships in 0.21.0 with the B.4.2 fixes. B.6 manual verification is part of the release gate.

## Implementation notes (2026-10-21)

Implemented on branch `feature/0.21.0-lock-privacy-key-integrity`, not committed.

**Part A**

- `AutoLockModal` is an opaque full-screen `Modal`; dismiss runs `dismissAll()` then `replace('/')`.
- `PrivacyCover` (new) is driven by `JournalKeyContext.isPrivacyCovered()` / `subscribePrivacyCover()`.
- `JournalKeyContext.onBeforeLock()`: drafts flush after the lock screen shows and before keys are zeroed, bounded by `BEFORE_LOCK_TIMEOUT_MS` (3 s).
- Editor:
  - `LockedPlaceholder` after a lock;
  - the discard guards are bypassed while locked;
  - drafts flush on background, before lock, and after 3 s idle;
  - live `isLeaseValid` check in save and delete (fixes the stale-closure re-check).
- `usePage` / `useJournalOverview` drop decrypted state when the key disappears.
- Journal and calendar screens show `LockedPlaceholder` after a lock.
- Storage drafts: `saveDraft` / `getDraft` / `listDrafts` / `deleteDraft` on native (`<journal>/drafts/`) and web (`canto/<journal>/drafts/`).
  - Removed by page delete, journal delete, and password change (`reencryptJournal`).
  - Rotated with the device key.
- `plugins/withAndroidRecentsPrivacy.js`: `setRecentsScreenshotEnabled(false)` on API 33+.
- `expo-screen-capture` added:
  - "Block screenshots" toggle (`src/lib/privacy.ts`);
  - iOS app-switcher blur at startup;
  - its unused `READ_MEDIA_IMAGES` and `DETECT_SCREEN_CAPTURE` permissions are blocked in `app.json`.

**Part B**

- `src/lib/storage/device-key-rotation.ts`: `runDeviceKeyRotation` owns the commit point. The store's `rotateDeviceKey()` runs inside the write barrier, and the cached device key is swapped before queued writers resume.
- After the commit point, a failure seals writes (`RotationInterruptedError`) until restart.
- Preflight refuses for: unindexed journal data, pending imports or transactions, a pending fallback key, oversized legacy attachments, too little free space, or an unreadable index.
- `src/lib/storage/key-integrity.ts`:
  - legacy zero-key classification;
  - strict `verifyJournalKey`;
  - counts-only `collectDiagnostics`.
- `LEGACY_ZERO_KEY` integrity code:
  - overview reads report it;
  - `scanJournalPages` counts legacy pages;
  - `restoreJournalCatalog` re-encrypts legacy pages, metadata, and zero-key attachment payloads in one transaction, only after the key is verified.

## Review follow-ups (2026-10-21)

An independent review found no critical issues, plus 12 findings. All are fixed, with regression tests:

1. **Stale rotation marker.** A completion marker left by a finished rotation could make a crash in the next rotation look completed, deleting the only working key.
   - Preflight now clears a stale marker, or refuses with `ROTATION_PENDING` if it can't.
   - A failed final marker cleanup now reports success.
   - Startup now drops the cached device key after rotation recovery. This fixes a pre-existing stale-key read after a rollback, which the web test exposed.
2. **Editor during lock.** The editor now locks the moment an auto-lock starts, before drafts flush and keys are zeroed.
   - Its guards are bypassed and stale discard prompts do nothing.
   - `forgetDraft` refuses once locked.
3. **Password change with drafts.** It now refuses (`DraftsPendingError`, `journalSettings.draftsPending`) instead of deleting drafts.
4. **Unverifiable key.** `verifyJournalKey` can now return `'unverifiable'` when only zero-key password layers exist.
   - Unlock opens the journal instead of saying "Wrong password".
   - Recovery refuses with `KEY_UNVERIFIABLE` (`journalIntegrity.unverifiableMessage`).
5. **Unlock integrity errors.** The derived key is cleared when verification throws.
6. **Change password.** The current password is checked with an uncached trial key, which is then zeroed. A wrong password no longer replaces the working key.
7. **Privacy cover.** It is now its own top-level `Modal`, so it also covers content modals.
8. **Overlapping resumes.** A resume generation counter keeps an older resume from lifting the cover.
9. **Native transaction cleanup.** The marker is now deleted before the staged files (`retireTransaction`).
10. **Hook state.** `usePage` / `useJournalOverview` expose a value only under the key it was read with, and free it from memory on key loss. There is no render-phase `setState` any more.
11. **Native record ids.** Ids are validated before use as path segments (`safeRecordId`).
12. **Rotation verify.** It now trial-decrypts the index, metadata, catalogs, and up to 10 pages per journal with the new key.
