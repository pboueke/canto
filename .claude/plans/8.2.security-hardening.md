## 1. User-selectable PBKDF2 iterations (Critical)

**Current:** 20,000 iterations hardcoded in two places.
**Problem:** Too low for modern security, but 600k may be too slow on low-end smartphones.
**Target:** Let users choose iteration count per journal from preset options.

### Iteration presets

| Label           | Value       | Description                |
| --------------- | ----------- | -------------------------- |
| Fast (50k)      | `50_000`    | Low-end devices            |
| Standard (200k) | `200_000`   | Balanced (default for new) |
| Strong (600k)   | `600_000`   | OWASP recommended          |
| Maximum (1.2M)  | `1_200_000` | High-security              |

Default for new journals: **200k** (reasonable balance). Users can increase/decrease per journal.

### UI: KDF iteration picker

Add an iteration count selector to both password modals. Only shown when the user enables/sets a password.

**In `NewJournalModal`** (`src/components/home/NewJournalModal.tsx`):

- Below the password confirmation field, add a "Key strength" row with a segmented-button/pill selector showing the 4 presets
- Only visible when password field is non-empty
- Default selection: "Standard (200k)"
- Each option shows label only (not the raw number)

**In `ChangePasswordModal`** (`src/components/journal/ChangePasswordModal.tsx`):

- Below the new password confirmation field, same iteration picker
- Pre-select the journal's current `kdfIterations` value (or nearest preset)
- Only visible when new password field is non-empty

### Migration concern

Existing journals were encrypted with keys derived at 20,000 iterations. Changing the constant means those journals can no longer be decrypted.

**Solution:** Store the iteration count in journal metadata. When deriving a key, use the journal's stored iteration count. New journals store the user's chosen value. Existing journals keep 20,000 until the user changes their password, at which point they pick a new iteration count.

### Changes

1. Add `kdfIterations` field to the `Journal` and `JournalContent` models (optional, defaults to `20_000` for backward compat).
2. Remove the `PBKDF2_ITERATIONS` constants from `password.ts` and `JournalKeyContext.tsx` — iterations are always passed as a parameter.
3. Update `deriveKey()` in `password.ts` to accept iterations as a required parameter.
4. Update `JournalKeyContext.deriveAndCache()` to accept an iterations parameter.
5. Create a shared `KdfIterationPicker` component (`src/components/common/KdfIterationPicker.tsx`) — segmented pill selector with the 4 presets.
6. Update `NewJournalModal` — add `KdfIterationPicker`, pass chosen iterations to `useCreateJournal`.
7. Update `ChangePasswordModal` — add `KdfIterationPicker`, pass chosen iterations to `handleChangePassword`.
8. Update `useCreateJournal` in `src/hooks/useStorage.ts` to store the user-selected `kdfIterations` on the journal.
9. Update `handleChangePassword` in `JournalSettings.tsx` to store the new `kdfIterations` value.
10. All call sites that derive keys must pass `journal.kdfIterations ?? 20_000`.
11. Add i18n keys for the presets and the "Key strength" label (all 8 languages in `src/i18n/dictionaries.ts`).

### Files

## 2. Device key rotation (Critical)

**Current:** Device key generated once, never rotated.
**Target:** Allow manual key rotation via global security settings; re-encrypt all data with new device key.

### Design

- Add a `rotateDeviceKey()` method to `EncryptionService` that:
  1. Generates a new 256-bit device key
  2. Lists all journals from the index
  3. For each journal: reads all files with old key, re-encrypts with new key, writes back
  4. Updates the index (re-encrypted with new key)
  5. Stores new key in SecureStore, overwrites old
  6. Updates cached key

- This is a destructive batch operation — must be atomic-safe (see issue #8 approach).

### Files

- `src/lib/encryption/device.ts` — add `rotateKey()` that generates new key, returns old + new
- `src/lib/encryption/index.ts` — add `rotateDeviceKey()` to `EncryptionService`
- `src/lib/storage/local.ts` — add `reencryptAll(oldKey, newKey)` method to `LocalStore`
- `src/components/home/SecuritySettingsModal.tsx` — "Rotate device key" button with confirmation dialog and progress indicator

### Risk mitigation

- Show a progress indicator and warning ("Do not close the app")
- Write each re-encrypted file to a `.tmp` suffix first, then rename (atomic swap per file)
- If the process crashes mid-way, on next launch detect `.tmp` files and roll forward or back

## 3. Persistent rate limiter (High)

**Current:** In-memory counter resets on app restart.
**Target:** Persist attempt count and lockout timestamp to `AsyncStorage`.

### Design

- Use `@react-native-async-storage/async-storage` (already a dependency) to store:
  ```json
  { "attempts": 3, "lockedUntil": 1741872000000 }
  ```
  Key: `canto_unlock_rate_limit`
- On `attempt()`: read from storage, check lockout, increment, write back
- On `reset()`: clear storage entry
- Make the limiter async (current callers already in async contexts)
- Add escalating lockout: 30s after 5 attempts, 5min after 10, 30min after 15

### Files

- `src/lib/encryption/ratelimit.ts` — rewrite to async with AsyncStorage persistence and escalating lockout
- `src/components/home/JournalAccessModal.tsx` — update to handle async `attempt()` calls

## 4. Session timeout / auto-lock (High)

**Current:** Derived keys cleared only on home screen focus.
**Target:** Auto-clear keys after configurable inactivity period (default 5 minutes). Timeout duration configurable in the global security settings modal.

### Timeout options

| Label      | Value     |
| ---------- | --------- |
| 1 minute   | `60_000`  |
| 5 minutes  | `300_000` |
| 15 minutes | `900_000` |
| Off        | `0`       |

Default: **5 minutes**. Stored in `AsyncStorage` key `canto_auto_lock_timeout`.

### Design

- Track last user interaction timestamp in a ref/context
- Use `AppState` listener to detect background/foreground transitions
- On foreground resume: if elapsed time > timeout threshold, clear all keys and navigate to home
- On inactivity while foregrounded: use a periodic check (e.g., 30s interval) — if last interaction was > threshold ago, clear keys
- Timeout picker in `SecuritySettingsModal` (see global settings section above)

### Files

- `src/contexts/JournalKeyContext.tsx` — add `touchActivity()` method and timeout logic
- `app/_layout.tsx` — add `AppState` listener that calls `clearAll()` + navigates home on timeout
- Touch interaction tracking: wrap navigation or key UI interactions to call `touchActivity()`
- `src/components/home/SecuritySettingsModal.tsx` — timeout picker UI

## 5. Biometric key storage (High)

**Current:** Biometric is a gate before password prompt. Failing biometric still allows password entry.
**Target:** When biometric is enabled, store the derived password key in SecureStore (protected by biometric access control), so biometric actually unlocks the journal without needing the password.

### Design

- When user enables biometric on a secure journal:
  1. Derive key from password (already cached at this point)
  2. Store key in SecureStore with key `canto_bio_key_{journalId}` and `requireAuthentication: true` (expo-secure-store option that requires biometric to read)
- On journal access with biometric enabled:
  1. Attempt to read key from SecureStore (triggers biometric prompt natively)
  2. If successful, use retrieved key — skip password prompt entirely
  3. If biometric fails, fall back to password prompt
- When user disables biometric: delete the SecureStore entry
- When user changes password: update the stored biometric key

### Files

- `src/lib/biometric.ts` — add `storeBiometricKey()`, `getBiometricKey()`, `clearBiometricKey()` using SecureStore with `requireAuthentication: true`
- `app/index.tsx` — update `handleJournalPress` to attempt biometric key retrieval before showing password modal
- `src/components/journal/JournalSettings.tsx` — update biometric toggle to store/clear key; update password change to refresh stored key

### Caveat

`expo-secure-store` `requireAuthentication` option availability varies by platform. Must check support and fall back to gate-only behavior on unsupported devices.

## 7. Index integrity verification (Medium)

**Current:** GCM auth tag protects individual files but there's no cross-file integrity check.
**Target:** Handle decryption/integrity failures gracefully without crashing or exposing state.

### Design

- Wrap all `readEncrypted` calls in try/catch
- If decryption fails (tampered data, wrong key, corrupted file): return `null` and log a warning
- In `readIndex()`: if decryption fails, treat as empty index (fresh start) and warn user
- In `getJournal()`: skip corrupted pages instead of crashing

### Files

- `src/lib/storage/local.ts` — add try/catch around `readEncrypted` calls with graceful fallbacks
- Consider: add a `console.warn` or user-visible alert when corruption is detected

## 8. Atomic password re-encryption (Medium)

**Current:** Pages re-encrypted sequentially in-place. Crash mid-operation = mixed-key state.
**Target:** Write-ahead approach — write re-encrypted data to temp files, then swap atomically.

### Design

1. For each page: encrypt with new key → write to `{pageId}.json.tmp`
2. Encrypt metadata with new key → write to `metadata.json.tmp`
3. Once all `.tmp` files written successfully:
   - Rename each `.tmp` → final name (atomic per-file on most filesystems)
   - Delete any leftover old files
4. On next app launch: if `.tmp` files exist for a journal, detect and complete the swap (crash recovery)

### Files

- `src/lib/storage/local.ts` — add `reencryptJournal(journalId, oldKey, newKey)` with temp-file approach
- `src/components/journal/JournalSettings.tsx` — use the new atomic method in `handleChangePassword`
- Add recovery logic in `LocalStore.initialize()` to detect and resolve incomplete re-encryptions
