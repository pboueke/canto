# Plan: Requirement #3 — Filesystem & Data Layer

## Objective

Create a filesystem library for Canto that handles local storage, encryption (device-level + application-level), and defines a remote store interface for future sync providers. This layer replaces the current mock data with real persistence.

## Security Design Principles

1. **Authenticated encryption only** — AES-256-GCM (not CBC). GCM provides both confidentiality and integrity, preventing padding oracle and ciphertext tampering attacks.
2. **Strong key derivation** — PBKDF2 with 600,000 iterations (OWASP 2023 minimum). The reference app's 10,000 iterations is dangerously low.
3. **Unique IV/nonce per encryption** — 12-byte random nonce for every GCM encryption. Nonce reuse completely breaks GCM security. Nonces are prepended to ciphertext.
4. **CSPRNG for all randomness** — All salts, IVs, and keys generated via `expo-crypto`'s `getRandomBytes` (backed by OS CSPRNG).
5. **Audited crypto libraries** — `@noble/ciphers` and `@noble/hashes` (by Paul Miller, audited by Cure53) instead of unmaintained `crypto-js`.
6. **Encrypt before leaving device** — All data is encrypted locally before any remote sync. Remote providers never see plaintext.
7. **Ciphertext format** — All encrypted blobs follow: `[12-byte nonce][ciphertext][16-byte GCM tag]`, base64-encoded for JSON storage.

## Phase 1: Data Models (`src/models/`)

Define TypeScript types/classes that mirror the reference app's data structures, adapted to modern TS conventions.

### Files to create:

- **`src/models/types.ts`** — Core type definitions:
  - `Journal` — id (UUID), title, icon, createdAt, secure (boolean), passwordHash (optional)
  - `JournalSettings` — use24h, previewTags, previewThumbnail, previewIcons, filterBar, sort, showMarkdownPlaceholder, autoLocation, remoteSync
  - `JournalContent` — extends Journal with pages array, settings, version
  - `Page` — id (UUID from date), text (markdown), date, thumbnail?, location?, tags[], files[], images[], comments[], modified (timestamp), deleted (soft-delete boolean)
  - `PagePreview` — lightweight version for list rendering (id, date, preview text, tags, flags for hasImage/hasAttachment/hasLocation)
  - `Comment` — text, date
  - `Attachment` — id, path, name, type ('image' | 'file'), deleted
  - `GeoLocation` — latitude, longitude, altitude?, accuracy?
  - `Filter` — query, properties (tags, hasFile, hasImage, hasComments, hasLocation), dateStart?, dateEnd?

- **`src/models/index.ts`** — Re-exports all types

### Notes:

- Use UUID v5 for deterministic IDs (date-based for pages, title-based for journals) — same pattern as reference app
- `PagePreview` separates list display data from full page content, avoiding loading all markdown/attachments for lists
- `deleted` field on Page enables sync conflict resolution (soft delete)
- `modified` timestamp enables change detection for sync

## Phase 2: Encryption Layer (`src/lib/encryption/`)

Two tiers of encryption matching the requirement:

### Files to create:

- **`src/lib/encryption/types.ts`** — Interfaces:
  - `EncryptionProvider` — `encrypt(data: string, key: string): Promise<string>`, `decrypt(ciphertext: string, key: string): Promise<string>`
  - `KeyDerivation` — `deriveKey(password: string, salt: string): Promise<string>`

- **`src/lib/encryption/device.ts`** — Device-level encryption:
  - Uses `expo-secure-store` for key storage on mobile (Keychain on iOS, Keystore on Android)
  - Falls back to `AsyncStorage` on web (with a clear warning/flag that web has no hardware-backed encryption)
  - Auto-generates a device encryption key on first launch, stored securely
  - Provides `deviceEncrypt(data)` / `deviceDecrypt(data)` — transparent to callers

- **`src/lib/encryption/password.ts`** — Application-level encryption:
  - PBKDF2 key derivation with **600,000 iterations** (OWASP 2023), SHA-256, password + 16-byte random salt → 256-bit key
  - AES-256-GCM encryption/decryption with **unique 12-byte random nonce per operation**
  - Ciphertext format: `base64([12-byte nonce][ciphertext][16-byte GCM auth tag])`
  - Salt generation via CSPRNG (`expo-crypto.getRandomBytes`)
  - Password verification via PBKDF2 (derive key, attempt decrypt of a known sentinel value) — no separate bcrypt hash needed
  - Provides `passwordEncrypt(data, password, salt)` / `passwordDecrypt(ciphertext, password, salt)`

- **`src/lib/encryption/index.ts`** — Unified API:
  - `createEncryptionService(options)` — factory that composes device + password encryption
  - For a secure journal: data → password encrypt → device encrypt → store
  - For a non-secure journal: data → device encrypt → store

### Dependencies to add:

- `expo-secure-store` — secure key storage on device (Keychain/Keystore backed)
- `expo-crypto` — CSPRNG (`getRandomBytes`) and SHA-256 digest
- `@noble/ciphers` — AES-256-GCM (audited by Cure53, pure JS, no native deps)
- `@noble/hashes` — PBKDF2 + SHA-256 (audited by Cure53, pure JS)

### Notes:

- **DO NOT use `crypto-js`** — it is unmaintained, only supports AES-CBC (no authenticated encryption), and is vulnerable to padding oracle attacks
- `@noble/ciphers` and `@noble/hashes` are audited by Cure53 and widely used in production
- Device encryption is transparent — the user doesn't need to set up anything
- Application-level encryption is opt-in per journal (the `secure` flag)
- Every encryption operation generates a fresh 12-byte nonce via CSPRNG — never reuse nonces

## Phase 3: Local Storage (`src/lib/storage/`)

Filesystem abstraction for reading/writing journal data on the device.

### Files to create:

- **`src/lib/storage/types.ts`** — Storage interfaces:
  - `LocalStore` interface:
    - `listJournals(): Promise<Journal[]>`
    - `getJournal(id: string): Promise<JournalContent | null>`
    - `saveJournal(journal: JournalContent): Promise<void>`
    - `deleteJournal(id: string): Promise<void>`
    - `getPage(journalId: string, pageId: string): Promise<Page | null>`
    - `savePage(journalId: string, page: Page): Promise<void>`
    - `deletePage(journalId: string, pageId: string): Promise<void>`
    - `saveAttachment(journalId: string, pageId: string, file: Attachment, data: ArrayBuffer): Promise<string>` (returns path)
    - `getAttachment(path: string): Promise<ArrayBuffer | null>`
    - `deleteAttachment(path: string): Promise<void>`

- **`src/lib/storage/local.ts`** — Implementation using Expo FileSystem:
  - Uses `expo-file-system` for file I/O
  - Directory structure on device:
    ```
    {documentDirectory}/canto/
    ├── journals.json          # encrypted index of all journals
    ├── {journalId}/
    │   ├── metadata.json      # encrypted journal metadata + settings
    │   ├── pages/
    │   │   ├── {pageId}.json  # encrypted page content
    │   │   └── ...
    │   └── attachments/
    │       ├── img-{pageId}-{hash}.{ext}
    │       ├── fl-{pageId}-{hash}.{ext}
    │       └── ...
    ```
  - All JSON files go through the encryption layer before writing
  - Attachment files are stored as binary, encrypted at rest via device encryption
  - Implements file locking to prevent concurrent writes

- **`src/lib/storage/index.ts`** — Exports `createLocalStore(encryptionService)`

### Dependencies to add:

- `expo-file-system` — file I/O on device
- `uuid` + `@types/uuid` — UUID generation

### Notes:

- The storage key pattern from the reference app (`SHA256(label:id)`) can be used for indexed lookups
- File naming for attachments follows the reference pattern: `{type}-{pageId}-{hash}.{ext}`
- `journals.json` index enables fast listing without reading every journal directory
- Each write to a journal/page also updates the `modified` timestamp

## Phase 4: Remote Store Interface (`src/lib/sync/`)

Define the interface for remote storage providers. Only the interface + types are needed now; actual implementations (Google Drive, FTP, etc.) come later.

### Files to create:

- **`src/lib/sync/types.ts`** — Remote store interface:
  - `RemoteStore` interface:
    - `connect(credentials: unknown): Promise<void>`
    - `disconnect(): Promise<void>`
    - `isConnected(): boolean`
    - `listRemoteJournals(): Promise<RemoteJournalMeta[]>`
    - `uploadJournalMeta(journal: JournalContent): Promise<void>`
    - `downloadJournalMeta(journalId: string): Promise<JournalContent | null>`
    - `uploadPage(journalId: string, page: Page): Promise<void>`
    - `downloadPage(journalId: string, pageId: string): Promise<Page | null>`
    - `deletePage(journalId: string, pageId: string): Promise<void>`
    - `uploadAttachment(journalId: string, path: string, data: ArrayBuffer): Promise<string>`
    - `downloadAttachment(remotePath: string): Promise<ArrayBuffer | null>`
    - `deleteAttachment(remotePath: string): Promise<void>`
  - `RemoteJournalMeta` — id, title, lastModified, salt
  - `SyncResult` — uploaded[], downloaded[], deleted[], conflicts[]
  - `SyncConflict` — journalId, pageId, localModified, remoteModified, resolution?

- **`src/lib/sync/engine.ts`** — Sync engine (orchestrator):
  - `SyncEngine` class:
    - Takes a `LocalStore` and a `RemoteStore`
    - `sync(journalId: string): Promise<SyncResult>` — compares `modified` timestamps, resolves what to upload/download/delete
    - `syncAll(): Promise<SyncResult[]>` — syncs all journals
    - Conflict resolution strategy: last-write-wins by default, with option to flag conflicts
  - This is the bridge between local storage and remote store, fulfilling the requirement that "the interface between this module and the filesystem library is already in place"

- **`src/lib/sync/index.ts`** — Exports types and engine

### Notes:

- No concrete `RemoteStore` implementations yet — those come with future requirements
- The sync engine uses the `modified` and `deleted` fields on `Page` to determine sync actions (same pattern as reference app's GDriveSync)
- Encrypted data flows through: local storage → encryption layer → remote store (data is encrypted before leaving the device)
- The `SyncEngine` is provider-agnostic — it doesn't care if the backend is Google Drive, FTP, S3, etc.

## Phase 5: Integration & Migration

Wire the data layer into the existing app and replace mock data.

### Files to modify:

- **`src/lib/mockData.ts`** — Keep but mark as deprecated; components can gradually migrate to real data
- **`src/hooks/useStorage.ts`** (new) — React hook wrapping `LocalStore`:
  - `useJournals()` — returns journals list + loading state
  - `useJournal(id)` — returns full journal content
  - `usePage(journalId, pageId)` — returns page
  - `useSavePage(journalId)` — returns save function
  - These hooks handle async loading, error states, and re-rendering

### Notes:

- The UI components don't change in this requirement — they continue using the same data shapes
- The hooks provide the same data shape as the current mock data, making migration seamless
- Actual UI migration from mocks to real storage can happen incrementally

## Implementation Order

1. **Models** (types.ts) — no dependencies, pure types
2. **Encryption** — depends on new packages only
3. **Local Storage** — depends on encryption + models
4. **Sync Interface** — depends on models + storage types
5. **Sync Engine** — depends on sync types + storage types
6. **Hooks** — depends on local storage
7. **Tests** — alongside each phase

Phases 1-2 can be done together. Phases 3-5 can be done together after 1-2 are complete. Phase 6 runs in parallel with each phase.
