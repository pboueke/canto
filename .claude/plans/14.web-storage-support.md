# Plan 14: Web Platform Storage Support

## Problem

Running the Expo app on web crashes immediately because:

1. **`expo-file-system`** — `Directory`, `File`, `Paths` classes have no web implementation. `new Directory(Paths.document, ...)` calls `this.validatePath` which doesn't exist on web.
2. **`expo-secure-store`** — web module is a no-op (`export default {}`). `getItemAsync`/`setItemAsync` silently return `undefined` or fail, so the device encryption key can't be stored/retrieved.

These two modules are used by the entire storage + encryption pipeline, which blocks the app at startup.

**All `expo-file-system` import sites** (every one of these will crash on web):

- `src/lib/storage/local.ts` — core storage (Directory, File, Paths)
- `src/components/journal/PageListItem.tsx` — writes temp cache file for thumbnail display (File, Paths)
- `src/lib/thumbnail.ts` — writes temp files + uses expo-image-manipulator (File, Paths)
- `src/lib/backup/export.ts` — backup creation (File, Directory, Paths)
- `src/lib/backup/import.ts` — backup restoration (File)

**What already works on web:**

- `expo-crypto` AES (`AESEncryptionKey`, `aesEncryptAsync`, `aesDecryptAsync`) — full WebCrypto implementation
- `@noble/hashes` PBKDF2 — pure JS
- `@react-native-async-storage/async-storage` — has web support
- Custom base64 utils in `encryption/utils.ts` — pure JS

## Strategy

Use Metro's platform file resolution (`.web.ts` / `.native.ts`) to provide web-specific implementations. The existing `LocalStore` interface in `types.ts` is the clean seam — no changes needed to hooks, sync, or any consumers.

## Detailed Steps

### Step 1: Web device key storage

Rename `device.ts` → `device.native.ts`, create `device.web.ts`.

The web version replaces `expo-secure-store` with `localStorage`:

```
device.web.ts:
- getOrCreateDeviceKey() → reads/writes localStorage key 'canto_device_encryption_key' (hex)
- rotateKey() → same logic, localStorage instead of SecureStore
- createDeviceEncryption() → identical structure, uses web getOrCreateDeviceKey
```

**Security note:** `localStorage` is not as secure as native secure store (no hardware-backed keychain). Any XSS vulnerability would expose the device key. Acceptable because:

- Web is primarily for development/preview
- Device encryption is a convenience layer; password encryption provides real security
- Add a console warning about reduced security on web

**Files:**

- Rename `src/lib/encryption/device.ts` → `src/lib/encryption/device.native.ts`
- Create `src/lib/encryption/device.web.ts`

No changes to `device.native.ts` content — just the rename so Metro resolves it for native.

### Step 2: Web storage implementation

Rename `local.ts` → `local.native.ts`, create `local.web.ts`.

The web version implements `LocalStore` using **IndexedDB**. Chosen over localStorage because:

- localStorage has ~5-10MB limit; IndexedDB is virtually unlimited
- IndexedDB supports binary data natively (for attachments)
- IndexedDB is async (matches existing async `LocalStore` interface)

**IndexedDB schema:**

```
Database: 'canto'
Object stores:
  - 'files' (keyPath: 'path')
    { path: string, data: string }
```

Mirrors the file-system model: each "file" is a key-value pair where the key is the virtual path (e.g., `canto/journals.json`, `canto/{id}/metadata.json`) and the value is the encrypted string content.

**Implementation — mirror native helpers:**

```typescript
// Virtual path helpers (same structure as native, return string paths)
function getBasePath(): string { return 'canto'; }
function getJournalPath(id: string): string { return `canto/${id}`; }
function getMetadataPath(id: string): string { return `canto/${id}/metadata.json`; }
function getPagePath(jid: string, pid: string): string { return `canto/${jid}/pages/${pid}.json`; }
function getIndexPath(): string { return 'canto/journals.json'; }
function getAttachmentPath(jid: string, pid: string, att: Attachment): string { ... }

// IDB helpers
async function idbGet(path: string): Promise<string | null> { ... }
async function idbPut(path: string, data: string): Promise<void> { ... }
async function idbDelete(path: string): Promise<void> { ... }
async function idbDeletePrefix(prefix: string): Promise<void> { ... }
async function idbListPrefix(prefix: string): Promise<string[]> { ... }

// readEncrypted / writeEncrypted — same logic as native, using idbGet/idbPut
```

`createLocalStore(encryption)` has the same signature and returns the same `LocalStore` interface.

**Key differences from native:**

- No crash recovery needed (IndexedDB transactions are atomic)
- No `ensureDir()` needed (flat key-value store)
- `saveAttachment` returns a virtual IDB path (used as a key for `getAttachment` lookups)
- No `.tmp` file dance — IDB puts are atomic
- `getAttachment(path)` uses `path` as an IDB key lookup (not a filesystem read)

**Files:**

- Rename `src/lib/storage/local.ts` → `src/lib/storage/local.native.ts`
- Create `src/lib/storage/local.web.ts`

### Step 3: Verify barrel exports

Current `src/lib/storage/index.ts` imports from `'./local'`. Metro resolves `./local` → `./local.web.ts` on web and `./local.native.ts` on native. No changes needed to `index.ts`.

Same for `src/lib/encryption/index.ts` importing from `'./device'`.

### Step 4: Thumbnail handling on web

**Problem:** Two files use `expo-file-system` for thumbnail operations:

1. `src/lib/thumbnail.ts` — uses `expo-file-system` to write temp files + `expo-image-manipulator` to resize. Both unavailable on web.
2. `src/components/journal/PageListItem.tsx:46-49` — writes decoded attachment data to a cache file via `expo-file-system`, then uses the `file://` URI in `<Image>`.

**Fix for `thumbnail.ts`:**

- Rename → `thumbnail.native.ts`
- Create `thumbnail.web.ts` that uses `<canvas>` to resize, or returns the input unchanged (skip resize on web — acceptable since thumbnails are 80px wide and web has more bandwidth/memory than mobile)

**Fix for `PageListItem.tsx`:**
The thumbnail fallback path (lines 40-55) decodes an attachment, writes it to a cache file, and returns the file URI. On web, skip the temp file and return a `data:image/jpeg;base64,${data}` URI directly.

The primary path (`page.thumbnail` → inline base64) already works on web (line 36: `data:image/jpeg;base64,${page.thumbnail}`). The fallback is only for pages saved before thumbnail generation was added.

**Approach:** Add a Platform check in `PageListItem.tsx` for the fallback path:

```typescript
// Web: use data URI directly (no file system access)
// Native: write to cache file for better memory management
if (Platform.OS === 'web') {
  return `data:image/jpeg;base64,${data}`;
}
const tmpFile = new ExpoFile(Paths.cache, `thumb-${page.id}.jpg`);
...
```

Move the `expo-file-system` import behind a conditional or use a lazy require so it doesn't crash the web bundle at import time.

### Step 5: Backup stubs for web

**Problem:** `backup/export.ts` and `backup/import.ts` import `expo-file-system` at the top level. Even if backup is never called on web, Metro bundles these imports and they crash at module evaluation time.

**Fix:**

- Rename `src/lib/backup/export.ts` → `export.native.ts`
- Rename `src/lib/backup/import.ts` → `import.native.ts`
- Create `export.web.ts` and `import.web.ts` as stubs that export the same interface but throw `'Backup is not supported on web'`

This keeps backup out of scope while preventing build failures.

**Files:**

- Rename `src/lib/backup/export.ts` → `export.native.ts`
- Create `src/lib/backup/export.web.ts` (stub)
- Rename `src/lib/backup/import.ts` → `import.native.ts`
- Create `src/lib/backup/import.web.ts` (stub)

Check `src/lib/backup/index.ts` (or wherever these are re-exported) — same Metro resolution logic applies, no barrel changes needed.

### Step 6: Verify expo-crypto AES works on web

The `utils.ts` imports from `expo-crypto`:

```typescript
import { aesEncryptAsync, aesDecryptAsync, AESEncryptionKey, AESSealedData } from 'expo-crypto';
```

`expo-crypto` has a full `.web.js` AES implementation using `crypto.subtle`. Verify this resolves correctly on web. If not, create `utils.web.ts` using `crypto.subtle` directly.

### Step 7: Verify Jest mocks still work

Current `jest.config.js` maps `expo-file-system/next` to a mock. After renaming `local.ts` → `local.native.ts`, Jest (running in Node) should resolve to `.native.ts` by default — but Jest's module resolution isn't identical to Metro's. Verify:

- `createLocalStore` import still resolves in tests
- `createDeviceEncryption` import still resolves in tests
- Existing test suite passes without changes

Run `npx expo start --web` and verify:

3. Pages can be created, edited, saved
4. Attachments can be added and displayed

## Risks & Mitigations

1. **IndexedDB availability** — Available in all modern browsers. Safari private browsing had issues historically but is fine now (Safari 15.4+).

2. **Storage limits** — IndexedDB has generous limits (typically 50%+ of disk). Far more than enough for a journaling app.

3. **Device key in localStorage — XSS risk** — Any XSS vulnerability exposes the device encryption key. Mitigated by: web is secondary platform, password encryption provides real security, console warning added. Could consider IndexedDB for the device key too (slightly harder to exfiltrate than localStorage).

4. **Attachment display** — Native uses `file://` URIs directly in `<Image>`. On web, the `useImageQueue` hook calls `getAttachment(path)` which returns base64 data — the `loadImage` callback in `ImageCarousel` already goes through this path, so loaded images are data URIs. Verify this works end-to-end.

5. **Jest module resolution** — Jest resolves differently from Metro. After `.native.ts`/`.web.ts` splits, verify Jest still picks up the right files. May need `moduleNameMapper` updates.

6. **expo-crypto AES on web** — Has a `.web.js` implementation but untested in this project. If it fails, implement `utils.web.ts` using `crypto.subtle` directly.

7. **`PageListItem` conditional import** — The `expo-file-system` import in `PageListItem.tsx` is top-level. On web, Metro will try to resolve it. Options: (a) move the import behind a dynamic `require()` inside the Platform check, (b) extract the native thumbnail cache logic into a small helper with `.native.ts`/`.web.ts` split. Option (b) is cleaner.

## Out of Scope

- Sync on web (depends on network layer, separate concern)
- Backup/export on web (stubs provided to prevent build failures)
- Biometric auth on web (no equivalent)
- Offline PWA support (future enhancement)
