# Plan 11.3: Remote Store Implementation Drift

## Problem

The sync implementation has drifted from the original multi-provider design:

1. `SyncManager` hardcodes `GDriveRemoteStore` directly instead of accepting any `RemoteStore`
2. `SyncEngine` has GDrive-specific path checks (`gdrive://`) baked into sync logic
3. `SyncManagerContext` and `GoogleAuthContext` are tightly coupled — no abstraction for other providers
4. `AccountButton` lives inside `InfoBox` (settings area) instead of the home page footer
5. No provider selection UI — connecting immediately assumes Google
6. Missing test coverage for the generic sync interface and GDrive end-to-end flow

---

## Phase 1: Abstract the Sync Provider Layer

### 1.1 Extend `RemoteStore` interface (`src/lib/sync/types.ts`)

Add a provider identifier method so consumers can determine which provider is active:

```typescript
export type SyncProvider = 'gdrive'; // extend as providers are added

export interface RemoteStore {
  readonly provider: SyncProvider;
  // ... existing methods unchanged
}
```

### 1.2 Remove GDrive-specific logic from `SyncEngine` (`src/lib/sync/engine.ts`)

- Replace the hardcoded `gdrive://` prefix check in `uploadPageAttachments` with a generic remote path detection. Add a method to `RemoteStore`:
  ```typescript
  isRemotePath(path: string): boolean;
  ```
- Replace the hardcoded `gdrive://${journalId}/attachments/${filename}` path construction in `downloadPageAttachments` with a method on `RemoteStore`:
  ```typescript
  buildRemotePath(journalId: string, filename: string): string;
  ```
- `GDriveRemoteStore` implements these returning `true` for `gdrive://` prefix and constructing `gdrive://...` paths

### 1.3 Make `SyncManager` provider-agnostic (`src/lib/sync/manager.ts`)

- Change constructor to accept a `RemoteStore` instance instead of creating `GDriveRemoteStore` internally:
  ```typescript
  constructor(private local: LocalStore, private store: RemoteStore) {}
  ```
- Change `getRemoteStore()` return type from `GDriveRemoteStore` to `RemoteStore`
- Remove `import { GDriveRemoteStore }` — provider selection moves to context layer

### 1.4 Update `SyncManagerContext` (`src/contexts/SyncManagerContext.tsx`)

- Import `GDriveRemoteStore` here (the composition root) and pass it to `SyncManager`
- The context is where provider selection happens — currently only GDrive, but structured so adding a provider means adding a case here
- Expose `provider: SyncProvider | null` in context value so UI can show which provider is active

### 1.5 Update `JournalSettings.syncProvider` type (`src/models/types.ts`)

- Import and use the `SyncProvider` type: `syncProvider?: SyncProvider`

## Phase 2: Provider Selection UI

### 2.1 Create `SyncProviderModal` (`src/components/home/SyncProviderModal.tsx`)

A modal that appears when the user taps "Connect Account" (before triggering any auth flow):

- Shows a list of available sync providers (currently just Google Drive)
- Each option shows the provider icon and name
- Tapping a provider triggers the corresponding auth flow (Google Sign-In for gdrive)
- Modal closes after successful sign-in or on cancel
- Props: `visible: boolean`, `onClose: () => void`

### 2.2 Update `AccountButton` to use `SyncProviderModal`

- When not signed in: tapping "Connect Account" opens `SyncProviderModal` instead of directly calling `signIn()`
- The modal then handles provider selection → auth flow

## Phase 4: Tests

### 4.1 Generic sync interface tests (`src/lib/__tests__/sync-interface.test.ts`)

Test that `SyncEngine` works correctly with **any** `RemoteStore` implementation (not just GDrive). Use a mock `RemoteStore` that implements the interface:

- `RemoteStore` contract: verify all interface methods are called correctly
- `isRemotePath` / `buildRemotePath` are used instead of hardcoded strings
- Provider-agnostic page sync: upload, download, conflict resolution, deletion propagation
- Attachment sync uses the generic remote path methods

### 4.2 GDrive end-to-end sync test (`src/lib/__tests__/gdrive-sync-e2e.test.ts`)

Full journal sync lifecycle using `GDriveRemoteStore` (with mocked HTTP/fetch):

1. **Setup**: Create a local journal with pages and attachments
2. **First sync**: Verify all pages and attachments are uploaded to GDrive
3. **Remote changes**: Simulate remote page edits (newer timestamps)
4. **Second sync**: Verify remote changes are downloaded locally
5. **Deletion propagation**: Delete a page locally, sync, verify remote deletion
6. **Remote deletion**: Simulate remote page deletion, sync, verify local deletion
7. **Conflict resolution**: Both local and remote modified, verify last-write-wins
8. **Attachment round-trip**: Upload attachment, verify `gdrive://` path, download on another "device" (fresh local store)
9. **Encrypted journal**: Full sync cycle with `derivedKey` passed through

### 4.3 Update existing tests

- `sync.test.ts`: Ensure the mock `RemoteStore` implements `isRemotePath` and `buildRemotePath`
- `sync-manager.test.ts`: Update to reflect constructor change (pass `RemoteStore` as second arg)
- `gdrive-store.test.ts`: Add tests for `isRemotePath` and `buildRemotePath`
