# Plan 20.1 — Journal persistence integrity and recoverable export

**Status:** Proposed
**Primary objective:** Prevent an Android lifecycle or storage-read failure from silently replacing a Canto journal/page index with a reduced view; fail closed with recoverable diagnostics instead. Ensure export distinguishes unreadable journal data from archive/share failures.

## 1. Incident and evidence

A Huawei P30 Lite on Android 10 (API 29) reportedly had about ten journal entries. After editing one entry overnight, only that entry appeared; Export Journal then showed the Spanish generic error `Error al exportar`.

The report can mean either ten pages in one journal or ten separate journals. Both loss shapes are possible in the current native store:

1. **Stale auto-lock key can be reused by an editor.** `JournalKeyProvider.clearAll()` zeros cached `Uint8Array` keys in place (`src/contexts/JournalKeyContext.tsx` and `src/lib/encryption/utils.ts`). `PageScreen` passes the same mutable key to `useSavePage`. After a background/inactivity auto-lock, an already-mounted screen can retain the zeroed buffer and write with it.
2. **A failed catalog rebuild can publish a subset.** `savePage()` and `getJournalOverview()` rebuild an invalid/missing catalog with `skipMalformedPages=true`, then persist the resulting catalog (`src/lib/storage/local.ts`). A page that cannot be decrypted/parsed is omitted, so an edit can publish a catalog containing only the edited page. `isPageCatalogV1()` validates only the catalog against itself, and later reads trust it without reconciling page files.
3. **A failed index read becomes an empty library.** `readIndex()` maps an undecryptable/missing index to `{ journals: [] }`. A later metadata or journal write can persist a one-journal index, hiding other on-disk journal directories.
4. **Critical singleton files are in-place writes.** Index, metadata, and page catalog writes use `File.write()` directly rather than the existing staged transaction protocol. A background kill can leave a partial record which the tolerant readers subsequently collapse into an empty/subset view.
5. **Export hides the useful failure.** `ExportJournalModal` maps every load, ZIP, cache, and share-sheet error to `backup.exportError`. Export uses the strict full-page reader while the overview uses the tolerant catalog reader, so a journal can show a reduced page list and fail export from the same underlying integrity defect.

The first four findings are source-demonstrated failure mechanisms. Which trigger occurred on the reporter's device remains unproven until its logcat and app-private storage state are preserved.

## 2. Product and safety contract

1. Page files and journal directories are authoritative user data. `page-catalog.json` and `journals.json` are indexes/projections only; neither may be treated as proof that absent records were deleted.
2. A malformed, undecryptable, incomplete, or ambiguous index/catalog must **block destructive publication**. The app must show a recoverable integrity state; it must not replace the file with an empty or reduced projection.
3. A storage write must never proceed with an auto-locked, revoked, or invalid derived key. An auto-lock must make the editor non-writable until it is unlocked again.
4. Every write that publishes index, metadata, or catalog state must use one crash-recoverable transaction and a single local mutation queue. A recovery pass must complete or roll back before the app exposes data.
5. Export must be read-only with respect to journal data. Its UI must distinguish: unreadable journal data, archive construction/space failure, and Android sharing failure. User-facing errors must remain localized and not leak keys, file paths, or plaintext.
6. Fresh install is the sole state in which a missing device key or missing index means “empty library.” Existing encrypted storage with a missing/invalid key is an integrity/recovery condition, never a new-library signal.
7. The Android solution must work on API 29 and be tested on a Huawei/EMUI-class physical device. Scoped external-storage permissions must not become a prerequisite for reading journal data.

## 3. Scope

### In scope

- `src/contexts/JournalKeyContext.tsx`, editor routes, and storage hooks: key-lifecycle-safe editing.
- `src/lib/storage/local.ts`, `local.web.ts`, storage types, and write barrier: fail-closed reads, transactional singleton writes, catalog/index integrity, and serialized mutation.
- `src/lib/encryption/device.ts` and store initialization: distinguish fresh install from lost device-key access.
- `src/components/journal/ExportJournalModal.tsx`, `src/lib/backup/export.ts`, i18n, and Android export/share integration: diagnostic export outcomes and API-29 validation.
- Native/Web storage, key-context, backup/export, and Android integration/device tests.
- A minimal recovery-state UI that preserves data and gives the user safe next actions.

### Out of scope

- Silent data repair by deleting pages, journals, or catalog/index files.
- Automatic recreation of a missing device key where Canto data already exists.
- Changing Canto's backup format, adding cloud sync, or adding a new external-storage permission for journal persistence.
- Claiming that existing encrypted files are decryptable after the device key has genuinely been destroyed; the product must preserve and report that condition, not fabricate recovery.
- Broad attachment-performance work except where needed to classify/export an integrity error.

## 4. Design

### 4.1 Make auto-lock an explicit write capability boundary

1. Replace mutable-key-only handoff with a key lease/token owned by `JournalKeyContext`. It must carry a monotonically increasing epoch (or equivalent revocation identity), not merely a `Uint8Array` reference.
2. On `clearKey`/`clearAll`, revoke active leases before zeroing key material and notify mounted journal/page screens through React state.
3. Page save/delete/create and attachment mutations must re-check the lease immediately before storage mutation, including after awaited thumbnail or attachment work. A revoked lease rejects with a typed `JOURNAL_LOCKED` outcome; it must never call encryption with the zeroed bytes.
4. The editor must return to its access/locked state and retain the unsaved draft in memory only until the user explicitly unlocks or discards it. It must show a localized “unlock before saving” message rather than an unhandled promise rejection.
5. Add a defense-in-depth storage assertion that rejects an all-zero 32-byte derived key on any password-layer write. This is not the primary authorization mechanism; the lease check is.

### 4.2 Treat index and catalog reads as three states, not nullable strings

Introduce internal result types such as:

```ts
type IndexedRead<T> =
  | { state: 'absent' } // expected only for a genuinely new root
  | { state: 'valid'; value: T }
  | { state: 'unreadable'; cause: StorageIntegrityCause };
```

1. `readIndex`/`readPageCatalog` must distinguish a file that does not exist from a file that exists but fails device decryption, password decryption, JSON parsing, validation, or consistency checks.
2. `listJournals` and overview loading must surface `unreadable` to the hook/UI; they must not substitute `[]`, `null`, or a rebuilt empty catalog.
3. Mutators (`saveJournal`, `saveJournalMetadata`, `deleteJournal`, `savePage`, `deletePage`, import recovery) must refuse to publish when their required baseline index/catalog is unreadable.
4. A catalog rebuild may publish only after it reads and validates every discovered page successfully. It must return an explicit incomplete/recovery-required result if any file cannot be decrypted, parsed, or validated.
5. For an existing journal whose catalog is missing/corrupt, do not silently publish an empty/subset replacement. Provide a read-only recovery diagnostic listing counts and opaque record identifiers; publication requires a complete scan. Preserve raw files unchanged on failure.
6. Keep `getJournal()` strict. Make all skip/omission behavior explicit and reportable; never use it as an implicit repair path.

### 4.3 Make native and Web singleton publication crash-recoverable and serialized

1. Extend the existing transaction staging protocol to cover every publication of `journals.json`, `metadata.json`, and `page-catalog.json`, not only full-journal/page commits.
2. A transaction must stage all new ciphertext, persist a commit marker, apply targets, and remain replayable until cleanup. Startup must recover this transaction before any list/read/mutation is exposed.
3. Add one mutation queue/mutex around all LocalStore mutators. The current device-key barrier protects key rotation but permits concurrent writers; it must be composed with, or replaced by, a serialization primitive that prevents last-writer-wins index/catalog snapshots.
4. Preserve crash semantics: prepared-but-uncommitted work rolls back; committed work rolls forward; recovery must never infer intent from a partial target file.
5. Retain the current page-and-catalog atomic operation, but make its target writes subject to the same durable transaction contract and add fault-injection coverage for every phase.

### 4.4 Fail closed when the device key is unavailable

1. Split `getOrCreateDeviceKey` into a non-mutating lookup and an explicit first-install creation path.
2. During initialization, inspect only keyless storage presence markers/root state. If durable Canto content exists but SecureStore cannot supply the device key, enter `DEVICE_KEY_UNAVAILABLE`; do not mint a replacement key and do not write index/catalog data.
3. Create a durable first-install marker atomically with initial device-key setup so an interrupted empty installation can be distinguished from a populated library.
4. Render a localized recovery state on Home rather than “No journals.” It must advise the user not to create/edit journals, offer log/support evidence, and explain that the current device key is required to decrypt local data.
5. Audit Android backup rules deliberately. Document that local encrypted files without the corresponding device key are not a restorable backup; do not present Android Auto Backup as user recovery.

### 4.5 Export diagnostics and Android sharing

1. Define typed export failures: `JOURNAL_UNREADABLE`, `JOURNAL_PAGE_INVALID`, `ATTACHMENT_UNREADABLE`, `ARCHIVE_WRITE_FAILED`, `INSUFFICIENT_SPACE`, and `SHARE_FAILED`.
2. `ExportJournalModal` must map those to distinct localized, actionable messages and log only a redacted error code/context. The generic Spanish `Error al exportar` may remain as the final fallback only.
3. Add an explicit preflight for cache free space and bounded archive size/memory. Keep archive generation read-only.
4. Evaluate the installed `expo-sharing` version's sticky `pendingPromise` behavior. Upgrade if the upstream fix exists; otherwise isolate/patch the Android share bridge so a failed or interrupted chooser cannot poison later export attempts in the same process.
5. Add an integrity-preserving support export only if it can be made read-only: a clearly labeled encrypted forensic package of existing app records, not a purportedly restorable plaintext journal. It must be offered only from the integrity state and never delete/normalize source data.

## 5. Implementation sequence

1. **Characterize before refactoring.** Add deterministic regression tests for stale auto-lock/editor save, malformed page/catalog rebuild, unreadable index followed by metadata write, concurrent writers, and transaction recovery. Each must fail on the current behavior.
2. **Key lease and editor lock.** Implement revocable key leases/context notification, guard every journal mutation, and update editor lock/error UX.
3. **Typed storage reads.** Refactor native and Web index/catalog readers and callers to preserve absent versus unreadable semantics. Add the recovery-state plumbing before changing write behavior.
4. **Safe catalog policy.** Remove tolerant rebuild publication. Implement complete-scan validation, non-destructive failure, and read-only diagnostic reporting.
5. **Transactional singleton writes and queue.** Route all singleton writes through durable transactions and serialize mutations. Add deterministic fault injection around marker/stage/apply/recovery.
6. **Device-key bootstrap gate.** Implement populated-root/key-unavailable detection and the first-install marker. Verify no later initializer/mutator can overwrite the evidence.
7. **Export classification.** Add typed errors, localized UI, cache/memory checks, and the Android sharing dependency fix/patch.
8. **Recovery UX and documentation.** Add concise support instructions, update backup wording, and document data-preservation handling for support staff.
9. **Release verification.** Run automated gates, API-29 emulator coverage, and a physical Huawei/EMUI validation before release.

## 6. Test and verification matrix

### Automated regression tests

- **Auto-lock:** open a secure journal/page; capture a key; trigger foreground/background or inactivity auto-lock; attempt save. Assert no storage file changes, no all-zero key reaches encryption, and the UI requires unlock.
- **Catalog integrity:** create three pages; remove/corrupt a catalog and make one unrelated page unreadable. Saving another page must reject/enter recovery and must leave the previous catalog/page files unchanged. It must never publish a one-page catalog.
- **Index integrity:** make an existing `journals.json` undecryptable; attempt metadata update/new journal/import recovery. Assert all writes are rejected and no reduced index is written.
- **Transaction fault injection:** kill/fail after each stage/marker/apply operation for index, metadata, catalog, page, and journal commits. On restart, assert either the complete old state or the complete new state—never a subset.
- **Concurrent mutation:** interleave save/delete/overview rebuild operations and assert index/catalog contain every committed mutation exactly once.
- **Device-key loss:** simulate SecureStore returning null while populated storage exists. Assert no replacement key, no empty Home screen, no index rewrite, and a recovery state.
- **Export:** malformed/unreadable journal data, missing attachment chunks, no cache space, archive failure, and native share rejection each render their distinct localized error. Assert export never changes journal files.
- **Web parity:** run the same integrity contracts against `local.web.ts`.

### Android verification

1. Install a debug build on an API-29 emulator and Huawei P30 Lite/EMUI 10 (or equivalent low-memory API-29 device).
2. Create a multi-page and multi-journal fixture. Background the app beyond auto-lock, resume, and attempt an edit; verify the editor locks rather than saving with a revoked key.
3. Force-stop at each fault-injection checkpoint and relaunch; verify the library is complete or a recovery state is shown, never an apparently empty/reduced library.
4. Verify export of a healthy journal opens the Android chooser and produces an archive; interrupt the chooser, retry in the same process, and verify the retry remains usable.
5. For an intentionally unreadable fixture, verify the exact localized diagnostic and that source file counts/bytes are unchanged after attempted export.
6. Capture `ReactNativeJS`, `ExpoSecureStore`, and sharing logcat output; confirm production diagnostics contain no plaintext, passwords, key material, or full app-private paths.

## 7. Acceptance criteria

- An Android auto-lock cannot allow an already-mounted editor to write with a revoked/zeroed key.
- No malformed, undecryptable, missing, or partial index/catalog can silently turn a non-empty library or journal into an empty/subset UI view.
- Existing journal/page files are preserved when recovery cannot prove a complete projection.
- Every index, metadata, and catalog publication is serialized and crash-recoverable.
- A missing device key plus existing data is reported as an integrity/recovery condition, never treated as a fresh install.
- Export reports whether the failure is journal integrity, archive/storage capacity, or Android sharing; it remains read-only.
- Native and Web regression tests, typecheck, lint, format check, API-29 emulator tests, and Huawei/EMUI physical validation pass.
