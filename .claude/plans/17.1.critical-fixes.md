# Plan: Requirement 17.1 — Critical Bug Fixes

## Context

Canto is at v0.17.0. A codebase audit (`.claude/notes/2026-03-20-6.md`) identified 5 CRITICAL data-corruption issues that can occur in normal usage. All involve race conditions, silent failures, or invalid data passing validation. This plan fixes all 5 with corresponding tests.

## Scope Summary

| #   | Issue                                                 | File(s)                                         | Fix                                                         |
| --- | ----------------------------------------------------- | ----------------------------------------------- | ----------------------------------------------------------- |
| 1   | Race condition in store initialization                | `src/hooks/useStorage.ts`                       | Promise-based initialization guard                          |
| 2   | Race condition in device key creation                 | `src/lib/encryption/device.ts`, `device.web.ts` | Promise-based creation guard + cached key check             |
| 3   | Silent page download failures during sync             | `src/lib/sync/gdrive/store.ts`                  | Collect failures, throw with details if any pages failed    |
| 4   | No error handling around saveAttachment during import | `src/lib/backup/import.ts`, `import.web.ts`     | try-catch each attachment, collect errors, report to caller |
| 5   | checkNumber accepts NaN/Infinity                      | `packages/canto-data/src/validation.ts`         | Add `Number.isFinite()` check                               |

## Implementation Plan

### Phase 1: Validation Fix (Issue #5)

**File:** `packages/canto-data/src/validation.ts`

The simplest and most isolated fix. `checkNumber()` currently only does `checkType(path, value, 'number')`, which accepts `NaN` and `Infinity` since `typeof NaN === 'number'`.

**Change:** Add `Number.isFinite()` guard after the type check:

```typescript
function checkNumber(path: string, value: unknown): void {
  checkType(path, value, 'number');
  if (!Number.isFinite(value as number)) {
    throw new ValidationError(path, 'finite number', String(value));
  }
}
```

**Test:** `packages/canto-data/src/__tests__/validation.test.ts` — add cases for `NaN`, `Infinity`, `-Infinity` in numeric fields (e.g., `modified`, geo coordinates).

### Phase 2: Race Condition — Store Initialization (Issue #1)

**File:** `src/hooks/useStorage.ts`

**Problem:** `ensureInitialized()` checks a boolean `initialized` flag, but concurrent callers can all enter the `if (!initialized)` block before `await store.initialize()` completes.

**Fix:** Replace the boolean flag with a stored Promise:

```typescript
let initPromise: Promise<LocalStore> | null = null;

async function ensureInitialized(): Promise<LocalStore> {
  const store = getStore();
  if (!initPromise) {
    initPromise = store.initialize().then(() => store);
  }
  return initPromise;
}
```

This ensures the first caller creates the promise, and all concurrent callers await the same promise. If initialization fails, we should reset `initPromise` to `null` so it can be retried:

```typescript
if (!initPromise) {
  initPromise = store
    .initialize()
    .then(() => store)
    .catch((err) => {
      initPromise = null;
      throw err;
    });
}
```

**Test:** `src/hooks/__tests__/useStorage.test.ts` — test that calling `ensureInitialized()` concurrently (e.g., 5 times with `Promise.all`) only triggers one `store.initialize()` call.

### Phase 3: Race Condition — Device Key Creation (Issue #2)

**Files:** `src/lib/encryption/device.ts`, `src/lib/encryption/device.web.ts`

**Problem:** `getOrCreateDeviceKey()` has a TOCTOU race — check-then-create without locking. Concurrent calls during app startup can each generate a different key.

**Fix (both files):** Use a Promise guard similar to Phase 2:

```typescript
let keyCreationPromise: Promise<Uint8Array> | null = null;

async function getOrCreateDeviceKey(): Promise<Uint8Array> {
  if (!keyCreationPromise) {
    keyCreationPromise = (async () => {
      // ... existing check-and-create logic ...
    })().catch((err) => {
      keyCreationPromise = null;
      throw err;
    });
  }
  return keyCreationPromise;
}
```

The `createDeviceEncryption()` function already caches in `cachedKey`, but the underlying creation must also be guarded since the cache is per-provider-instance.

**Test:** `src/lib/encryption/__tests__/device.test.ts` — test concurrent `getOrCreateDeviceKey()` calls via `Promise.all` produce the same key and only one SecureStore write occurs. Similar test for `device.web.ts` with localStorage.

### Phase 4: Data Integrity Warning Modal (shared component)

**New file:** `src/components/common/DataIntegrityWarningModal.tsx`

A reusable modal for data integrity issues. Used by both sync (Phase 5) and import (Phase 6). Follows the existing modal pattern (see `ThemePickerModal.tsx`, `SyncModal.tsx`): `Modal` + overlay + themed content.

**Props:**

```typescript
interface DataIntegrityWarningProps {
  visible: boolean;
  onClose: () => void;
  title: string; // e.g., "Sync Warning" or "Import Warning"
  description: string; // explains what went wrong
  details: string[]; // list of failed items (page names, attachment names)
  suggestion: string; // recommended action
  actions: Array<{
    label: string;
    onPress: () => void;
    variant: 'primary' | 'secondary' | 'destructive';
  }>;
}
```

**UI layout:**

- Warning icon (caution triangle character) + title
- Description text explaining the problem
- Scrollable list of failed items (max height ~200px)
- Suggestion text in a highlighted box
- Action buttons (e.g., "Retry" / "Keep Partial" / "Cancel")

**i18n:** Add a new `dataIntegrity` section to the dictionary:

```typescript
dataIntegrity: {
  syncWarningTitle: string;
  syncWarningDescription: string;
  syncRetrySuggestion: string;
  syncKeepPartial: string;
  importWarningTitle: string;
  importWarningDescription: string;
  importSuggestion: string;
  failedItems: string;
  retry: string;
  acknowledge: string;
}
```

**Test:** `src/components/common/__tests__/DataIntegrityWarningModal.test.tsx` — renders with props, displays details list, fires action callbacks.

### Phase 5: Sync Download Failures — Ask User (Issue #3)

**Files:**

- `src/lib/sync/gdrive/store.ts` — collect failures, return partial result with failure metadata
- `src/lib/sync/engine.ts` — detect partial result, surface to caller
- `src/contexts/SyncManagerContext.tsx` — expose failure state
- `src/components/home/NewJournalModal.tsx` — show `DataIntegrityWarningModal` for cloud import

**Problem:** `Promise.allSettled()` silently drops failed page downloads. User gets incomplete data.

**Fix — store.ts:** Return both successful pages and failure details instead of throwing:

```typescript
interface DownloadResult {
  content: JournalContent;
  failures?: Array<{ name: string; reason: string }>;
}

const results = await Promise.allSettled(
  pageFiles.map(async (pf) => {
    const pageContent = await api.getFileContent(token, pf.id);
    return safeJsonParse<Page>(pageContent, `page:${pf.name}`);
  }),
);

const pages: Page[] = [];
const failures: Array<{ name: string; reason: string }> = [];
for (let i = 0; i < results.length; i++) {
  const r = results[i];
  if (r.status === 'fulfilled') {
    pages.push(r.value);
  } else {
    failures.push({
      name: pageFiles[i].name,
      reason: r.reason instanceof Error ? r.reason.message : String(r.reason),
    });
  }
}

return {
  content: { ...meta, pages } as JournalContent,
  failures: failures.length > 0 ? failures : undefined,
};
```

**Fix — engine.ts / SyncManagerContext:** Propagate `failures` up. If failures exist during sync, pause sync and surface the failure state so the UI can show the modal.

**Fix — NewJournalModal.tsx (cloud import path):** When `handleCloudJournalSelect()` gets a result with failures, show `DataIntegrityWarningModal` with:

- Description: "X of Y pages could not be downloaded"
- Details: list of failed page names
- Suggestion: "Check your internet connection and try again. You can also keep the partial import and re-sync later."
- Actions: **"Retry"** (re-attempts download) | **"Keep Partial"** (proceeds with successful pages) | **"Cancel"** (aborts import)

**Fix — SyncManagerContext (background sync path):** When regular background sync encounters failures, store them in sync state. The existing sync status UI can show a warning indicator. Tapping it opens `DataIntegrityWarningModal` with:

- Actions: **"Retry Sync"** | **"Acknowledge"** (dismisses, sync will retry next cycle)

**Test:** `src/lib/sync/gdrive/__tests__/store.test.ts` — mock `api.getFileContent` to reject for one page; assert result contains both successful pages and failure details.

### Phase 6: Import Attachment Error Handling (Issue #4)

**Files:** `src/lib/backup/import.ts`, `import.web.ts`, `src/components/home/NewJournalModal.tsx`

**Problem:** If `saveAttachment()` throws, the entire import aborts with no cleanup.

**Fix — import.ts / import.web.ts:** Wrap each `saveAttachment()` in try-catch. Collect failures. Complete the import with successful attachments:

```typescript
const attachmentErrors: Array<{ name: string; pageId: string; error: string }> = [];

for (const owner of owners) {
  try {
    const savedPath = await store.saveAttachment(/* ... */);
    pageAttachmentPaths.set(`${owner.pageId}:${zipFilename}`, savedPath);
  } catch (err) {
    attachmentErrors.push({
      name: owner.name ?? zipFilename,
      pageId: owner.pageId,
      error: err instanceof Error ? err.message : String(err),
    });
    pageAttachmentPaths.set(`${owner.pageId}:${zipFilename}`, '');
  }
}
```

Extend `ImportResult`:

```typescript
interface ImportResult {
  journalId: string;
  attachmentErrors?: Array<{ name: string; pageId: string; error: string }>;
}
```

**Fix — NewJournalModal.tsx:** After `finishImport()`, if `result.attachmentErrors` is non-empty, show `DataIntegrityWarningModal`:

- Description: "X attachment(s) could not be saved during import"
- Details: list of failed attachment names
- Suggestion: "The journal was imported but some attachments are missing. Try importing again from the same backup file to recover them."
- Actions: **"OK"** (acknowledges, journal is already imported)

**Test:** `src/lib/backup/__tests__/import.test.ts` — mock `saveAttachment` to throw for one attachment; assert import completes, returns the error list, and other attachments are saved correctly.

## Testing Strategy

Each phase includes unit tests as described. All tests use Jest mocks for IO (SecureStore, localStorage, GDrive API, filesystem). No integration tests needed — these are isolated logic fixes.

Run: `npx jest --testPathPattern="(useStorage|device|gdrive/store|import|validation|DataIntegrityWarning)" --no-coverage`

## Risk Assessment

- **Phase 1 (validation):** Low risk — stricter validation may reject previously-accepted data. Ensure no existing test data uses NaN/Infinity
- **Phase 2-3 (race conditions):** Low risk — adding promise guards is additive, doesn't change success-path behavior
- **Phase 4 (modal):** Low risk — new component, no existing code modified
- **Phase 5 (sync failures):** Medium risk — changes return type of download function; callers must handle the new `failures` field. Both cloud import and background sync paths must be updated
- **Phase 6 (import errors):** Medium risk — changes `ImportResult` type; `NewJournalModal` must handle `attachmentErrors`
