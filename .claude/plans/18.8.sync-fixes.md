## Issue 1: NewJournalModal too wide on web

### Root Cause

`NewJournalModal` uses `animationType="slide"` with `flex: 1` container and no width constraint. Other modals either use `webModalContent` (from `src/styles/web.ts`, sets `maxWidth: 1000`) for floating modals or have explicit `maxWidth` values. The NewJournalModal, being full-screen on mobile, needs web-specific width limiting.

### Fix

Add `maxWidth` and `alignSelf: 'center'` to the container style on web, matching the pattern used by the app's full-screen layout (similar to how the page editor constrains content width on web). Use the existing `webModalContent` value (1000px) or a smaller value (~600px) since the form content is narrow.

### Files

- `src/components/home/NewJournalModal.tsx` — add `Platform.OS === 'web'` width constraint to `styles.container` or apply inline style

### Tests

- No automated test needed — this is a visual/layout fix. Manual verification on web.

## Issue 2: Can't import synced journals after password change

### Root Cause

When a user changes their journal password in `JournalSettings.tsx`:

1. **New salt is generated** (`encryption.generateSalt()`) → new `syncKey = PBKDF2(newPwd, newSalt)` (line 186-189)
2. **Local data is re-encrypted** via `store.reencryptJournal()` — writes pages to disk with new key but **does NOT update `page.modified` timestamps** (local.ts line 411: `atomicWrite(pageFile, JSON.stringify(page), ...)`)
3. **GDrive registry is updated** with new salt/kdfIterations on next sync (engine.ts line 117-122)
4. **But pages on GDrive are NOT re-uploaded** — the engine compares `localPage.modified === remoteEntry.modified` (engine.ts line 175), finds them equal, and **skips** re-upload

Result: GDrive registry says "use new salt" but pages are still encrypted with the **old** key. Any subsequent cloud import derives from new salt → can't decrypt old-key pages.

### Fix (TDD approach)

**Step 1: Write failing e2e test** in `src/lib/__tests__/gdrive-sync-encryption.test.ts`:

- Sync a password-protected journal
- Simulate password change: generate new salt, derive new key, update journal metadata in local store
- Sync again with the new key
- Verify all pages on GDrive are re-encrypted with the new key (i.e., decryptable with new key only)
- Verify a cloud import with the new password succeeds

**Step 2: Fix the sync engine** — when the sync key changes, all pages must be re-uploaded. Two possible approaches:

**Option A (recommended): Detect key change via registry salt mismatch.** Before comparing page timestamps, check if the local journal's salt differs from the remote registry's salt. If so, force re-upload all pages.

- `engine.ts` — add a `registrySalt` parameter or have the engine fetch the current registry to compare salts
- When salt mismatch detected: treat all pages as "local newer" → re-encrypt and re-upload with new key
- Update sync index after re-upload

**Option B: Touch timestamps during re-encryption.** Have `reencryptJournal()` bump `page.modified` to `Date.now()`. This is simpler but has the side effect of making all pages appear "recently modified" to the user.

Option A is preferred because it keeps page timestamps accurate and only affects the sync layer.

### Files

- `src/lib/__tests__/gdrive-sync-encryption.test.ts` — new test cases for password change + sync
- `src/lib/sync/engine.ts` — detect salt change and force re-upload
- `src/lib/sync/types.ts` — if needed, add `getRegistryInfo()` to `RemoteStore` or pass current registry salt to `sync()`
- `src/lib/sync/gdrive/store.ts` — if needed, implement registry read for salt comparison

### Tests

- E2E: sync after password change → all pages re-encrypted with new key
- E2E: cloud import after password change → succeeds with new password
- E2E: sync after password removal → all pages re-encrypted with empty-password key

## Issue 3: Web can't import password-protected journals from GDrive

### Root Cause (investigation needed)

The cloud import flow in `NewJournalModal.tsx:executeCloudImport` is platform-agnostic — it uses `deriveKey` (from `@noble/hashes`) and `aesGcmDecrypt` (from `expo-crypto` which has a Web Crypto API backend on web). Both should work on web.

Possible causes to investigate:

1. **expo-crypto web AES returns different types** — the web `combined()` method might return a different buffer type than native, causing issues in `uint8ToBase64`/`base64ToUint8` round-trips
2. **GDrive API CORS or auth issues on web** — the GDrive fetch calls might fail differently on web
3. **`getLocalStore()` dynamic import** — the lazy `import('@/hooks/useStorage')` on line 232 might resolve differently on web
4. **Error swallowing** — the catch block (line 306) might not surface the real error

### Fix (TDD approach)

**Step 1: Write failing test** in `src/lib/__tests__/gdrive-sync-e2e-web.test.ts`:

- Create a password-protected journal on web, sync it to mock GDrive
- In a separate "device" context, import it via cloud import with the correct password
- Verify all pages are decrypted and saved locally

**Step 2: Debug and fix** — run the test, observe the failure, and fix the root cause. The test infrastructure already has `InMemoryDrive` and `InMemoryLocalStore` with web platform support.

If the issue is in `expo-crypto` web behavior, may need to add a web-specific workaround in `src/lib/encryption/utils.ts` or create `utils.web.ts`.

### Files

- `src/lib/__tests__/gdrive-sync-e2e-web.test.ts` — new test for cloud import of password-protected journals
- Likely fix in one of: `src/lib/encryption/utils.ts`, `src/components/home/NewJournalModal.tsx`, or `src/lib/sync/gdrive/store.ts`

## Issue 4: Missing contrast on danger zone confirmation buttons

### Root Cause

The delete confirmation button in `ConfirmDeleteModal.tsx` (line 108) and the account delete button in `AccountButton.tsx` (line 494) use `theme.colors.error` as background color with white (`#fff`) or `foreground` text. Several themes have light/pastel error colors that produce insufficient contrast:

| Theme      | Error Color          | Contrast vs White |
| ---------- | -------------------- | ----------------- |
| Nord       | `rgb(191, 97, 106)`  | ~2.8:1 (fail)     |
| Everforest | `rgb(230, 126, 128)` | ~2.1:1 (fail)     |
| Rose Pine  | `rgb(235, 111, 146)` | ~2.3:1 (fail)     |
| One Cyan   | `rgb(224, 108, 117)` | ~2.3:1 (fail)     |

WCAG AA requires 4.5:1 for normal text, 3:1 for large text.

### Fix

Instead of using white text on error-colored buttons, use a contrast-aware approach:

**Option A (recommended): Use dark text on light error backgrounds.** Change the danger button text color from `#fff` to a dark color (e.g., the theme's `background` for dark themes that have bright error colors, or keep `#fff` for dark enough error colors). A simple luminance check can determine which to use.

**Option B: Darken the error colors.** Adjust the error colors in themes with insufficient contrast. This affects all error color usage though, not just buttons.

**Option A implementation:** Create a utility function `getContrastText(bgColor: string): string` that returns `'#fff'` or `'#000'` based on relative luminance. Apply it in `ConfirmDeleteModal.tsx` and `AccountButton.tsx`.

### Files

- `src/styles/themes.ts` — add a `getContrastText` helper or add a `errorContrast` color to theme
- `src/components/journal/ConfirmDeleteModal.tsx` (line 114) — use contrast-aware text color
- `src/components/home/AccountButton.tsx` (line 505) — use contrast-aware text color
- `src/components/journal/FilterBar.tsx` (line 208) — check if also affected (clear filter button)

### Tests

- Unit test for `getContrastText` utility: verify correct output for all theme error colors
- Verify all themes produce WCAG AA compliant contrast ratios on danger buttons
