## 1. Encrypted Thumbnail Generation

**Problem:** Page previews load slowly because the full-size image is decrypted on every render. Only non-encrypted images get thumbnails; encrypted images are skipped entirely.

**Solution:** Generate a small (80×80) thumbnail at page save time and store it in the `Page.thumbnail` field (already exists but unused). The thumbnail is stored as a base64 string inside the page JSON, so it's encrypted along with the page data automatically.

### Steps

1. **Install `expo-image-manipulator`** — needed for resizing images natively.
   - User runs: `npx expo install expo-image-manipulator`

2. **Create `src/lib/thumbnail.ts`** — utility to generate a thumbnail:
   - Takes a base64 image string
   - Writes it to a temp file, calls `ImageManipulator.manipulateAsync()` with resize `{ width: 80 }` and compress 0.5 JPEG
   - Reads the result back as base64, cleans up temp files
   - Returns the small base64 string

3. **Update `handleSave` in `app/page/[id].tsx`**:
   - Before saving, check if draft has any non-deleted images (encrypted or not)
   - If yes, pick the first non-deleted image, call `getAttachment()` to get its base64, generate thumbnail, set `draft.thumbnail = base64Thumbnail`
   - If no images remain, clear `draft.thumbnail`

4. **Update `PageListItem.tsx`**:
   - Check `page.thumbnail` first (from PagePreview). If present, use it directly as the image source (base64 data URI) — no decryption needed at list render time
   - Fall back to existing `firstImage` flow only if thumbnail is absent (backward compat with old pages)

5. **Update `PagePreview` type and `pageToPreview()`** in `src/models/types.ts`:
   - Add `thumbnail?: string` to `PagePreview`
   - Copy `page.thumbnail` into preview

### Tests

- **`src/lib/__tests__/thumbnail.test.ts`**: Mock `expo-image-manipulator` and `expo-file-system`. Test that `generateThumbnail()` calls manipulate with correct resize params and returns base64.
- **`src/models/__tests__/types.test.ts`** (or extend existing): Test `pageToPreview()` carries `thumbnail` field through.
- **`src/components/journal/__tests__/PageListItem.test.tsx`**: Test that when `page.thumbnail` is set, it renders an Image with the base64 URI directly without calling `enqueueThumbnail`.

## 2. Editable Page Date & Time

**Problem:** Date and time in the page header are display-only, even in edit mode.

**Solution:** When editing, make the date and time tappable to open the native date/time picker (`@react-native-community/datetimepicker`, already installed).

### Steps

1. **Update `PageHeader` component** (`src/components/page/PageHeader.tsx`):
   - Add props: `isEditing: boolean`, `onDateChange?: (date: Date) => void`
   - When `isEditing` is true, wrap date and time sections in `Pressable`
   - On date press: show `DateTimePicker` in `date` mode
   - On time press: show `DateTimePicker` in `time` mode
   - Merge the selected date/time parts and call `onDateChange` with the resulting Date
   - Add visual hint when editable (e.g. subtle underline or edit icon)

2. **Update `app/page/[id].tsx`**:
   - Pass `isEditing` and an `onDateChange` handler to `PageHeader`
   - Handler calls `updateDraft({ date: newDate.toISOString() })`

### Tests

- **`src/components/page/__tests__/PageHeader.test.tsx`**: Test that date/time sections are pressable when `isEditing=true` and not when false. Test that `onDateChange` is called with the selected date.

## 3. Discard Changes on Leave (Back Button / Navigation)

**Problem:** The discard dialog only shows when toggling the edit FAB. Pressing the back button or Android hardware back while editing with unsaved changes silently discards data.

**Solution:** Intercept all navigation-away events and Android hardware back press, showing the existing discard dialog.

### Steps

1. **Update `app/page/[id].tsx`**:
   - Add `useEffect` with `BackHandler.addEventListener('hardwareBackPress', ...)`:
     - If `isEditing && isDirty`, show the discard Alert and return `true` (prevent default)
     - Otherwise return `false`
   - Add `useEffect` with `router` `beforeRemove` listener (via `useNavigation` from `@react-navigation/native`):
     - If `isEditing && isDirty`, call `e.preventDefault()` and show the discard Alert
     - On discard, reset draft and dispatch the prevented navigation action

2. **Update `BackButton` usage in `PageHeader`**:
   - Instead of directly calling `router.back()`, accept an optional `onBack` prop
   - The page screen passes a handler that checks dirty state before navigating

### Tests

- **`app/page/__tests__/[id].test.tsx`** (or `src/components/page/__tests__/PageScreen.test.tsx`):
  - Test that `BackHandler` callback returns `true` when editing with dirty state
  - Test that `BackHandler` callback returns `false` when not editing or not dirty
  - Test that the discard alert is shown when back is pressed with unsaved changes

## 5. Scroll Pagination on Journal Screen

**Problem:** All pages are loaded and rendered at once, which is slow for large journals.

**Solution:** Client-side pagination — slice the already-loaded `filteredPages` array and use FlatList's `onEndReached` to show more.

### Steps

1. **Create `src/hooks/usePagination.ts`**:
   - Takes the full `filteredPages` array and `pageSize` (default 15)
   - Returns `{ visiblePages, loadMore, hasMore, reset }`
   - Uses `useState` to track how many pages to show (initially `pageSize`)
   - `loadMore` increments by `pageSize`
   - `reset` is called when `filteredPages` reference changes (new filter or journal reload)

2. **Update `app/journal/[id].tsx`**:
   - Use `usePagination(filteredPages, 15)`
   - Pass `visiblePages` to `FlatList.data`
   - Set `onEndReached={loadMore}`, `onEndReachedThreshold={0.5}`
   - Add a `ListFooterComponent` that shows a small spinner when `hasMore` is true

### Tests

- **`src/hooks/__tests__/usePagination.test.ts`**: Test initial slice is 15, `loadMore` adds 15, `hasMore` is false when all shown, reset works when data changes.

## 6. Hidden Dev Menu

**Problem:** No way to bulk-create test data for performance testing.

**Solution:** A secret-access dev menu reachable by pressing the Canto logo 7 times on the home screen, then opening the changelog modal where a "Dev Menu" button appears.

### Activation Flow

1. Tap Canto logo 7 times → sets a `devUnlocked` flag in component state
2. Open changelog modal → "Dev Menu" button appears at the bottom (only when `devUnlocked`)
3. Press "Dev Menu" → opens a separate DevMenu modal

### Dev Menu Capabilities

- **Duplicate Journal**: Select a journal → duplicates it with all pages and all attachments (deep copy with new IDs)
- **Duplicate Page**: Select journal + page → duplicates the page N times (with attachments)
- **Generate Blank Journals**: Create N empty journals with default settings
- **Generate Blank Pages**: Select a journal → create N blank pages with random dates

### Steps

1. **Create `src/components/dev/DevMenu.tsx`**:
   - Modal component with the 4 actions above
   - Each action has a number input for count
   - Journal/page selection via dropdown lists
   - Uses storage hooks to read journals/pages and create duplicates
   - Duplication logic:
     - Read source journal/page data
     - Generate new UUIDs for journal, pages, attachments
     - Copy attachment files with new paths via `getAttachment()` + `saveAttachment()`
     - Save duplicated entities

2. **Create `src/lib/devTools.ts`**:
   - `duplicateJournal(sourceId, derivedKey?, count?)`: Deep-copies a journal N times
   - `duplicatePage(journalId, pageId, derivedKey?, count?)`: Copies a page N times within the same journal
   - `generateBlankJournals(count)`: Creates N empty journals
   - `generateBlankPages(journalId, count)`: Creates N blank pages

3. **Update `app/index.tsx` (HomeScreen)**:
   - Add `tapCount` state and `devUnlocked` state
   - Wrap `<Logo>` in a `Pressable` that increments `tapCount`, sets `devUnlocked = true` at 7

4. **Update `src/components/home/InfoBox.tsx`**:
   - Accept `devUnlocked` prop
   - In the changelog modal, conditionally render a "Dev Menu" button when `devUnlocked`
   - On press, close changelog and open DevMenu modal

### Tests

- **`src/lib/__tests__/devTools.test.ts`**:
  - Test `duplicateJournal` creates new journal with new ID, copies all pages with new IDs, copies attachments
  - Test `duplicatePage` creates N copies with unique IDs
  - Test `generateBlankJournals` creates N journals with default structure
  - Test `generateBlankPages` creates N pages with valid dates
- **`src/components/dev/__tests__/DevMenu.test.tsx`**: Test that the modal renders the 4 actions, test count input works.
- **Home screen test**: Test that logo tap counter increments and `devUnlocked` becomes true at 7 taps.

## 7. Replace Default App Icon with Canto Logo

**Problem:** The app icon on the device launcher is still the default Expo placeholder. All assets in `assets/` (`icon.png`, `splash-icon.png`, `android-icon-foreground.png`, `android-icon-background.png`, `android-icon-monochrome.png`, `favicon.png`) are Expo defaults. The actual Canto logo already exists at `src/assets/images/logo_t_v1_256.png` (256×256, black "C" with "canto" text on transparent background) and `src/assets/images/canto_bv1.png` (larger version, same design).

**Solution:** Generate properly sized icon assets from the existing Canto logo and replace the placeholder files in `assets/`.

### Icon Requirements (Expo/EAS)

- **`icon.png`** (iOS): 1024×1024, no transparency (iOS strips it). Must be the logo on a solid background.
- **`favicon.png`** (web): 48×48.
- **`splash-icon.png`**: 200×200 (or larger, centered). Can have transparency.
- **Android adaptive icon**:
  - `android-icon-foreground.png`: 1024×1024 with safe zone (logo centered in inner 66% circle). Transparent background.
  - `android-icon-background.png`: 1024×1024 solid color (or pattern).
  - `android-icon-monochrome.png`: 1024×1024, single-color silhouette on transparent background (for Material You themed icons).

### Steps

1. **Generate icon assets** using a script or image tool:
   - Source: `src/assets/images/canto_bv1.png` (the "C" logo)
   - `assets/icon.png`: 1024×1024 — Canto logo centered on white (#FFFFFF) background
   - `assets/favicon.png`: 48×48 — Canto logo on white background
   - `assets/splash-icon.png`: 200×200 — Canto logo on transparent background
   - `assets/android-icon-foreground.png`: 1024×1024 — Canto logo centered (within 66% safe zone) on transparent background
   - `assets/android-icon-background.png`: 1024×1024 — solid white (#FFFFFF)
   - `assets/android-icon-monochrome.png`: 1024×1024 — black logo silhouette on transparent background

   Since we can't run image processing tools in the CLI, the user will generate these using an image editor or a script. I'll provide exact specs and a Node.js script using `sharp` (devDep) to automate it.

2. **Verify `app.json`** references are correct (they already point to `./assets/icon.png` etc. — no changes needed there).

3. **After replacing assets**, user runs: `npx expo prebuild --clean` to regenerate native projects with new icons.

### Tests

- No unit tests needed — this is a static asset replacement. Visual verification after build.
