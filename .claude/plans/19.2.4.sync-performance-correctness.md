# Plan 19.2.4 — bounded, resumable, and efficient Web sync

**Status:** Proposed release-blocking follow-up for unreleased v0.19.2
**Primary objective:** Preserve the memory-safety gains from plans 19.2.2 and
19.2.3 while removing the request amplification, repeated work, state errors,
and key-lifecycle races found in the complete branch review against `main`.

## 1. Why this plan exists

The current branch has made sync safer in several important ways:

- backup import verifies persisted data and compensates on failure;
- new attachment storage is descriptor-aware and independently encrypted by
  chunk;
- oversized legacy attachments fail safely rather than entering a whole-value
  path;
- Web AES-GCM output no longer calls Expo Crypto's byte-by-byte base64 encoder;
- cancellation reaches local chunk iteration, WebCrypto boundaries, retries,
  and Drive fetches;
- a renderer-scoped checkpoint can stop a large initial upload before Chrome's
  native allocator grows without bound.

The staged follow-up also contains an intentional throughput correction from
the user: new content was moved from 512-KiB to 10-MiB chunks because Drive's
per-request latency made the smaller size impractical. Plans 19.2.2 and 19.2.3
were not updated to capture that decision, and the repository contains no
real-Drive benchmark comparing candidate sizes. The review should therefore
not treat 512 KiB as a validated optimum or revert to it by specification fiat.

The Chrome finding from 19.2.3 remains foundational: a roughly 225-MiB journal
could push the renderer beyond 5 GiB while V8 heap stayed nearly flat. The
controlled harness attributed the growth to renderer-native WebCrypto and
successful fetch activity; changing multipart body representation and trying
an HTTP/2 stream did not bound it. This is not evidence that Canto intentionally
holds several gigabytes of journal data. 19.2.4 must both prove that Canto drops
all chunk references and limit cumulative browser-native work, because the app
cannot explicitly release memory owned by Chromium.

The actual problems are that the larger size was combined with a chunk-count
budget calibrated for 512 KiB, and that provider metadata traffic still
dominates useful upload work:

1. A 150-chunk renderer budget with 10-MiB chunks can represent 1.5 GiB of
   plaintext before framing, AES-GCM output, base64, and multipart overhead.
   The budget must be expressed in bytes independently of the selected chunk
   size.
2. The resumable path lists each attachment generation, then performs another
   exact-name Drive lookup for every chunk that the first listing already proved
   absent.
3. Web checkpoint transfers are serialized even though two concurrent chunks
   are within the approved bound.
4. Every completed page re-lists and re-downloads all immutable sync-index
   snapshots. Because each page adds another snapshot, metadata work grows
   quadratically within one run and grows again over the lifetime of a journal.
5. Any run that starts chunk work is reported as checkpointed, even if it
   completed below budget. Errors after the first chunk are also hidden as
   checkpoints.
6. Partial generations are locally migrated to a different chunk size,
   abandoning completed remote work instead of resuming it. The problem is the
   resume-time rewrite, not the 10-MiB default for newly created content.
7. Imported AES keys are cached by mutable `Uint8Array` identity, allowing an
   in-flight operation to recover a key after auto-lock zeroes its source array.
8. The new chunk-generation migration writes outside the device-key rotation
   barrier.

For the documented 384-attachment / approximately 707-chunk journal, the cold
resume path can perform roughly 1,798 chunk-related Drive requests before page,
index, registry, and retry traffic:

```text
384 generation inventories
+ 707 redundant exact-name lookups
+ 707 chunk uploads
= 1,798 requests
```

Because the checkpoint path is serial, request latency is paid almost entirely
in series. This is the most direct explanation for sync remaining too slow.

## 2. Product contract

19.2.4 will use the following non-negotiable behavior.

### 2.1 Attachment protocol

- New and newly imported `canto-chunked-v1` content keeps the user-selected
  10-MiB plaintext default unless the real-Drive validation matrix in this plan
  demonstrates a better operating point.
- `canto-chunked-v1` treats the descriptor's `chunkSize` as authoritative; the
  format is not redefined to require one universal size.
- Existing descriptors remain readable according to their declared
  `chunkSize`, including historical 512-KiB and current 10-MiB content.
- Sync never rewrites a local attachment merely to alter transfer size.
- A retry reuses the same immutable generation and skips remote indexes that
  are already present before opening local content.
- A partial generation remains invisible until its page and sync-index entry
  are durably published.
- Remote orphan-generation cleanup remains separate from upload and resume.
  Upload failure must not guess generation ownership or delete remote data.

### 2.2 Renderer budget

- The Web safety limit is byte-bounded, not merely chunk-count-bounded. The
  initial target is 75 MiB of missing plaintext-equivalent work per renderer,
  preserving the raw-data budget implied by the earlier 150 × 512-KiB limit
  while allowing at most seven complete 10-MiB chunks plus a partial chunk.
- This is a renderer-lifetime budget, not a fresh allowance for every sync. A
  manager-owned ledger is shared by every journal and every sync in the current
  renderer.
- The ledger is stored in `sessionStorage` so a normal reload does not reset it.
  It clears only when the tab is fully closed and a new renderer session begins.
- Each reservation records both raw bytes and a conservative estimated native
  allocation cost for frame encoding, WebCrypto input/output, base64, and fetch
  body construction. The Chrome harness calibrates the cost multiplier and
  renderer limit; JavaScript heap alone is not accepted as evidence because the
  observed growth is renderer-native.
- Reservation uses the exact expected plaintext length of each missing index,
  including a smaller final chunk. It therefore remains safe when reading a
  descriptor whose chunk size differs from the current default.
- The budget is reserved before IndexedDB reads, local decryption, sync
  encryption, or request-body construction.
- At most two reserved chunks may be in local-read/WebCrypto/fetch work at once.
- A completed run with renderer capacity remaining is a normal success. It
  persists `lastSync` and does not require a tab restart.
- A run that completes useful sync work exactly as the renderer allowance is
  consumed remains `completed` and persists `lastSync`, but carries
  `requiresFreshRenderer: true`; later syncs are blocked until the tab is fully
  closed.
- Exhausting the budget produces `checkpointed` only after all publishable
  completed pages have durable index entries and unsynced work still remains.
- A second journal cannot obtain a fresh allowance after the first journal has
  spent the renderer budget. The native allocation risk belongs to the browser
  renderer, not to a Canto journal or one `SyncEngine` instance.
- Canto queues, results, traces, provider caches, and UI state must not retain a
  completed plaintext chunk, decrypted frame, ciphertext, base64 string, Blob,
  FormData, or request body. The lifetime ledger remains necessary even after
  that assertion passes because browser-native high-water can remain elevated
  without a JavaScript retaining path.

### 2.3 Outcome semantics

Engine and manager outcomes must be distinguishable:

```ts
type SyncRunOutcome =
  | { kind: 'completed'; result: SyncResult; requiresFreshRenderer: boolean }
  | {
      kind: 'checkpointed';
      result: SyncResult;
      reason: 'renderer-budget';
      requiresFreshRenderer: true;
    }
  | { kind: 'cancelled'; requiresFreshRenderer: boolean }
  | { kind: 'failed'; error: Error; requiresFreshRenderer: boolean };
```

- `checkpointed` means only that the renderer byte budget was exhausted.
- A network, Drive, crypto, IndexedDB, or data-integrity failure remains an
  error even if chunk work already occurred.
- `requiresFreshRenderer` is orthogonal to outcome. It may prevent same-tab
  retry without replacing the real status or error message.
- User-requested cancellation remains cancellation. Disabling sync leaves
  remote data untouched and does not show a failure notification.
- `lastSync` and the remembered remote salt are persisted only for
  `completed`.
- Automatic same-renderer resume is suppressed for every outcome carrying
  `requiresFreshRenderer: true`, including a completed run that consumed the
  renderer's lifetime allowance.

### 2.4 Provider request bounds

For a cold upload with `A` immutable attachment generations and `C` missing
chunks:

- generation inventory uses one paginated folder listing per prepared batch,
  not one listing per attachment;
- each missing chunk causes exactly one Drive create request in the uncontended
  case;
- no exact-name lookup occurs after the prepared inventory has proved a chunk
  absent;
- each present chunk is skipped without IndexedDB, local crypto, sync crypto,
  or upload work;
- an unexpected 404 for a cached present ID may perform one verified fallback
  lookup before recreation;
- concurrency never exceeds two active chunk uploads.

### 2.5 Sync-index bounds

- A run reads the remote index state once when opening its publication session.
- Publishing a completed page creates one immutable delta and updates the
  session's in-memory merged index without re-reading already observed files.
- The compatibility `index.json` projection is conditionally updated at most
  once at checkpoint/finalization, not after every page.
- Index deltas are compacted so a journal does not accumulate an unbounded
  number of files that every future client must download.
- Concurrent writers remain safe: a compatibility projection is never the sole
  authoritative record, and compaction never deletes an input before an
  immutable replacement is durable.

### 2.6 Chunk-size validation

Chunk size is a performance and memory tuning parameter, not an article of
faith. Keep 10 MiB as the working default while measuring at least 512 KiB,
2 MiB, 5 MiB, 10 MiB, and 20 MiB against real Drive.

The matrix must separate two workloads:

1. **Many small attachments:** the documented 384-attachment distribution.
   Every non-empty attachment requires at least one Drive object, so increasing
   chunk size cannot reduce the request count below the attachment count.
   Batched inventory and removal of redundant lookups matter more here.
2. **Few large attachments:** generated 20–250 MiB files. Chunk size directly
   controls useful bytes per Drive request, retry cost, and peak renderer
   allocation here.

For each candidate record:

- total elapsed time and useful MiB/s;
- request count and p50/p95 upload duration;
- post-GC JavaScript heap and browser-agent/RSS high-water;
- retry cost after an injected interruption;
- responsiveness with one and two workers;
- checkpoint count under the same byte budget.

The current transport also needs explicit validation. Google documents
multipart upload for small files of 5 MB or less and recommends resumable upload
for larger files. A 10-MiB raw attachment chunk becomes roughly an 18-MiB sync
ciphertext string after the framed payload and sync layer are base64 encoded.
Benchmark current multipart uploads against resumable uploads rather than
assuming either is faster; resumable upload adds a session-init request, while
multipart sends the larger object in one request. See the official
[Drive upload guidance](https://developers.google.com/workspace/drive/api/guides/manage-uploads).

Selection rule:

- retain 10 MiB if it meets the renderer-memory gate and is within 10% of the
  best measured throughput;
- choose another default only with recorded real-Drive evidence;
- never couple renderer safety to a fixed number of chunks again.

### 2.7 Resume contract

Sync remains resumable across a checkpoint, reload, tab close, renderer crash,
network interruption, and app restart:

1. Every attachment descriptor carries an immutable generation. Remote chunk
   object names are deterministic from attachment ID, generation, and index.
2. A successful Drive create response makes that immutable index reusable even
   if the client crashes before publishing the page.
3. The next renderer opens one prepared remote inventory before local reads. It
   treats present indexes as complete and schedules only missing indexes.
4. Present indexes cause no IndexedDB read, local decryption, WebCrypto call, or
   upload body allocation.
5. Sync never changes generation or chunk size merely because a prior run is
   partial. Existing remote work is therefore never invalidated by resume.
6. A page object is uploaded only after every attachment generation referenced
   by that page is complete.
7. The immutable sync-index delta is the publication boundary. Until it exists,
   remote readers continue seeing the previous complete page revision.
8. After publication, the next renderer skips the page through the remote
   index. A crash between page upload and index publication may repeat one page
   upload but cannot expose a partial attachment generation.
9. No password, derived key, imported CryptoKey, access token, local payload, or
   upload body is stored in the resume ledger. Only non-sensitive renderer work
   counters and the existing remote immutable objects survive.

## 3. Target module design

The implementation should deepen two existing provider seams instead of adding
more lookup and checkpoint decisions to `SyncEngine`.

### 3.1 Prepared attachment-upload module

Replace the current combination of `prepareAttachmentChunkUploads`,
`listAttachmentChunkIndexes`, and implicit `fileIdCache` behavior with one
prepared upload interface:

```ts
interface PreparedChunkUploads {
  missingIndexes(attachment: Attachment): readonly number[];
  uploadMissingChunk(
    attachment: Attachment,
    index: number,
    encryptedData: string,
    signal?: AbortSignal,
  ): Promise<void>;
}

interface RemoteStore {
  prepareChunkUploads(
    journalId: string,
    attachments: readonly Attachment[],
    signal?: AbortSignal,
  ): Promise<PreparedChunkUploads>;
}
```

The interface includes these invariants:

- preparation observes exact immutable generation/index names for the supplied
  attachments and records both presence and known absence;
- `missingIndexes` is metadata-only and deterministic for that prepared view;
- `uploadMissingChunk` rejects an index outside the prepared missing set;
- a known-absent chunk is created directly;
- a known-present chunk is never uploaded through this method;
- provider file IDs, names, folder IDs, queries, cache keys, and fallback lookup
  rules remain inside the Drive adapter;
- the in-memory adapter implements the same interface and records request and
  concurrency metrics for tests.

`SyncEngine` should ask this module what work is missing, reserve byte budget,
and provide encrypted chunk values. It should not decide how Drive proves
existence or whether a create/update is appropriate.

### 3.2 Sync-index publication module

Replace repeated `downloadSyncIndex` / `uploadSyncIndex` orchestration with a
publication session:

```ts
interface SyncIndexPublication {
  readonly initial: Readonly<SyncIndex>;
  publishPage(pageId: string, entry: SyncIndexEntry, signal?: AbortSignal): Promise<void>;
  finalize(projection: SyncIndex, signal?: AbortSignal): Promise<void>;
}

interface RemoteStore {
  openSyncIndexPublication(journalId: string, signal?: AbortSignal): Promise<SyncIndexPublication>;
}
```

The Drive adapter owns:

- the initial legacy-index and immutable-file listing;
- fetching each observed immutable file no more than once per session;
- entry merge/tie-break semantics;
- immutable per-page delta naming and creation;
- in-memory incorporation of deltas created by this session;
- one best-effort ETag-protected compatibility projection at finalization;
- compaction and compaction-race recovery.

`SyncEngine` owns only the domain decision that a page is publishable after its
attachments and encrypted page object are durable. It calls `publishPage` at
that point. It never lists snapshots or performs a merge-before-every-write.

### 3.3 Compaction format

Continue reading current `index.json` and `index-v2-*.json` files. Add an
additive compact immutable format, for example:

```ts
interface CompactSyncIndex {
  version: 3;
  entries: SyncIndex;
  coveredFileIds: string[];
}
```

Compaction rules:

1. Trigger when uncompacted immutable files exceed a conservative threshold,
   initially 128.
2. Merge only files whose IDs and contents were observed by this session.
3. Create a uniquely named immutable `index-v3-<uuid>.json` containing the
   merged entries and exact covered IDs.
4. Confirm successful creation before deleting anything.
5. Delete only covered immutable files. Deltas created concurrently after the
   inventory are not listed in `coveredFileIds` and survive.
6. Readers merge all surviving v2 deltas and v3 compact snapshots using the
   existing revision/tombstone tie-break.
7. If a listed input disappears between listing and download because another
   client compacted it, re-list once and rebuild from the durable replacement
   rather than failing sync.
8. Multiple concurrent compactors are valid. Their immutable outputs can be
   merged, and a later compaction can cover redundant compact snapshots.
9. `index.json` remains a compatibility projection and is never used to decide
   which immutable files are safe to delete.

The format must be validated through the in-memory Drive adapter before any
cleanup is enabled against real Drive. If race tests do not establish safety,
ship 19.2.4 with per-session caching and no deletion, and keep compaction behind
a disabled feature flag rather than risking index loss.

## 4. Implementation phases

### Phase 0 — Characterization tests before behavior changes

Add failing tests that capture current defects:

1. A cold prepared upload proves that known-missing chunks incur exact-name
   lookups before create.
2. A 100-page Web upload records repeated snapshot downloads and demonstrates
   superlinear index requests.
3. A 17-chunk run under the configured budget currently returns checkpointed
   instead of completed.
4. A Drive failure after one uploaded chunk currently becomes checkpointed and
   loses its error.
5. Auto-lock zeroes a key while sync retains its array, then cached crypto still
   encrypts with the old imported key.
6. Device-key rotation overlaps a chunk-generation migration outside the write
   barrier.
7. A 150-item budget accepts 1.5 GiB when descriptors use the selected 10-MiB
   default, proving that item count is not a safe renderer budget.

Tests should assert outcomes and provider metrics through the target module
interfaces. Once the deep modules replace the old methods, delete tests that
only verify the retired shallow calls.

### Phase 4 — Byte budget and two-worker scheduler

Files centered in this phase:

- `src/lib/sync/engine.ts`
- `src/lib/sync/manager.ts`
- `src/lib/sync/types.ts`
- sync memory and checkpoint tests

Steps:

1. Replace `NewChunkUploadBudget` with a manager-owned `RendererWorkLedger`.
   The manager creates one ledger for the tab, and every journal and
   `SyncEngine` run receives a lease against its remaining lifetime allowance
   rather than a new per-run budget.
2. Persist the versioned ledger under one global `sessionStorage` key. Do not
   key it by journal, account, sync run, or attachment. Reloading the page must
   retain the cumulative charge; only ending the tab's storage session starts
   a fresh allowance.
3. Maintain two conservative counters: expected plaintext bytes and estimated
   renderer-native allocation cost. Reject a reservation if either configured
   limit would be crossed. Calibrate the native-cost estimate with the Chrome
   harness instead of treating JavaScript heap as total browser memory.
4. Derive expected bytes for index `i` from descriptor `byteLength`,
   `chunkSize`, and `chunkCount`; reject inconsistent descriptors before local
   reads.
5. Build missing chunk work items from prepared inventories. Known-present
   remote chunks consume no renderer-work allowance.
6. Reserve and persist each charge synchronously, immediately before dispatch,
   in deterministic page/attachment/index order. Once native-heavy work may
   have begun, do not refund the charge after success, failure, or cancellation:
   Chrome may still retain the associated native allocations.
7. Execute reserved work through exactly two workers.
8. Keep each worker's sequence bounded to one local chunk, one decrypted frame,
   one sync ciphertext, and one fetch body.
9. Drop every payload reference in a `finally` boundary after its request
   settles. Prepared inventories, queues, outcomes, traces, and Drive caches may
   retain metadata only; none may retain plaintext, ciphertext, Blob, FormData,
   or request bodies.
10. Stop scheduling immediately when the next work item cannot fit either
    remaining ledger limit.
11. Publish every fully completed page; never publish a page with a partial
    attachment generation.
12. Return checkpointed only if missing work remains because the ledger was
    exhausted.

## 5. Test plan

### 5.1 Protocol and storage

- New byte/base64/browser/native/imported attachments use the selected default
  descriptor size, initially 10 MiB.
- Exact boundary cases use `S = ATTACHMENT_CHUNK_SIZE`: 0, 1, `S − 1`, `S`,
  `S + 1`, and multiple chunks plus a partial final chunk.
- Historical 512-KiB descriptors and current 10-MiB descriptors remain readable
  and resumable without rechunking.
- Existing redirects remain readable, but no new sync path writes redirects.
- Corrupt descriptor math fails before any IndexedDB read or Drive call.
- Logic tests that do not measure production memory use deliberately small
  descriptor sizes instead of allocating one or more production-size chunks.

### 5.2 Drive request-count tests

Using the in-memory Drive adapter:

- cold `A`-attachment / `C`-chunk upload performs one paginated inventory and
  exactly `C` creates, with zero exact-name chunk lookups;
- partial resume performs one inventory, zero local reads for present indexes,
  and one create per missing index;
- a stale cached-present ID returning 404 performs at most one fallback lookup;
- two workers are observed under load and active chunk uploads never exceed two;
- a cancellation aborts workers and starts no later chunk.

Include a deterministic 384-attachment / 707-chunk metadata fixture. Payloads
may be tiny test frames where a test is measuring calls rather than memory.

### 5.3 Index publication tests

- Publishing 100 pages performs O(100) immutable writes and no repeated reads of
  snapshots already observed by the session.
- The compatibility projection is updated no more than once per finalization.
- Concurrent first writers preserve both entries.
- Concurrent page writers with equal and differing revisions preserve the
  existing tombstone tie-break.
- Compaction covers only observed IDs, preserves concurrent unseen deltas, and
  tolerates an input disappearing between list and fetch.
- Readers merge legacy, v2, and v3 combinations.
- A failed compact-snapshot creation deletes nothing.
- A failed cleanup leaves redundant but readable files.

### 5.4 Outcome and checkpoint tests

- An under-budget chunk upload completes, persists `lastSync`, and allows a
  later same-tab sync only while cumulative renderer capacity remains.
- Repeated individually under-budget syncs consume the same cumulative
  allowance and eventually require a fresh renderer; no run receives a fresh
  75-MiB allowance.
- Reloading the same tab does not reset the ledger, and switching to a second
  journal does not create an independent allowance.
- Ending the tab's storage session and opening a new tab creates a fresh ledger;
  the new run resumes by inventorying immutable remote chunks rather than
  re-uploading completed indexes.
- A completed run that consumes the final allowance persists `lastSync`, stays
  completed in the UI, and blocks later same-tab native-heavy work through
  `requiresFreshRenderer: true`.
- After forced GC, completed payloads have no JavaScript retaining path through
  engine workers, queues, results, traces, UI state, or provider caches, even if
  Chrome's browser-agent/RSS measurement remains above baseline.
- Exhaustion before a page completes leaves the partial generation unindexed
  and returns checkpointed.
- Exhaustion exactly after a page completes publishes that page, finalizes the
  index, and returns checkpointed.
- A network/Drive/crypto/IndexedDB failure after chunk work remains failed,
  retains its message, and carries `requiresFreshRenderer: true`.
- User cancellation remains cancelled; Disable Sync leaves remote files intact.
- Key rotation never uses renderer checkpointing and remains all-or-nothing.

### 5.5 Security and lifecycle tests

- Auto-lock aborts active sync before destroying its journal key.
- Evicted/zeroed arrays cannot retrieve cached imported keys.
- Device-key clear and journal-key clear both release imported cache entries.
- No mutating LocalStore operation overlaps device-key rotation.
- Cancellation and key release do not turn a completed page/index publication
  into a false `lastSync` success.

## 7. Acceptance criteria

- New/imported descriptors use the benchmarked default, with 10 MiB retained
  unless recorded real-Drive evidence selects another size.
- No sync-time rechunking or generation replacement occurs.
- Existing remote indexes are skipped before local reads and crypto.
- The documented cold fixture performs no redundant exact-name chunk lookups.
- Chunk inventory and index work grow linearly, not quadratically, with journal
  size.
- Web upload uses at most two concurrent chunks and a 75-MiB plaintext budget,
  independent of descriptor chunk size.
- The renderer-work allowance is cumulative across successful and failed runs,
  all journals, and reloads in one tab; it resets only with a new tab storage
  session.
- Ledger reservations account conservatively for WebCrypto, base64, and fetch
  native allocations that may outlive Canto's JavaScript references, and are
  never refunded merely because a run returned.
- Under-budget work completes normally; only actual budget exhaustion is
  checkpointed.
- Failures and cancellations remain distinguishable after chunk work begins.
- `lastSync` is written only for completed sync.
- Auto-lock prevents later chunks from using the destroyed journal key.
- Every LocalStore mutator is serialized against device-key rotation.
- Index compaction is race-safe or remains disabled; no release may enable
  destructive cleanup without passing concurrent-writer tests.
- Targeted tests, full Jest, format, lint, typecheck, and `make check` pass.
- Manual synthetic Web sync and the chunk-size/transport matrix pass with
  bounded memory and materially reduced provider request count.
- No private archive, journal content, attachment name, token, or key is added
  to source, tests, traces, or review artifacts.

## 8. Non-goals

- Replacing flat `.canto.zip` v1 or JSZip.
- Automatically migrating oversized legacy monolithic attachments.
- Changing AES-GCM framing or the authenticated chunk identity fields.
- Redesigning Google authentication or changing providers.
- Client-side deletion of remote orphan attachment generations.
- Publishing a partially rotated password/device-key state.
- General UI redesign beyond accurate sync outcomes and instructions.

## 9. Rollout and rollback

- Land byte-budget characterization and removal of resume-time migration before
  provider optimizations; do not revert the selected 10-MiB default without
  benchmark evidence.
- Keep index changes additive: old clients continue reading `index.json`; new
  clients read legacy/v2/v3 immutable records.
- Gate destructive v3 compaction cleanup independently from v3 reading/writing.
- If compaction shows any concurrency ambiguity, disable deletion without
  rolling back prepared chunk inventory, scheduler, or state fixes.
- Keep nonstandard existing descriptors readable so rollback never requires
  rewriting local attachments.
- Do not mark v0.19.2 releasable until the manual Web release gate and full suite
  both complete.
