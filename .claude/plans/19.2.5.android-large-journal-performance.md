# Plan 0.19.2.5 — bounded Android imports and fast large-journal views

**Status:** Proposed release plan  
**Release:** `0.19.2.5`  
**Primary objective:** Make large journals safe and responsive on Android without
weakening backup compatibility, local encryption, transactional import, sync
resume behavior, or the 12-MiB attachment chunk contract established in
0.19.2.4.

**Planning provenance:** Prepared by OpenAI Codex at the user's direct request
after repository inspection and two parallel, read-only reviews of `main...HEAD`:
one against repository standards and one against plans 19.2.1–19.2.4. The user
specifically required this revision to begin by investigating the prior commits
that restored sync and by adding coverage where manual validation exposed the
most costly failures. No production implementation is part of this plan update.

## 1. Executive decision

The four reported symptoms share two architectural causes:

1. Large backup and image paths still cross the JavaScript/native boundary as
   whole values even though attachment storage is chunked.
2. Read-oriented screens ask the storage layer for a complete journal, forcing
   Android to open, decrypt, and parse every page for information that fits in a
   small preview catalog.

0.19.2.5 should fix those boundaries, not tune delays around them:

- native backup import will inspect ZIP metadata and extract one entry at a time
  without loading the archive into Hermes;
- imported and existing journals will have an encrypted, rebuildable page
  catalog used by the journal list, filters, tags, and calendar;
- full pages will be read only when a page is opened or a full-data operation
  such as sync, export, or password rotation explicitly needs them;
- page images will materialize automatically through a bounded display pipeline
  that writes decrypted chunks directly to an app-private cache file;
- the calendar will render from the catalog through a virtualized list.

There is one mandatory predecessor to all of that work. The recent sync recovery
series must be audited and protected first. Commits `88a9d75`, `3e93cc2`, and
`f318f5f` restored resumability/index compaction, expanded coverage, and hardened
the import/auth failures found during manual validation. 0.19.2.5 must begin by
reconstructing their intended contracts, replaying the failures they addressed,
and adding cross-layer regression tests at the seams that hurt in real use. No
ZIP, catalog, calendar, or image architecture change starts until that gate is
green.

The page files and attachment generations remain the source of truth. The new
catalog is an optimization that can always be rebuilt.

## 2. Investigation findings

### 2.1 Android backup import `OutOfMemoryError`

The failing fixture is a version-1, unencrypted backup with this aggregate
shape:

| Property                      |    Observed value |
| ----------------------------- | ----------------: |
| ZIP size                      | 224,385,550 bytes |
| Pages                         |               351 |
| Page JSON bytes               |           798,791 |
| Attachment entries            |               384 |
| Uncompressed attachment bytes |       225,321,227 |
| Largest attachment            |  80,106,024 bytes |

The current native path performs these operations twice, first in
`inspectBackup` and again in `importJournal`:

```ts
const raw = await file.bytes();
const zip = await JSZip.loadAsync(raw);
```

`File.bytes()` creates a JavaScript `Uint8Array` for the complete 224-MB file.
JSZip then retains the archive buffer and creates its own parsing/inflation
state. A desktop Node characterization reached about 278 MiB maximum RSS merely
opening this archive; it did not inflate the 80-MB attachment, encrypt storage
chunks, create a thumbnail, or build the final journal. Android therefore fails
for a predictable architectural reason, even though attachments are consumed
one at a time later.

The selected fixture is unencrypted. Its failure does not require a backup
format change: Android can stream each ordinary ZIP entry through platform ZIP
APIs and into the existing 12-MiB local attachment chunks.

Legacy version-1 backups with `manifest.encrypted=true` have a separate,
unavoidable constraint. Each encrypted attachment is one AES-GCM value whose
authentication tag covers the whole entry, so it cannot be authenticated and
decrypted incrementally with the current format. 0.19.2.5 will preserve these
backups and their existing bounded-size guard, but it must fail before import
with an actionable message when one encrypted entry exceeds that safe bound.
It must never attempt the unsafe allocation or silently produce a partial
journal. A new backup format is not required for the reported unencrypted
fixture and is outside this patch release.

### 2.2 Images remain hidden until tapped

The behavior is currently intentional:

- `ImageCarousel` automatically queues only attachments accepted by
  `canGenerateThumbnailFromAttachment`;
- that predicate rejects chunked images, unknown-size images, and legacy images
  larger than 512 KiB;
- a rejected image receives a pressable placeholder and is loaded only after a
  tap;
- tests explicitly assert that chunked and oversized originals are not queued.

That policy is correct for journal-list thumbnails, where reconstructing
hundreds of originals would be harmful, but it is wrong after the user has
opened one page.

Simply removing the predicate is unsafe. Native `getAttachment` currently
decrypts every local chunk into a `string[]`, joins the complete base64 value,
and then the page screen writes that complete base64 value to a random cache
file. Large images therefore create several simultaneous representations and
the random `img-*`/`eimg-*` cache files have no explicit lifecycle.

The page screen also calls `useJournalTags`, which reads and decrypts every page
in the journal while the image queue is starting. This adds avoidable I/O and
crypto contention to the same transition.

### 2.3 Calendar is slow

Opening the calendar currently:

1. calls `useJournal`, loading and decrypting every page again;
2. maps every full page to a preview;
3. computes the month summary;
4. renders every month eagerly in one `ScrollView`;
5. creates roughly 35–42 day cells per month before the user can interact.

The full-journal read is the dominant avoidable cost. Eager month rendering is
the second cost and grows with journal history.

### 2.4 Opening a journal takes more than one minute

Native `getJournal` reads metadata, lists the pages directory, and then performs
a sequential file read, device decryption, optional password decryption, and
JSON parse for every page.

`JournalScreen` starts that scan through `useJournal` and then unconditionally
calls `refresh()` from `useFocusEffect`. Because the focus callback depends on
journal pages, settings, thumbnail state, and sync state, it can be recreated
while focused and trigger further scans. The reported 351-page journal can
therefore cause at least 702 page reads on a normal open, with additional passes
possible as dependencies change. Android pays filesystem and native-crypto
bridge latency on every small file; desktop IndexedDB and CPU behavior hide much
of that amplification.

The same whole-journal API is also used for operations that do not need pages:

- journal settings, title, icon, and sync setup call `saveJournal`, which
  rewrites every page;
- opening a page obtains tag suggestions through another `getJournal` scan;
- opening the calendar starts another full scan;
- the post-import verification calls `getJournal`, rereading every newly written
  page.

### 2.5 Test baseline

The relevant current suites pass: 6 suites and 143 tests. They cover small
backup correctness, carousel behavior, queue serialization, journal/sync
scheduling, and calendar helpers. They do not characterize archive buffering,
page-file I/O counts, calendar virtualization, cache cleanup, or physical-device
memory. Some carousel tests enforce the behavior this plan must replace.

## 3. Release contracts

### 3.1 Backup import contract

- Selecting or inspecting a backup must never call `File.bytes()` on the whole
  ZIP on native platforms.
- Native ZIP handling must keep archive bytes outside the JavaScript heap and
  expose only bounded metadata, bounded text entries, or one attachment chunk.
- The 224,385,550-byte fixture must import on the target Android device without
  `OutOfMemoryError`, process death, a half-visible journal, or orphaned import
  files.
- Import remains a new-journal operation with regenerated journal, page, and
  attachment IDs.
- Existing path validation, schema validation, password behavior, attachment
  warnings, thumbnail limits, and transactional rollback remain intact.
- The importer must preflight disk space before writing journal content.
- Cancellation, JavaScript errors, native errors, app restart, and process death
  must all leave either the old state or one complete imported journal.
- Import progress gains explicit `preparing`, `pages`, `attachments`, and
  `finalizing` phases. Password derivation and archive inspection continue to
  show a spinner before work begins.

### 3.2 Journal overview contract

- The journal screen, tag suggestions, and calendar must not call `getJournal`.
- A warm journal open reads encrypted metadata and one encrypted page catalog;
  it reads zero page files.
- After a catalog exists, a page file is loaded only when that page is opened or
  a full-data workflow explicitly requests it. A one-time legacy catalog rebuild
  is the documented exception.
- Sync remains free to take one complete, immutable journal snapshot. This plan
  does not change the Drive protocol, 12-MiB chunk size, checkpointing, index
  compaction, or resume semantics from 0.19.2.4.
- Export and password rotation load full data only after the user starts those
  actions and must show progress while doing so.

### 3.3 Page-image contract

- A persisted thumbnail appears immediately for the first image when present.
- Every active image on an opened page starts loading automatically; no image
  requires a tap merely to decrypt or display it.
- Android materializes at most one full image stream at a time. Work is bounded
  to one stored attachment chunk plus crypto/encoding overhead, independent of
  total image size.
- The current image is prioritized, followed by adjacent images and then the
  remainder in page order.
- A tap may reprioritize an image or open an already loaded image. A retry button
  is shown only after a real load failure.
- Leaving the page, locking the journal, or replacing the attachment generation
  cancels queued work and releases decrypted cache leases.
- Journal-list thumbnails retain their current bounded policy and never
  reconstruct a chunked original.

### 3.4 Calendar contract

- The calendar consumes the journal catalog and reads zero full page files.
- Only a bounded window of month cards is mounted on Android.
- Anniversary and month navigation behavior remains unchanged.
- Scroll restoration remains stable after replacing pixel-oriented `ScrollView`
  state with virtualized-list state.

## 4. Target architecture

### 4.1 Keep heavy data behind deep interfaces

The UI should no longer know whether a backup is JSZip-backed, whether an image
is chunked, or how a catalog is encrypted. Introduce three internal boundaries:

```ts
interface BackupArchive {
  inventory(): Promise<BackupInventory>;
  readText(name: string, maxBytes: number): Promise<string>;
  streamBytes(name: string, chunkBytes: number): AsyncIterable<Uint8Array>;
  close(): Promise<void>;
}

interface JournalOverview {
  metadata: Omit<JournalContent, 'pages'>;
  pages: ListPagePreview[];
  tags: string[];
  latestModified: number;
}

interface AttachmentDisplayLease {
  uri: string;
  release(): Promise<void>;
}
```

The exact method names may change during implementation, but these ownership
rules may not:

- `BackupArchive` owns ZIP parsing, temporary entry files, path safety, and
  cleanup.
- The journal repository owns catalog consistency and migration.
- The display service owns chunk decryption, cache files, cancellation, and
  cache cleanup.
- React components receive small values and URIs, not archive buffers or full
  base64 attachments.

### 4.2 Data flow after the change

```text
backup file
  -> native ZIP inventory
  -> one temporary extracted entry
  -> 12-MiB JS chunk
  -> encrypted local attachment generation
  -> delete temporary entry

journal open
  -> metadata.json + page-catalog.json
  -> list/filter/tag/calendar views
  -> getPage(pageId) only after page navigation

page image
  -> one encrypted local chunk
  -> decrypt and decode
  -> append bytes to app-private cache file
  -> URI lease to Image
  -> delete on release/stale-cache cleanup
```

## 5. Mandatory Phase 0 — audit and protect the sync recovery work

### 5.1 Why this is the first phase

The branch contains a large, tightly coupled sync/storage recovery series rather
than one isolated fix:

| Commit    | Intent to verify                                                                         |
| --------- | ---------------------------------------------------------------------------------------- |
| `88f2d97` | Bound attachment sync/import previews and preserve compatibility                         |
| `df4ac1e` | Harden checkpointed Web sync and renderer-memory behavior                                |
| `88a9d75` | Restore resumable Drive sync and compact sync-index files                                |
| `3e93cc2` | Raise sync/storage coverage after the behavior changes                                   |
| `f318f5f` | Harden large import, Android crypto compatibility, and long-running Drive authentication |

The review baseline is `main...HEAD`; the intent sources are plans 19.2.1
through 19.2.4 plus the manual failures that drove follow-up commits. The audit
must inspect implementation and tests together, not assume a passing suite
proves the workflow.

The current test arrangement has a particularly important blind spot:

- `src/components/**` and `app/**` are excluded from collected coverage;
- there is no `SyncModal` test;
- manager, engine, Drive-store, and API tests mostly exercise their layer with
  mocked neighbors;
- therefore “Sync now closes/does nothing,” stale progress, hidden 401/403
  errors, and incorrect button blocking can recur while global coverage remains
  near 99%.

Phase 0 prioritizes incident impact and contract boundaries over filling easy
uncovered lines.

### 5.2 Reconstruct and reconcile the sync contract

Before writing new behavior, build an audit matrix with one row per user-visible
or durability contract and these columns:

- originating plan/manual incident;
- implementing commit and production symbols;
- current automated test(s);
- platform(s) actually exercised;
- missing cross-layer seam or fault point;
- expected state, remote side effect, request count, and user feedback;
- disposition: proven, missing test, contradictory intent, or confirmed bug.

At minimum, trace these workflows from UI/context through manager, engine,
remote store, API, and local storage:

1. first sync of a large imported journal;
2. checkpoint before a chunk opens, checkpoint after useful uploads, page reload,
   complete tab close, app restart, and resume;
3. successful sync finalization and index compaction;
4. two devices publishing different pages and the same page concurrently;
5. token expiry during index open, page download, attachment download, chunk
   upload, page publish, compatibility-index update, and compaction;
6. permission/quota 403 during each publish boundary;
7. cancellation, auto-lock, logout, modal close, and provider disconnect;
8. new 12-MiB content, historical chunk sizes, and partial-generation resume;
9. cloud import followed immediately by normal sync;
10. local metadata/settings changes while sync is starting or in flight.

The initial commit review has already identified high-risk hypotheses. Phase 0
must prove or disprove each against production code and a failing test:

- manager/context/UI still communicate through `SyncResult | null` plus optional
  flags even though 19.2.4 specified a discriminated outcome; this may explain
  silent UI behavior and error/checkpoint ambiguity;
- the renderer ledger is currently memory-only and manager reconstruction resets
  it, while 19.2.4 says normal reload must retain the limit; the test, UI text,
  and plan cannot all be correct as written;
- v3 compaction may delete older compact snapshots without proving that every
  deleted input is represented by `coveredFileIds`, and the required one-time
  re-list when an input disappears needs an integration test;
- a 401 refresh may return the same locally “fresh” token that Drive rejected;
  retry tests must force token replacement and distinguish authentication from
  retryable transport failures;
- cloud import still writes the whole journal and then writes every page again,
  without the same reopen/readback verification used by file backup import;
- native and Web stores duplicate password-frame fallback logic and mostly have
  parallel implementation-shaped tests instead of one shared `LocalStore`
  contract suite;
- browser-only renderer behavior lives in a shared `.ts` module, and several new
  user-facing auth/import errors bypass the required translation dictionaries.

Treat these as audit leads, not conclusions to preserve. A test may demonstrate
that a suspected issue is safe, but the matrix must record the evidence and the
reason.

Resolve documentation/implementation contradictions explicitly. In particular,
the audit must decide and document whether a normal browser reload is an
approved fresh-renderer resume boundary or whether only a fully closed tab is.
The renderer ledger, manager state restoration, UI wording, and browser-level
test must all implement the same answer. Do not preserve contradictory tests and
plan text merely because both pass independently.

Append the completed matrix and decisions to this plan before Phase 1. Any
confirmed bug is release-blocking and is fixed in a sync-only change before the
new import/catalog implementation begins.

### 5.3 Add incident-derived regression coverage first

Add the following tests before refactoring storage or screens. Whenever
practical, first demonstrate that the test fails against the parent of the
commit that fixed the incident or against a deliberately disabled invariant.
This proves the assertion would have caught the real regression.

#### A. Sync UI and manager readiness

- Add `SyncModal` component tests even though components are excluded from the
  coverage denominator.
- Pressing “Sync now” while the manager is still initializing must either wait
  or show a stable actionable state; it may not silently return `null` and close.
- A normal success, checkpoint, cancellation, 401, 403, network failure, and
  `requiresFreshRenderer` outcome must leave the expected button enabled/blocked
  state and visible feedback.
- The modal must not close itself merely because an async run returned `null`.
- The error shown to the user must preserve the useful status/category without
  leaking Drive response bodies, tokens, keys, or stack details.
- Reopening the modal must reflect manager state rather than stale component
  feedback.
- Characterize every current `null` return path. Then either implement the
  discriminated `SyncRunOutcome` required by 19.2.4 or update the contract with a
  reviewed reason; no UI branch may infer cancellation, manager-not-ready,
  authentication failure, or checkpoint from the same undifferentiated value.

#### B. Reload, restart, and durable resume

- Add a browser-level test that crosses the actual provider/manager lifecycle,
  not only `new SyncManager()` in the same Jest process.
- Distinguish rerender, route navigation, page reload, full tab close, and native
  app restart; test each supported boundary explicitly.
- Persist remote chunks and immutable index deltas across the simulated restart,
  recreate all renderer-local state, and assert only missing indexes are read or
  uploaded.
- A present remote chunk must cause zero local attachment read, crypto, or upload
  work after resume.
- `lastSync` and remembered salt remain unchanged at checkpoint/failure and are
  committed exactly once after complete success.
- Progress after resume must account for already-complete work without moving
  backwards or sitting at zero during material Drive work.

#### C. Mid-run authentication and provider errors

- Use a fault-injecting Drive fake that can return 401/403/412/429/5xx at each
  remote operation, not only at sync startup.
- A single 401 must request a fresh token, reconnect without clearing valid ID
  caches, and retry the failed idempotent operation once.
- The refresh path must invalidate or bypass a cached token that Drive has just
  rejected; a mock returning the same token is a failing test, not a successful
  refresh.
- Concurrent 401s share one token-refresh promise rather than opening multiple
  authentication flows.
- A failed refresh ends the run as an authentication error with resumable remote
  work intact.
- 403 permission/quota errors are not mislabeled as checkpoints and are not
  retried as authentication failures.
- 412 precondition conflicts re-read and merge only where the protocol defines
  conditional updates.
- 408/429/5xx/network retries obey bounded exponential backoff, cancellation,
  jitter, and `Retry-After` where provided. Non-retryable errors stop without
  sleeping through all configured attempts.

The audit may conclude that mid-run token refresh is missing rather than merely
untested. If so, implement it behind one manager/provider credential-refresh
boundary and cover it before Phase 1.

#### D. Index publication, compaction, and multiple devices

- Add one integration harness with two independent managers/stores sharing a
  stateful in-memory Drive; do not mock the publication session itself.
- Interleave immutable delta creation, page publication, v3 snapshot creation,
  compatibility-index update, and covered-input deletion at every await point.
- Readers must observe the union of both devices' published entries throughout.
- A successful sync compacts even when fewer than 128 deltas exist; a checkpoint
  retains the 128-file upper bound without deleting needed inputs.
- Compaction is idempotent after crash/retry and never deletes an input before a
  durable replacement covers it.
- Verify exact coverage for both v2 deltas and prior v3 snapshots before
  deletion. If a listed input disappears during compaction, re-list once and
  rebuild from the authoritative surviving set.
- A compaction failure leaves sync success and resume correctness intact, while
  the next successful run can compact the backlog.
- Assert bounded hidden-index file count over many successful syncs and repeated
  two-device races, not only one finalization.

#### E. Request counts, chunk sizes, and progress truthfulness

- For a fixture with `A` generations, `C` missing chunks, and `P` pages, assert
  the planned bounds for listings, downloads, uploads, page publishes, index
  deltas, compatibility projection, and compaction.
- Record every Drive request in the fake and classify it into progress-visible
  work. The UI may show a named preparation/finalization phase, but long request
  sequences must not be invisible behind a frozen page-only bar.
- Assert new descriptors use exactly `12 * 1024 * 1024` plaintext bytes, including
  backup/cloud imports, while old descriptor chunk sizes remain authoritative.
- Assert sync never rewrites a generation or changes chunk size on resume.
- Include exact object-size assertions so a 1.2-MiB typo cannot satisfy a test
  that checks only chunk count or “greater than zero.”

#### F. Key, cancellation, and cleanup lifecycle

- Auto-lock aborts before key zeroization and no later queued callback can import
  or use the old key.
- Logout/provider disconnect aborts retries, Drive fetches, crypto, publication,
  and compaction without unhandled promise rejections.
- Cancellation at every publish boundary preserves already durable immutable
  work and does not update `lastSync`.
- Keep-awake/lifecycle cleanup is best-effort when Android activity disappears;
  a rejected cleanup/activation promise must not become an uncaught error.
- Completed and cancelled runs release queued chunks, request bodies, timers,
  subscriptions, and temporary trace data.

#### G. Import-to-sync compatibility

- Import the same generated journal through Web backup, native backup adapter,
  and cloud-import paths, then sync it through the real engine/Drive fake.
- Cover Web-produced AES sealed values on Android-compatible decrypt helpers and
  Android-produced values on Web-compatible helpers.
- A long cloud import refreshes a token after a page/attachment 401 and continues
  without redownloading completed pages.
- A successful import publishes metadata/page/attachment descriptors that sync
  can resume without migration, duplicate attachment generations, or chunk-size
  drift.
- File and cloud import must reopen the journal through a newly created store
  instance before reporting success. Inject partial page writes, duplicate
  writes, failed readback, and failed rollback; cloud import may not retain its
  current duplicate `saveJournal` plus `savePage` persistence pattern.

#### H. Shared storage and standards contracts

- Run one reusable `LocalStore` contract suite against native and Web adapters
  for page/attachment CRUD, stale encrypted flags, wrong keys, partial writes,
  rollback, transaction recovery, and write-barrier ordering.
- Exercise dynamic write-barrier dispatch with every mutating storage method so
  a newly added method cannot silently bypass serialization because of a method
  name string.
- Move or wrap browser-only renderer-ledger behavior behind a `.web.ts` adapter
  and prove native managers never instantiate it.
- Route all auth, import, sync, and diagnostic user-visible messages through
  i18n; add a dictionary-completeness test and UI assertions for error categories.
- Keep production diagnostics content-free and ensure trace/debug routes are
  excluded from release builds as required by 19.2.4.

### 5.4 Coverage policy for the risky seams

Run full coverage at the start and record per-file branch/function/line coverage
for all files changed by the sync recovery series, especially:

- `src/lib/sync/manager.ts`;
- `src/lib/sync/engine.ts`;
- `src/lib/sync/gdrive/api.ts` and `store.ts`;
- `src/lib/sync/renderer-work-ledger.ts`;
- `src/lib/storage/local.ts`, `local.web.ts`, and `write-barrier.ts`;
- `src/contexts/SyncManagerContext.tsx` and both Google auth providers;
- `src/components/journal/SyncModal.tsx`;
- backup/cloud-import crypto and retry boundaries.

Global near-99% coverage remains required, but it is not the Phase 0 success
metric. The additional gate is:

- every incident above has at least one cross-layer regression test;
- every outcome/error/cancellation branch in the manager and publication
  finalizer is exercised;
- component/app tests run in CI even where those files stay excluded from the
  percentage calculation;
- request-count and memory tests assert forbidden work, not only final values;
- no test passes solely because a broad mock bypasses the production boundary it
  claims to protect.

### 5.5 Phase 0 exit gate

Do not begin Workstream A until:

- the audit matrix is complete and its contradictions are resolved;
- the incident-derived tests fail for the intended broken behavior and pass on
  the corrected branch;
- any newly confirmed sync/auth/index/UI bug is fixed and manually smoke-tested;
- the two-device/stateful-Drive suite is green;
- targeted suites, full Jest/coverage, lint, typecheck, formatting, and hooks are
  green;
- one real-Drive smoke run proves fresh sync, interruption, approved restart
  boundary, resume, success compaction, and a second-device read.

Keep Phase 0 commits reviewable: land characterization tests first, then any
required sync fix, then coverage completion. Do not mix them with the native ZIP
module or page-catalog schema.

## 6. Workstream A — bounded native backup archives

### A1. Add an Android ZIP adapter

Create a local Expo native module backed by Android's platform `ZipFile` API.
Do not choose a third-party ZIP dependency merely to shorten implementation;
the adapter needs a narrow, testable surface and predictable streaming
behavior.

The module must:

- open the copied `file://` backup without transferring it to JavaScript;
- return a central-directory inventory containing canonical name, directory
  flag, compression method, compressed size, uncompressed size, and CRC;
- stream an entry through a fixed native buffer into a generated app-private
  temporary file;
- verify uncompressed byte count and CRC before reporting success;
- never use an archive entry name as an output path;
- support cancellation between native copy buffers;
- close `ZipFile`, input streams, and output streams in `finally` blocks.

The TypeScript native adapter will read the generated temporary file through
`FileHandle.readBytes()` in descriptor-sized chunks and delete it immediately
after the consumer finishes. JSZip remains behind the same interface for Web
and for unit-test fixtures; it is no longer used by Android import.

### A2. Validate the archive before extracting content

Build and validate one inventory before import:

- reject absolute paths, `..`, backslash traversal, NULs, duplicate canonical
  names, symlink-like entries, unsupported compression methods, negative or
  overflowing sizes, and malformed CRC metadata;
- require exactly one `manifest.json` and `journal.json`;
- cap manifest, settings, journal metadata, and individual page JSON entries at
  documented text-entry limits before reading them into JS;
- count pages and attachment entries from the inventory rather than repeatedly
  applying JSZip regular expressions;
- calculate total uncompressed bytes, largest temporary entry, and expected
  local encrypted-storage expansion;
- compare that estimate plus a safety reserve with `Paths.availableDiskSpace`;
- report insufficient storage before creating a journal ID or attachment root;
- validate that the selected file's size/mtime fingerprint did not change
  between inspection and password submission.

The disk estimator must derive framing/base64/encryption overhead from the
actual local formats and have unit tests. Do not use a guessed fixed multiple.

### A3. Refactor import around the archive interface

- Make `inspectBackup` read only the inventory and bounded manifest entry.
- Make `importJournal` reopen the inventory and process page entries
  sequentially.
- For an unencrypted attachment, extract one entry to a temp file and feed it to
  `saveAttachmentStream` in the descriptor's existing 12-MiB chunks.
- Refactor thumbnail import to accept a generic bounded stream or temporary URI
  instead of a `JSZipObject`. Preserve the 8-MiB source and 128-KiB output
  limits.
- Delete each extracted entry before advancing progress to the next attachment.
- Release all page JSON, attachment chunks, base64 strings, and native handles
  before yielding to the UI thread.
- Keep shared-attachment behavior: each owning page receives its own immutable
  local generation.

For encrypted v1 entries:

- inspect the central-directory size before extraction;
- keep the current safe whole-entry limit;
- reject an unsafe attachment before any journal writes, with a localized
  explanation that this legacy encrypted backup contains an attachment too
  large for the device;
- keep wrong-password and authentication failures fatal rather than converting
  them to attachment warnings.

### A4. Make the import transaction process-death safe

Introduce a durable import marker under a dedicated app-private import root.
It records only generated IDs, paths, expected counts, and phase; it never
contains plaintext, password keys, or attachment data.

Phases:

1. `prepared`: preflight passed, but nothing is visible in `journals.json`;
2. `writing`: page/attachment/catalog files may exist under the generated
   journal directory;
3. `publishing`: all staged content and the encrypted catalog were verified;
4. `committed`: the journal index entry is durable.

Startup recovery rules:

- `prepared` or `writing`: delete the incomplete journal root and temp entries;
- `publishing`: replay the idempotent index publication if all expected files
  and catalog checks are valid, otherwise roll back;
- `committed`: remove only the marker and stale temp directory;
- unknown/corrupt marker: do not publish; remove the generated import root after
  confirming it is not referenced by the journal index.

Replace the final full `getJournal` verification pass with incremental durable
verification while writing plus a final metadata/catalog/page-count check. The
transaction must preserve the guarantee from 19.2.1 without rereading and
decrypting every page after import.

## 7. Workstream B — encrypted journal page catalog

### B1. Define a rebuildable catalog

Add one encrypted `page-catalog.json` per native journal and one equivalent IDB
record on Web. Version the payload independently from the Canto data schema.

`PageCatalogV1` contains:

- journal ID and catalog schema version;
- one `ListPagePreview` per page, including deleted pages needed by sync/local
  consistency checks;
- normalized tag union for active pages;
- latest page modification timestamp;
- page count and a deterministic digest of page IDs/revisions;
- enough date data to derive anniversary and month summaries;
- no attachment bytes, encryption keys, or full comments/files/images arrays.

The preview projection must come from one shared pure function. Journal list,
filter search, tags, and calendar must have behavior identical to projections
computed from full pages today.

The catalog uses the same device-encryption and optional journal-password layer
as page metadata. Secure journal text, tags, dates, and thumbnail data must not
become readable before unlock.

### B2. Keep page and catalog commits atomic

Page files remain authoritative, but every mutation must update the catalog in
the same recoverable commit:

- create page;
- edit/save page;
- soft delete page;
- sync download or conflict resolution;
- backup import;
- cloud import;
- password and device-key rotation.

On native, extend the existing staged-file transaction mechanism to stage the
new page ciphertext and catalog ciphertext, write one commit marker, and replay
both together after a crash. On Web, use one IndexedDB read-write transaction.
Catalog construction and writes must pass through the device-key write barrier.

Do not let screens update the catalog directly. The repository derives the
preview from the exact `Page` value it commits.

### B3. Separate metadata writes from full journal writes

The current `saveJournal` documentation says “metadata and settings,” but its
implementation rewrites every page. Split the use cases:

- metadata/settings update: metadata plus top-level journal index only;
- page commit: page plus catalog;
- new/full journal import: metadata, pages, catalog, then index publication;
- complete journal read: retained for sync/export/rotation and clearly named as
  a heavyweight batch operation;
- overview read: metadata plus catalog only.

Update settings, title/icon changes, theme changes, and sync-provider setup to
use the metadata path. Password rotation remains a deliberate full-data
operation with progress and its existing transaction guarantees.

### B4. Migrate existing journals lazily and visibly

- Never scan all journals during app startup.
- If a journal has no catalog, build it once when that journal is first opened.
- Show an “Optimizing journal…” state with page-count progress; do not present an
  indefinite spinner.
- Write the rebuilt catalog transactionally and then use it for that same open.
- If a catalog is missing, corrupt, has an unsupported version, or fails its
  digest validation, discard and rebuild it from page files.
- A journal imported by 0.19.2.5 receives its catalog during import, so its first
  open does not pay migration cost.
- Cancellation leaves the old pages intact and no catalog published.

Add development-only counters for metadata reads, catalog reads, page reads,
decryptions, and rebuilds. These counters are test seams and diagnostic tools,
not production console noise.

## 8. Workstream C — fast journal and page opening

### C1. Replace `useJournal` on read-oriented screens

Introduce `useJournalOverview` with:

- one in-flight request per journal/key identity;
- cancellation or stale-result suppression on navigation/key change;
- explicit `initial`, `migrating`, `ready`, and `error` states;
- repository invalidation after page or metadata commits;
- no automatic second read merely because React dependencies changed.

Use it in `JournalScreen` and the calendar. Derive sorted pages, filters, tags,
anniversaries, latest-modified, and unsynced indicators from catalog previews.

The page screen must obtain tag suggestions from the catalog instead of
`useJournalTags -> getJournal`. Loading a single page and its images must not
compete with a 351-page tag scan.

### C2. Correct focus and explicit full-data workflows

- Remove the unconditional `refresh()` on initial focus.
- Refresh the overview only on a real return transition or repository
  invalidation, using a stable callback independent of journal/page arrays.
- Preserve the existing rule that automatic sync waits until initial visible
  thumbnail work has entered its loader.
- Calculate auto-sync dirtiness from catalog `latestModified`, not a full page
  array.
- Let `SyncEngine` perform its own full immutable read only after sync starts.
- Move export's full-journal load into the export modal and show progress.
- Load full pages for password rotation only after the user confirms the
  operation.
- Update `JournalSettings` to use catalog page count and metadata-only saves.

### C3. Keep list rendering bounded

The journal screen already paginates previews, but it sets
`initialNumToRender={visiblePages.length}`. Keep the first page of 15 bounded,
and add explicit Android `maxToRenderPerBatch`, `windowSize`, and
`removeClippedSubviews` values validated on device. Do not preload attachment
originals from list items.

## 9. Workstream D — virtualized calendar

Replace the calendar `ScrollView` and eager `months.map` with a vertical
`FlatList`:

- data is the lightweight month summary derived from catalog previews;
- `AnniversaryRow` is the list header;
- configure a small `initialNumToRender`, `maxToRenderPerBatch`, and `windowSize`;
- enable `removeClippedSubviews` on Android after visual regression testing;
- memoize month rows and stable callbacks so scroll-state updates do not rerender
  every month;
- preserve the Web max-width card behavior.

Replace raw pixel-only restoration with a stable anchor containing month key and
relative offset. Restore with `scrollToIndex`/`scrollToOffset` and handle
`onScrollToIndexFailed`. A catalog rebuild or newly added month must not send
the user to an unrelated year.

Do not add a second persisted calendar index initially. For 351 lightweight
previews, the O(P) month reduction should be negligible once filesystem and
crypto work is removed. Add a precomputed month summary only if physical-device
profiling shows the pure reduction itself exceeds the budget.

## 10. Workstream E — automatic, bounded page images

### E1. Add an attachment display service

Move display materialization out of `app/page/[id].tsx` and the generic
base64-returning `getAttachment` path.

Native behavior:

- create one opaque file in an app-private cache namespace;
- for chunked content, read, device-decrypt, password-decrypt, validate, and
  base64-decode one stored chunk at a time;
- append decoded bytes with `FileHandle.writeBytes()`;
- check cancellation between chunks and before publishing the URI;
- atomically publish a lease only after expected byte length and chunk count
  validate;
- delete incomplete output on any error;
- never keep a `string[]` of decoded chunks or join the full attachment;
- retain a measured guard for legacy monolithic attachment values.

Web behavior may use a Blob/Object URL, but it must revoke the URL when the lease
is released. The public display contract is URI-based on both platforms.

### E2. Define cache ownership and security

- One service owns all materialized files and reference counts leases by
  attachment generation.
- Repeated use of the same generation in one unlocked session reuses the same
  completed file.
- Password-encrypted image files are deleted on page unmount, journal lock,
  logout/key clear, and app background according to the existing lock policy.
- Unencrypted display files may use a size-bounded LRU, but never unbounded
  random filenames.
- Startup removes stale/incomplete display files left by crashes.
- File names are opaque and reveal neither journal titles nor attachment names.
- Cache eviction never deletes source attachment generations.

### E3. Change carousel scheduling and UX

- Queue all active page images automatically after the initial navigation
  interaction.
- Use one shared Android semaphore across plain and encrypted carousels so two
  groups cannot materialize large images concurrently.
- Show the persisted thumbnail for the first image while its original loads.
- Show a spinner/skeleton for every other queued image.
- Reprioritize the visible image when horizontal scroll changes.
- Continue serially until all active images are loaded or individually failed.
- Display a localized retry action for a failed image without blocking the rest
  of the queue.
- Map viewer indexes by attachment ID among loaded images; do not use the raw
  carousel index against a filtered loaded-image array.
- Abort queued and active work on unmount and release every acquired lease.

Remove `canGenerateThumbnailFromAttachment` from page-carousel decisions but
retain it for list-thumbnail generation.

- Preserve wrong-password, schema validation, name conflict, attachment warning,

  `pageToListPreview` across dates, tags, text, location, comments, deleted

- Test catalog creation during backup/cloud import and sync downloads.
- Test metadata-only updates perform zero page writes.
- Test absent/corrupt/version-mismatched catalogs rebuild once and persist.
- Test secure catalog data cannot be read with a missing/wrong key.

### 10.3 Screen tests

- Journal initial focus performs one overview request and no duplicate refresh.
- Returning from a page refreshes only after an actual mutation/invalidation.
- Opening a page requests one page and one catalog, not a full journal.

### 10.4 Image tests

  retry, cancellation, stale completion suppression, and unmount cleanup.
- Instrument the materializer to prove it never retains more than one chunk and
  never calls full `getAttachment` for chunked content.
- Test lease reuse, reference counting, encrypted-cache purge, LRU bounds,

### 10.5 Physical Android release matrix

Run on the reporting device and at least one representative 4–6-GB-RAM Android

## 12. Performance and memory gates

The baseline device measurements collected after the mandatory sync audit
become part of the release evidence. The following gates are minimum targets:

| Flow              | Release gate                                                                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Backup inspection | No whole-file JS allocation; manifest visible within 2 s after picker copy completes                                                                   |
| 224-MB import     | Completes without OOM/process death; peak JS working set is independent of total archive size and bounded by one attachment chunk plus crypto overhead |
| Import cleanup    | Zero temp/import-marker leftovers after success, failure, cancel, and restart recovery                                                                 |
| Warm journal open | Journal shell and first 15 previews visible within 2 s; exactly metadata + catalog reads; zero page reads                                              |
| First legacy open | Visible migration progress; one page scan only; subsequent open meets warm gate                                                                        |

| Calendar open     | First month window interactive within 2 s from an open journal; zero page reads                                                                        |
| Page images       | Thumbnail/placeholder immediate; every image starts automatically; one materialization active on Android                                               |

For memory, record both JS heap and process PSS/RSS. Passing because V8/Hermes
heap is flat while native memory grows is not sufficient. The implementation
must demonstrate that increasing total archive/image size increases elapsed
streaming work and final storage, not the peak number of simultaneously retained
payload bytes.

All normal hooks must pass. Coverage must remain at the branch/main standard:
`npm run test:ci` may not reduce global line, statement, function, or branch
coverage and should remain near 99%. Typecheck, lint, formatting, and

reload. `sessionStorage` intentionally retains the renderer safety stop across
reloads; a new tab/session may resume durable immutable work. The manager,
ledger, SyncModal wording, and lifecycle tests now agree on this.
