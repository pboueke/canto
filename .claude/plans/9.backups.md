# Plan: Journal Export & Import (Requirement 9)

## Overview

Add per-journal backup functionality: export a journal as a portable `.zip` file (with optional encryption using the journal's password), and import a previously exported journal during journal creation.

**Library:** `jszip` (pure JS, compatible with managed Expo workflow — no prebuild needed)

---

## Phase 1: Export Infrastructure

### 1.1 Install `jszip`

```bash
npm install jszip --legacy-peer-deps
```

### 1.2 Create `src/lib/backup/export.ts`

Export service that builds a ZIP from a journal:

```
exportJournal(journalId, derivedKey?, encrypted: boolean) → Uint8Array (ZIP)
```

**ZIP structure (portable, readable JSON):**

```
canto-export/
├── manifest.json          # { version: 1, appVersion, exportDate, encrypted, journalId }
├── journal.json           # Journal metadata (decrypted)
├── settings.json          # JournalSettings
├── pages/
│   ├── {pageId}.json      # Decrypted page content (each page)
│   └── ...
└── attachments/
    ├── {original-filename} # Decrypted binary attachments
    └── ...
```

**When `encrypted: true`:**

- The manifest stays plaintext (so import can detect encryption)
- `manifest.json` includes `encrypted: true`, `salt`, `kdfIterations`
- All other files are AES-256-GCM encrypted using the journal's password-derived key
- Ciphertext format: same base64([nonce][ciphertext][tag]) used internally
- Attachment references in pages are rewritten to use portable filenames

**When `encrypted: false`:**

- Everything is plaintext JSON / raw binary
- `manifest.json` includes `encrypted: false`
- Usable as a human-readable archive

**Steps:**

1. Load journal via `LocalStore.getJournal(id, derivedKey)`
2. For each page, load full content
3. For each attachment, load via `LocalStore.getAttachment()`
4. If encrypted export: re-encrypt each file with password-derived key (no device layer)
5. If unencrypted: write plaintext
6. Build ZIP with `jszip`, return as Uint8Array
7. Write to cache directory, share via `expo-sharing`

### 1.3 Create `src/lib/backup/import.ts`

Import service that reads a ZIP and creates a new journal:

```
importJournal(zipUri: string, derivedKey?: Uint8Array) → { journal, needsPassword }
```

**Steps:**

1. Read ZIP from URI via `expo-file-system`
2. Parse `manifest.json` to check version and encryption status
3. If encrypted and no key provided, return `{ needsPassword: true }`
4. Deserialize journal metadata → assign new UUID
5. Deserialize each page → assign new UUIDs, remap attachment references
6. Save each attachment via `LocalStore.saveAttachment()` (re-encrypts with device key)
7. Save journal via `LocalStore.saveJournal()`
8. Return created journal

### 1.4 Create `src/lib/backup/index.ts`

Public exports for both services.

## Phase 3: Import UI

### 3.1 Update `NewJournalModal.tsx`

Add a new section at the bottom of the modal (after theme picker, before create button):

- Divider with "OR"
- **"Import from Backup"** button
- Tapping it opens a document picker (`expo-document-picker`) to select a `.zip` file
- After selection:
  - Parse manifest
  - If encrypted: show password prompt
  - Derive key, attempt import
  - If journal name conflicts with existing: show rename dialog
  - On success: close modal, navigate to new journal

### 3.2 Name conflict handling

- After parsing the journal name from the ZIP, check against existing journals
- If conflict found: show alert with options:
  - Rename (pre-filled with "{name} (copy)" or "{name} (2)")
  - The user can edit the name freely
- Re-importing the same journal always creates a new copy (new UUID), so multiple imports are always allowed

## Edge Cases & Considerations

1. **Large journals** — `jszip` works in memory; for very large journals (hundreds of MB of attachments), memory could be an issue. Acceptable for v1 since most journals are text-heavy.
2. **Soft-deleted pages/attachments** — Excluded from export (only active content exported).
3. **Attachment deduplication** — If two pages reference the same attachment file, it's included once in the ZIP with a mapping in manifest.
4. **Password-protected journal without active session** — Export button should require the journal to be unlocked (derivedKey available). This is naturally enforced since you can't view the journal without unlocking it.
5. **File extension** — Export as `.canto.zip` for easy identification, standard ZIP internally.
6. **Import validation** — Check manifest version, required files present, JSON parseable before committing any writes.
