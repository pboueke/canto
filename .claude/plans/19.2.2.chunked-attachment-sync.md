# Plan 19.2.2 — bounded-memory chunked attachments and Drive sync

**Status:** Partially implemented in unreleased v0.19.2

## User decision

- Install published `canto-data@1.1.0` (already resolved locally).
- New attachments and newly imported attachments use the published
  `Attachment.content` descriptor and chunked storage.
- Existing descriptor-absent attachments remain readable/exportable, but an
  oversized legacy attachment is **not** sent through the old whole-value sync
  path. Sync returns a localized per-file warning instead of risking OOM.
- Do not automatically migrate a legacy large attachment: its current
  whole-file AES-GCM representation cannot be converted without materializing
  the very payload that caused the crash.

## Goal

Make attachment sync have a fixed upper memory bound per active chunk on native
and web, rather than a bound proportional to an attachment’s total size. New
and imported content uses `canto-chunked-v1`; existing large monolithic content
fails safe with an actionable result.

## Non-goals

- Do not reinterpret or replace flat `.canto.zip` v1. Keep import/export
  compatibility; streaming ZIP is a separate project.
- Do not convert old large monolithic local/remote payloads in place.
- Do not expose provider paths, chunk names, encryption keys, or per-chunk
  storage implementation to UI callers.
- Do not change the current password-encryption exception result copy except to
  add the separate localized legacy-sync warning.

## Fixed protocol

### Descriptor and chunk size

Use the published descriptor exactly:

```ts
content: {
  format: 'canto-chunked-v1',
  byteLength,
  chunkSize: 512 * 1024,
  chunkCount,
}
```

`Attachment.path` is a storage root, derived from journal/page/attachment IDs.
It must be unique even for equal filenames on the same page. A chunk is indexed
`0..chunkCount - 1`; no array of remote/local paths is stored in page metadata.

### Content frame and encryption

Create one internal **attachment-content module** behind `LocalStore`. Its
interface receives an attachment reference, keys, and a byte source/sink; its
implementation owns chunk naming, framing, crypto layering, incomplete-write
cleanup, and legacy detection. Callers must not enumerate chunk filenames.

For each chunk, encode an authenticated frame containing a format marker,
journal ID, page ID, attachment ID, chunk index, total chunk count, and raw
payload bytes. Then apply the existing layers independently per frame:

1. optional journal-password AES-GCM (inner),
2. mandatory device AES-GCM (outer),
3. independent sync AES-GCM when travelling to Drive.

On every read, decrypt and validate the frame identity/index/count before
returning payload bytes. This rejects reordered/substituted chunks even though
AES-GCM is independently valid for each chunk. No keys, nonce values, or
provider IDs enter the descriptor.

### Atomicity and fallback

- Write chunks under a temporary root; write/publish the final root only after
  all chunks succeed. On failure/cancellation, remove the temporary artifacts.
- Persist the page (and therefore descriptor) only after final root publication.
- Content absent means legacy: use the exact existing monolithic reader.
- A chunked read with any missing/corrupt frame fails with attachment and chunk
  context; it never falls back to a different chunk or treats it as legacy.

## Implementation sequence

### 1. Dependency and small interfaces

1. Keep `package.json` / `package-lock.json` on `canto-data@^1.1.0`; normalize
   the lockfile so the dependency update does not carry unrelated `dev` →
   `devOptional` churn from the local npm version.
2. Extend `LocalStore` additively with an internal/use-by-sync attachment-content
   interface: chunk reader/writer, storage-size lookup, delete, password
   re-encryption, and device-key rotation methods that receive an `Attachment`.
   Keep legacy `saveAttachment(path, base64)`/`getAttachment(path)` behavior for
   UI and flat v1 backup code during the migration.
3. Extend `RemoteStore` additively with cancellation-aware descriptor/chunk
   upload/download methods. Keep old string methods for remote legacy fallback.
4. Thread `AbortSignal` through `RemoteStore`, Drive transport, and retry sleep;
   pass it to `fetch`.

### 2. Deep local storage adapters

1. Add the shared chunk framing/encryption module plus focused unit tests for
   framing, identity validation, ordering, missing chunks, cancellation, and
   cleanup.
2. Native: use Expo File byte/stream APIs to read/write individual chunk files;
   never call `File.text()`/base64 conversion for a new sync chunk.
3. Web: store chunk ciphertext as `ArrayBuffer`/`Blob` records in IndexedDB;
   retain the resilient 60-second attachment read logic for legacy records.
4. Update page/journal cleanup, password re-encryption, and device-key rotation
   to enumerate a chunk root via the module. New large chunked password changes
   must no longer hit the 32 MiB skip path; preserve the prior skip/result
   behavior only for oversize legacy data.
5. Add a stream/file ingestion path for image, camera, and file picker values so
   new large assets are chunked before they become a full base64 data URL. Keep
   the existing base64 entry point only for small/legacy caller compatibility.
6. New flat ZIP imports write into the chunked store (the ZIP parser remains
   flat/in-memory by design for this release); importer creates the descriptor
   only after a successful chunk write.

### 3. Bounded Drive transport and sync

1. Store each new remote chunk as a deterministic attachment-ID/index Drive
   object under the existing journal attachments folder. The encrypted page
   metadata carries the descriptor; upload all chunks before uploading that page.
2. Make Drive request bodies and response reads at most one encoded chunk. A
   512 KiB plaintext chunk may briefly be base64/multipart encoded, but an
   80 MiB attachment must never exist as one JS string at this seam.
3. Upload/download at most two chunks across the journal (byte-bounded queue,
   not two whole attachments). Retry only retryable network/408/429/5xx errors
   with jitter/Retry-After; cancel immediately through `fetch` and retry waits.
4. Preserve existing basename-based one-object Drive download/upload for
   descriptor-absent legacy attachments that are below the safe legacy limit.
5. Before old-string sync, obtain stored byte size without reading content. If
   an attachment is descriptor-absent and exceeds the safe limit, skip it,
   record its name/page/size in a `SyncWarning`, do not update that page’s
   remote modified/index value, and display a localized warning. This makes the
   retry safe and avoids silently claiming that the file was synced.
6. Reuse the shared attachment downloader in cloud journal import and replace
   its unbounded per-page `Promise.allSettled` handling with the same bounded
   queue.

### 4. UI, previews, backup, and compatibility

1. Keep existing UI image display/download compatibility by having the storage
   module reassemble only when the user explicitly opens one attachment. List
   previews must prefer existing thumbnails and avoid loading a full chunked
   file when none exists.
2. Keep flat v1 backup export/import behavior. Export reassembles a selected
   chunked attachment into the existing one-entry ZIP payload; the
   `canto-data` helper strips `content` after rewriting to the ZIP path.
3. Do not change the v1 manifest or path parser. Add direct regression tests for
   legacy unencrypted/encrypted archives and chunked-local → flat-v1 export →
   fresh chunked import.
4. Add localized `SyncWarning` result text to every supported dictionary and
   surface each deferred legacy file with its formatted size in SyncModal.

### 5. Tests and validation

Add native/web storage tests for chunk order, corruption, partial-write cleanup,
delete, re-encryption, device rotation, same-name attachments, and descriptor-
absent compatibility. Add sync/Drive tests for a multi-chunk encrypted round
trip, cancellation during fetch/retry, partial remote upload, legacy fallback,
and oversized legacy warning. Add cross-platform and simulated web E2E coverage
for a multi-chunk attachment, a flat v1 backup round trip, and a password change
on a chunked 80 MiB-equivalent fixture without whole-value encoder calls.

Run at minimum:

```bash
npm run format:check
npm run lint
npm run typecheck
npm test -- --runInBand
make check
```

Also run an Android physical-device test that creates/syncs a chunked attachment
larger than the old failure size, then inspect `adb logcat` for OOM/Fatal errors.

## Current v0.19.2 implementation

The initial safety slice now has a descriptor-aware chunk path:

1. image picker and file picker ingest browser `File` slices and native Expo
   `FileHandle.readBytes` values in fixed 512 KiB reads before attaching a
   `canto-chunked-v1` descriptor; flat backup imports also attach the descriptor.
   Native and web LocalStore persist independently device-encrypted chunks plus
   a device-encrypted manifest;
2. each chunk contains the authenticated identity frame before optional journal
   password encryption, and reader validation rejects a substituted/missing chunk;
3. SyncEngine transfers only one independently sync-encrypted chunk at a time and
   uploads the page only after every chunk succeeds; Google Drive uses stable
   attachment-ID/index names and forwards cancellation to the chunk request;
4. local delete, password re-encryption, and device-key rotation traverse chunk
   roots; reading/exporting an attachment reassembles only on that explicit path;
5. descriptor-absent legacy content above 512 KiB (or with unknown size) is deferred
   with the existing per-file sync warning rather than entering the whole-value path.

## Deliberate residuals

Flat-v1 ZIP parsing remains JSZip/base64 compatibility code and can materialize an
archive entry before handing it to chunked storage. This is an existing archive-format
limitation and is not used by image, camera, or file picker intake: those sources use
bounded browser `Blob.slice` reads or native Expo `FileHandle.readBytes` calls. A
physical-device memory profile remains required before release.

## Acceptance criteria

- `canto-data@1.1.0` is installed and used by new attachment metadata.
- Every new or imported attachment above the chunk threshold is stored and
  synced as independently authenticated chunks; no sync operation allocates a
  complete attachment base64/ciphertext/multipart string.
- An existing oversized descriptor-absent attachment is never sent to legacy
  sync; users receive a localized, per-file warning and its page remains dirty.
- Legacy small attachments, flat v1 backup archives, current remote basename
  objects, password behavior, and cross-platform sync continue to work.
- Cancellation/retry does not publish a descriptor/page before all chunks
  succeed, and partial artifacts are recoverable/cleaned up.
- The targeted suites, full repository suite, type/lint/format gates, and
  Android device smoke test pass.
