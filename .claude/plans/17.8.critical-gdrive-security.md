# 17.8 Critical: GDrive Sync Encryption

## Problem

Password-protected diary entries are stored as **plain text** on Google Drive. The sync flow fully decrypts data locally (stripping both device and password encryption layers) before uploading raw JSON to GDrive. Non-secure journals are also uploaded as plain text with no protection.

### Root Cause

`SyncEngine.sync()` calls `local.getJournal(id, derivedKey)` which returns fully-decrypted plaintext. This plaintext is passed directly to `remote.uploadJournalMeta()` and `remote.uploadPage()`, which serialize as plain JSON.

### Current Flow (broken)

```
Upload: local (encrypted) → getJournal(derivedKey) → plaintext → uploadPage(JSON.stringify) → GDrive (PLAIN TEXT)
Download: GDrive (PLAIN TEXT) → downloadPage(JSON.parse) → plaintext → savePage(derivedKey) → local (encrypted)
```

## Solution

Encrypt all journal content at the **SyncEngine level** before passing to RemoteStore. Every journal gets a "sync key" derived from its salt. For password-protected journals, the sync key is the existing `derivedKey` (password + salt). For non-secure journals, a key is derived from salt alone (empty password), providing protection against passive GDrive scraping.

### Key Insight: Salt Already Exists on All Journals

`useCreateJournal` already generates a salt for every journal and calls `deriveAndCache(journalId, input.password || '', salt, iterations)`. The infrastructure for deriving keys from empty passwords already exists — it just isn't used during sync for non-secure journals.

### Target Flow

```
Upload: plaintext → AES-GCM encrypt (syncKey) → ciphertext → uploadPage → GDrive (ENCRYPTED)
Download: GDrive (ENCRYPTED) → downloadPage → ciphertext → AES-GCM decrypt (syncKey) → plaintext
```

### What Stays Unencrypted on GDrive

- **Registry** (`canto-journals.json` in appDataFolder): `{ id, title, encrypted, salt }` — needed for sync discovery and key derivation
- **Timestamp index** (`index.json` per journal): `{ [pageId]: { modified, deleted } }` — needed for sync comparison without decrypting every page (see Phase 2)
- **File names**: page IDs as filenames (`{pageId}.json`) — needed for file-level sync
- **Folder structure**: `Canto/{journalId}/pages/`, `Canto/{journalId}/attachments/`

### What Gets Encrypted

- `meta.json` content (journal settings, icon, theme, etc.)
- All page content (`pages/{pageId}.json`)
- All attachments (`attachments/*`)

### Timestamp Index

Currently `downloadJournalMeta` eagerly fetches and parses ALL remote pages to build a page map for timestamp comparison. With encryption, this would mean decrypting every page on every sync just to check `modified` and `deleted` — wasteful and slow for large journals.

Instead, introduce a lightweight **unencrypted timestamp index** stored alongside each journal on GDrive:

```
Canto/{journalId}/index.json
```

Format:

```typescript
interface SyncIndex {
  [pageId: string]: { modified: number; deleted?: boolean };
}
```

**Tradeoffs**: This leaks page IDs, page count, modification timestamps, and deletion status — but NOT content. This is acceptable because:

- Page IDs are UUIDs (no semantic meaning)
- Timestamps reveal access patterns but not content
- The alternative (decrypt all pages on every sync) adds O(N) decryption for every sync cycle
- GDrive already leaks file counts and modification times via its own metadata

The engine writes the index on every upload and reads it for comparison. Only pages that actually need syncing get fetched and decrypted.

## Implementation

### Phase 1: SyncEngine Encryption Layer

**File: `src/lib/sync/engine.ts`**

Add encrypt/decrypt helpers that wrap `aesGcmEncrypt`/`aesGcmDecrypt` from `@/lib/encryption/utils`. The `syncKey` parameter (renamed from `derivedKey`) becomes **required** for all journals (not just secure ones).

The engine is responsible for all encryption/decryption. The remote store is a dumb transport layer that accepts/returns opaque strings. See Phase 2 for the detailed upload/download flow.

**Attachment handling**:

- Upload: `local.getAttachment(path)` → `aesGcmEncrypt(data, syncKey)` → `remote.uploadAttachment()`
- Download: `remote.downloadAttachment()` → `aesGcmDecrypt(data, syncKey)` → `local.saveAttachment()`

### Phase 2: Modify RemoteStore Interface + Add Timestamp Index

**Files: `src/lib/sync/types.ts`, `src/lib/sync/gdrive/store.ts`**

The `uploadJournalMeta` method currently destructures `JournalContent` to extract metadata fields. Since the engine will now pass pre-encrypted data, we need to change the engine-to-store interface:

- Encrypted metadata string (not a `JournalContent` object) + journal id/title/salt for registry
- Encrypted page string + page id for filename
- Timestamp index: plain JSON with `{ [pageId]: { modified, deleted? } }`

New type and updated `RemoteStore` interface in `src/lib/sync/types.ts`:

```typescript
/** Lightweight sync index — stored unencrypted on remote for O(1) comparison. */
export interface SyncIndex {
  [pageId: string]: { modified: number; deleted?: boolean };
}

// Current → Updated:

uploadJournalMeta(journal: JournalContent): Promise<void>;
// →
uploadJournalMeta(journalId: string, encryptedMeta: string, registry: { title: string; encrypted: boolean; salt?: string }): Promise<void>;

uploadPage(journalId: string, page: Page): Promise<void>;
// →
uploadPage(journalId: string, pageId: string, encryptedContent: string): Promise<void>;

// NEW: timestamp index read/write
uploadSyncIndex(journalId: string, index: SyncIndex): Promise<void>;
downloadSyncIndex(journalId: string): Promise<SyncIndex | null>;

// downloadJournalMeta no longer fetches pages — only encrypted meta.json:
downloadJournalMeta(journalId: string): Promise<string | null>;
// (was: Promise<DownloadResult | null>)

// downloadPage already returns raw content, just change return to opaque string:
downloadPage(journalId: string, pageId: string): Promise<string | null>;
```

This separates the "what to store" (encrypted blobs) from "how to organize" (registry, index, file naming).

**GDrive implementation** (`store.ts`):

- `uploadSyncIndex`: upserts `index.json` in the journal folder with `JSON.stringify(index)`
- `downloadSyncIndex`: reads `index.json`, parses with `safeJsonParse`
- `downloadJournalMeta`: simplified — returns raw `meta.json` content string (no page fetching)
- `uploadJournalMeta`: writes encrypted string to `meta.json`, updates registry with plain metadata
- `uploadPage`: writes encrypted string to `{pageId}.json`

**Engine sync flow change** (Phase 1 + 2 combined):

```
UPLOAD:
  1. local.getJournal(id, derivedKey) → plaintext JournalContent
  2. Encrypt meta: aesGcmEncrypt(JSON.stringify(metaWithoutPages), syncKey)
  3. remote.uploadJournalMeta(id, encryptedMeta, { title, encrypted, salt })
  4. For each page to upload:
     a. aesGcmEncrypt(JSON.stringify(page), syncKey) → remote.uploadPage(id, pageId, ciphertext)
  5. Build SyncIndex from all local pages { [pageId]: { modified, deleted } }
  6. remote.uploadSyncIndex(journalId, index)

DOWNLOAD (comparison phase):
  1. remote.downloadSyncIndex(journalId) → SyncIndex (plain JSON, no decryption)
  2. Compare local pages vs remote index by pageId/modified/deleted
  3. Only fetch pages that need syncing:
     remote.downloadPage(id, pageId) → ciphertext → aesGcmDecrypt → JSON.parse → Page

DOWNLOAD (metadata):
  1. remote.downloadJournalMeta(id) → encrypted string
  2. aesGcmDecrypt(ciphertext, syncKey) → JSON.parse → journal metadata
```

This eliminates the current pattern of eagerly fetching all remote pages on every sync. Only changed pages get downloaded and decrypted.

### Phase 3: Ensure All Journals Have Sync Keys

**File: `src/contexts/JournalKeyContext.tsx`** and callers

The key context already derives keys for non-secure journals using empty password. Verify that:

1. `deriveAndCache` is called for ALL journals on open (not just secure ones)
2. The key is available when sync triggers

**File: `src/components/journal/SyncModal.tsx`**

Currently passes `derivedKey ?? undefined` to `syncJournal`. After this change, a key must always be available. Check all sync call sites:

- `SyncModal.handleEnableSync` / `handleSyncNow`
- `useSyncManager` auto-sync triggers
- Any background sync scheduling

If the key isn't cached (e.g., after auto-lock cleared it), the engine must re-derive it from the journal's salt before syncing. For non-secure journals this can happen transparently (empty password + salt). For secure journals, sync must be deferred until the user unlocks.

### Phase 4: Update Existing Tests

**File: `src/lib/__tests__/gdrive-sync-e2e.test.ts`**

Update all tests to pass a `syncKey` and verify that:

1. Data uploaded to GDrive is encrypted (not plain JSON)
2. Data downloaded from GDrive is decrypted correctly
3. The sync key round-trips: encrypt → upload → download → decrypt matches original

**File: `src/lib/__tests__/helpers/sync-test-helpers.ts`**

Update `makeJournal` to always include a salt. Add helper for generating test sync keys.

### Phase 5: New Tests

Add dedicated encryption-focused sync tests:

1. **Encrypted upload verification**: Sync a journal, inspect what was written to GDrive (via InMemoryDrive), verify it's not parseable JSON (it's base64 ciphertext)
2. **Encrypted round-trip**: Upload encrypted → download → decrypt → verify content matches
3. **Wrong key rejection**: Download with wrong key → AES-GCM auth fails → error
4. **Non-secure journal encryption**: Journal without password still gets encrypted on GDrive using salt-derived key
5. **Attachment encryption**: Verify attachments are encrypted before upload
6. **Mixed sync**: One device uploads encrypted, another device downloads and decrypts correctly (same salt/password)
7. **Sync index accuracy**: After upload, `index.json` contains correct `{ modified, deleted }` for every page
8. **Sync index comparison**: Engine only downloads pages where remote index shows newer `modified` — verify no unnecessary `downloadPage` calls
9. **Sync index missing**: First sync against a remote with no `index.json` gracefully handles null (treat as empty remote)
