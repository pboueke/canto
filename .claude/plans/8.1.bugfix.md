# Bugfix 0.8.1: Always derive encryption key

## Problem

When a user creates a journal without setting a password, no salt is generated and no PBKDF2 key is derived. This means `derivedKey` stays `undefined` throughout the journal's lifecycle, and all data (metadata, pages, attachments) is stored with only device-level AES-256-GCM encryption — no password-layer encryption.

The goal: **always** derive a key from password + salt (using empty string `""` as password when none is set), so every journal always has two encryption layers.

## Root cause

In `src/hooks/useStorage.ts` (`useCreateJournal`), lines 206-217:

```typescript
const hasPassword = !!input.password;
if (hasPassword && input.password) {
  const saltBytes = encryption.generateSalt();
  salt = uint8ToBase64(saltBytes);
  if (deriveAndCache) {
    derivedKey = await deriveAndCache(journalId, input.password, salt);
  }
}
```

When `input.password` is falsy (empty/undefined), the entire block is skipped: no salt, no key.

## Changes

### 1. `src/hooks/useStorage.ts` — `useCreateJournal`

**Always generate salt and derive key.** Replace the conditional block:

```typescript
const saltBytes = encryption.generateSalt();
const salt = uint8ToBase64(saltBytes);
const password = input.password || '';
let derivedKey: Uint8Array | undefined;
if (deriveAndCache) {
  derivedKey = await deriveAndCache(journalId, password, salt);
}
```

Keep `secure: !!input.password` — the `secure` flag means "user set a password" (controls whether the UI shows a password prompt). Salt is now always present.

### 2. `app/index.tsx` — `handleJournalPress`

For non-secure journals (no user password), auto-derive the key from empty string before navigating:

```typescript
async function handleJournalPress(journal: Journal) {
  if (journal.biometric) {
    const success = await authenticateBiometric(t.home.biometricReason);
    if (!success) return;
  }

  if (journal.secure && !getKey(journal.id)) {
    // User-set password — show password modal
    setAccessJournal(journal);
    setAccessError(null);
  } else if (!journal.secure && journal.salt && !getKey(journal.id)) {
    // No password but has salt — auto-derive from empty string
    await deriveAndCache(journal.id, '', journal.salt);
    router.push(`/journal/${journal.id}`);
  } else {
    router.push(`/journal/${journal.id}`);
  }
}
```

### 3. `app/index.tsx` — `handleCreate`

Always pass `deriveAndCache` to `create`, not just when a password is set:

```typescript
const journalId = await create(input, deriveAndCache);
```

### 4. `app/journal/[id].tsx` — Auto-derive for non-secure journals

The journal screen reads the derived key from context. If the journal has a salt but no cached key (e.g., navigated via deep link), auto-derive:

```typescript
const { getKey, deriveAndCache } = useJournalKeys();

// After journal loads, if it has salt but no cached key, derive from empty string
useEffect(() => {
  if (journal && journal.salt && !journal.secure && !getKey(journal.id)) {
    deriveAndCache(journal.id, '', journal.salt);
  }
}, [journal]);
```

This is a safety net — normally the home screen handles it, but this covers direct navigation.

### 5. Migration: existing unencrypted journals

Existing journals created before this fix have no salt and their data has only device encryption. Options:

**Option A (simple, chosen):** Leave them as-is. `readEncrypted` already handles `derivedKey === undefined` gracefully (skips password layer). These journals work fine — they just lack the second layer. A future "re-encrypt" feature could add it.

**Option B (not chosen):** Auto-migrate on first access — generate salt, derive key from `""`, re-encrypt all data. This is complex and risky for a bugfix.

**Decision: Option A.** The fix ensures all _new_ journals get dual encryption. Old journals continue to work. The `salt` field being undefined signals "legacy, no password layer."
