# Transactional backup import integrity fix

## Problem and evidence

A long Journey → Canto conversion was imported through Canto Web and left a
newly created journal whose metadata could not be parsed. The failing ID was
generated by Canto during import, not supplied by the archive. The generated
archive itself is structurally valid:

- `manifest.json` declares `encrypted: false`.
- `journal.json`, `settings.json`, and all page JSON entries parse correctly.
- The failing storage value resembles device-encrypted base64 ciphertext rather
  than export JSON.

The import paths currently write a new journal and return success without
reading it back. A failed or inconsistent local-storage write can therefore
leave a broken journal record visible to the application. This plan makes the
write/read lifecycle transactional on both web and native platforms.

## Scope

- `src/lib/backup/import.web.ts` — browser/IndexedDB import path.
- `src/lib/backup/import.ts` — native filesystem import path.
- `src/lib/storage/local.web.ts` — browser IndexedDB timeout/retry behavior.
- `src/lib/sync/engine.ts`, `src/lib/sync/manager.ts`, and the Google Drive
  store/tests — resilient large-attachment sync behavior.
- Existing backup-import tests in `src/lib/__tests__/backupWeb.test.ts` and
  `src/lib/__tests__/backup.test.ts`.
- Storage interfaces only if a small shared transactional helper is introduced.

Google-auth session expiry is out of scope: it affects remote-sync credentials,
not local journal or device-encryption keys. Auto-lock clears in-memory journal
password keys, but the active import retains its local key and the device key
remains persistent. The fix must nevertheless behave safely if any storage
operation fails mid-import.

## Design

Treat the final journal persistence as a transaction with compensating cleanup:

1. Construct `newJournal` and its final attachment references exactly as today.
2. Persist the journal and pages.
3. Read the full new journal back through `store.getJournal(newJournalId,
   metadataKey)`.
4. Verify that the readback is present and structurally matches the expected
   journal: ID, title, journal settings, and complete page count. Let storage's
   JSON/decryption errors propagate as integrity failures.
5. On any failure from persistence or verification, invoke
   `store.deleteJournal(newJournalId)` as best-effort cleanup, log a concise
   cleanup warning if that itself fails, and rethrow the original error.
6. Return `ImportResult` only after verification succeeds.

This uses the existing platform-agnostic `LocalStore` contract. Both platform
implementations already provide `saveJournal`, `savePage`, `getJournal`, and
`deleteJournal`.

## Implementation steps

### 1. Add a shared-shaped transactional tail to both importers

1. In `import.web.ts` and `import.ts`, replace the current unconditional final
   `saveJournal` / page-save / return block with the same guarded sequence.
2. Preserve the existing `metadataKey` rule: only password-protected journals
   receive `derivedKey` for metadata/pages.
3. Keep attachment processing before this transaction; attachment failures
   remain the current recoverable warnings in `ImportResult`.
4. Put both the write and post-write readback inside `try/catch`.
5. In `catch`, delete only `newJournalId`; never delete the source archive or
   any pre-existing journal. Cleanup failure must not hide the original write
   or verification error.
6. Add an error prefix such as `Imported journal failed storage verification:`
   so the UI can distinguish this from malformed backup input.

### 2. Decide and document page-write ownership

`LocalStore.saveJournal` already persists every page. The importers currently
call `savePage` again afterwards, which performs duplicate writes and may alter
page `modified` timestamps because `preserveModified` is not passed.

1. Prefer removing the redundant loop after confirming `saveJournal` has the
   required semantics on both `local.ts` and `local.web.ts`.
2. If the explicit loop is retained for a platform-specific reason, pass
   `preserveModified: true` and include it in the transactional boundary.
3. Add a regression assertion that imported page modification timestamps match
   the backup unless a documented migration intentionally changes them.

### 3. Add regression tests for both platforms

For `backupWeb.test.ts` and `backup.test.ts`:

1. Keep the existing normal export → import → readback round-trip test and
   strengthen it to assert the imported journal is readable immediately after
   `importJournal` resolves.
2. Add a storage wrapper/mock that throws or returns an unreadable result from
   `getJournal` after a successful write. Assert that import rejects with the
   integrity-verification error and `deleteJournal` receives only the new ID.
3. Add a write-failure case (`saveJournal` or final page persistence) and
   verify the same cleanup behavior.
4. Add a cleanup-failure case: `deleteJournal` fails, but the surfaced error is
   still the original storage/verification error.
5. Cover both an unencrypted backup (the reported case) and a password-backed
   backup to ensure the correct `metadataKey` is used for readback.
6. Add a regression fixture based only on synthetic journal data. Do not add
   the user’s Journey or generated Canto archive to the repository.

### 4. Validate user-facing behavior

1. Build and run Canto's relevant Jest suites for web and native backup import.
2. On web, import a large synthetic archive (many pages and attachments) and
   verify that the result opens after import and after a page refresh.
3. Exercise an injected storage-verification failure and confirm no journal is
   left in the journal list or IndexedDB.
4. On native, repeat the equivalent import/readback test and confirm no journal
   directory or registry entry remains after a forced failure.
5. Manually retry the supplied local converted archive only after the
   transactional fix is in place; confirm it either opens normally or fails
   clearly without leaving a corrupted journal behind.

## Acceptance criteria

- Web and native imports return success only after the newly saved journal can
  be read and validated from local storage.
- Any write/readback failure removes the partial new journal without affecting
  existing journals.
- The original failure reason remains visible even when cleanup fails.
- Import preserves page metadata timestamps and no longer performs unnecessary
  duplicate page writes.
- Existing encrypted and unencrypted backup-import behavior remains covered by
  tests.
- A session expiration or auto-lock event cannot cause a successful-looking,
  unreadable imported journal.

## Large Web attachment sync and safe disablement

### Problem

Web sync can fail reading a large local attachment before it reaches Google
Drive, for example:

```
[IDB] Timeout reading canto/<journal-id>/attachments/<attachment>.mp4
```

`local.web.ts` applies the same fixed 10-second timeout to every IndexedDB
operation. In `SyncEngine.uploadPageAttachments`, attachments are read and
encrypted/uploaded in parallel. A large base64 video can exceed that budget or
contend with other reads, causing the entire sync to fail. The current Disable
Sync action switches settings off, but an already-running sync has no explicit
cancellation or stale-run guard.

### Design

1. Keep IndexedDB transactions bounded, but make the read timeout appropriate
   to the stored data and retry a transient timeout with bounded backoff.
2. Limit attachment sync concurrency, especially on web, so a large video does
   not compete with many simultaneous IndexedDB reads and base64 encryptions.
3. Make disabling sync invalidate/cancel the active journal run. It must stop
   further uploads, avoid writing a successful `lastSynced` value, and leave
   the remote backup untouched rather than attempting cleanup/deletion.
4. Surface a specific per-attachment sync error with retry guidance; preserve
   the journal's local data and keep sync disabled when the user requested it.

### Implementation steps

1. In `local.web.ts`, replace the blanket timeout use for attachment reads with
   a narrowly scoped helper that supports a longer configurable attachment-read
   budget and a small bounded retry policy for timeout/transaction-abort errors.
   Do not make all metadata/index operations wait longer.
2. Ensure each timed-out IndexedDB request removes its handlers or otherwise
   settles exactly once, so a late success cannot race a retry.
3. In `sync/engine.ts`, replace unrestricted `parallel(atts, ...)` attachment
   work with a bounded concurrency helper. Check a cancellation signal before
   reading, encrypting, and uploading each attachment.
4. Extend `SyncManager` with a per-journal cancellation generation or
   `AbortSignal`. `forgetJournal`, disable-sync, and app teardown should
   invalidate the current run; stale progress/state updates must be ignored.
5. Wire `SyncModal.handleDisableSync` to request cancellation before (or as
   part of) persisting `remoteSync: false` and `autoSync: false`. Keep the
   existing remote files: disabling sync is not remote deletion.
6. Distinguish cancelled sync from failed sync in state/UI so a user who chose
   Disable Sync does not receive a misleading error notification.

### Tests

1. Add Web storage tests that simulate a delayed attachment read: verify retry
   succeeds within the attachment-specific budget and that normal metadata
   reads retain the short timeout.
2. Add sync-engine tests with a large synthetic attachment and controlled
   promises to prove attachment concurrency is bounded.
3. Simulate an IndexedDB timeout after one upload: assert the sync reports the
   attachment path, does not advance `lastSynced`, and preserves local data.
4. Start a sync, disable it while an attachment is pending, then resolve the
   pending operation. Assert that no subsequent upload occurs, status becomes
   idle/cancelled, and remote data is not deleted.
5. Run existing Google Drive and Web sync suites, plus a manual Web test with a
   representative large MP4 under throttled CPU/storage conditions.

### Additional acceptance criteria

- Large attachments no longer fail solely because of the global 10-second
  IndexedDB timeout or unbounded attachment concurrency.
- Users can disable sync during a long transfer without corrupting local state,
  marking a failed run as successful, or deleting their remote backup.
- Retry/cancellation behavior is tested on Web and does not regress native
  sync behavior.
