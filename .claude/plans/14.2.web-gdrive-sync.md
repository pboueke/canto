# Plan 14.2: Google Drive Sync on Web

## Context

Google Sign-In and sync are fully functional on native (iOS/Android) via `@react-native-google-signin/google-signin`. On web, `GoogleAuthContext.web.tsx` is a no-op stub that warns "not available on web". Since the entire sync stack (engine, manager, GDrive API, GDrive store) uses plain `fetch()` and is platform-agnostic, **only the OAuth authentication layer is missing on web**.

The sync button in `JournalHeader` is also hidden on web via a `Platform.OS !== 'web'` check, and the `AccountButton` calls the no-op `signIn()`.

## Approach: expo-auth-session for Web Only

**Decision**: Keep `@react-native-google-signin` for native, implement web OAuth via `expo-auth-session` in the `.web.tsx` override.

**Why not Google Identity Services (GIS)?** GIS is browser-only — it doesn't work in React Native webviews and has no refresh token support (access tokens expire after 1 hour with no silent refresh). Not suitable for long-lived Drive sync sessions.

**Why not replace native auth with expo-auth-session too?** The native auth works perfectly. Replacing it risks regressions on mobile for zero benefit. Expo's Metro bundler already handles `.web.tsx` platform splitting, so we get clean separation with no conditional logic.

**Why expo-auth-session?** It's already in the Expo ecosystem, supports web via popup/redirect OAuth flows, handles PKCE and auth code exchange, and provides `refreshAsync()` for silent token refresh. The existing GCP web client ID works with it directly.

## Phase 3: Implement Web Google Auth

### 3.1 Implement `GoogleAuthContext.web.tsx`

Replace the no-op stub with a real OAuth implementation using `expo-auth-session/providers/google`.

**Auth flow:**

1. User clicks "Sign In" → `Google.useAuthRequest()` triggers browser popup/redirect
2. User authorizes → callback returns auth code
3. Exchange auth code for access token + refresh token via `AuthSession.exchangeCodeAsync()`
4. Fetch user info from `https://www.googleapis.com/userinfo/v2/me`
5. Store tokens in localStorage with configurable retention

**Token refresh:**

- On mount: check localStorage for stored refresh token
- If found and not expired (per retention policy): use `AuthSession.refreshAsync()` to get fresh access token silently
- If refresh fails or token expired: user must sign in again
- `getAccessToken()`: if current access token is near expiry, refresh transparently

**Implementation details:**

- Use `Google.useAuthRequest()` with `responseType: ResponseType.Code` for auth code flow (gives refresh tokens)
- Pass `webClientId` from `google-credentials.ts`
- Scopes: `drive.appdata`, `drive.file`
- `makeRedirectUri()` for web returns current page URL automatically
- Same `GoogleAuthState` interface as native (user, accessToken, getAccessToken, isSignedIn, isLoading, signIn, signOut)

### 3.2 Token Storage with Configurable Retention

Store in localStorage with metadata:

```typescript
interface StoredAuth {
  refreshToken: string;
  user: GoogleUser;
  storedAt: number; // timestamp
  retentionDays: number; // 0 = never expire, 1, 7, 30
}
```

Key: `canto-google-auth`

On mount:

1. Read stored auth from localStorage
2. Check if `storedAt + retentionDays` has passed → if so, clear and require re-auth
3. If valid, attempt silent refresh with stored refresh token
4. If refresh succeeds, user is signed in transparently

On sign-out: clear localStorage entry.

Default retention: **7 days**.
