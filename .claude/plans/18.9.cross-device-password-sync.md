# Plan 18.9: Cross-device password sync — test coverage and fix

## The bug (recap)

When a journal's password is changed on one device, syncing on a second device that hasn't received the change CORRUPTS the remote: the second device's `engine.sync()` sees `localSalt != remoteSalt`, treats it as "I just changed the password locally", and force re-uploads its (stale) data with its (wrong) key, overwriting the remote's good encryption AND reverting the registry to the second device's state.

After this, cloud import fails because registry/page encryption are inconsistent.

The root cause is that the `keyChanged` heuristic in `engine.ts` cannot distinguish:

- **(A) "I just changed my password locally"** → push to remote (correct: re-upload all pages with new key, update registry)
- **(B) "Another device changed the password since my last sync"** → abort (we'd corrupt remote with stale data)

## Test suite audit — what's missing

### Existing coverage

| Scenario                                  | Test file                         | Real encryption?   | Cross-device?                      |
| ----------------------------------------- | --------------------------------- | ------------------ | ---------------------------------- |
| Push after local password change (case A) | `gdrive-sync-encryption.test.ts`  | Yes (key-tag mock) | No (single mock store)             |
| Cloud import after re-sync                | `gdrive-sync-encryption.test.ts`  | Yes                | Pseudo (two stores, same registry) |
| Web sync e2e                              | `gdrive-sync-e2e-web.test.ts`     | No (passthrough)   | No                                 |
| Cross-platform native↔web                 | `cross-platform-sync-e2e.test.ts` | No (passthrough)   | Yes (two `InMemoryLocalStore`s)    |

### Gaps that allowed the bug to ship

1. **No test for case (B)** — "remote changed externally". All existing password-change tests are single-device "local changed → push" scenarios. There is zero coverage for the "another device changed it, I'm syncing stale data" case.
2. **No multi-device round-trip with actual encryption verification** — `cross-platform-sync-e2e.test.ts` mocks encryption as identity, so it never catches "android pushed wrong-key data over web's good data".
3. **No test asserting that sync ABORTS when it would corrupt remote** — engine currently always returns success; there's no failure-mode test that verifies "in scenario X, sync should refuse to proceed".
4. **No test for `lastKnownRemoteSalt` semantics** — this is the state we'd add to disambiguate cases (A)/(B); it needs explicit coverage.
5. **No test for cloud import after sync corruption** — the user's reported fallback path ("wipe device, re-import") fails when remote is in inconsistent state, but no test exercises this.
6. **No test for password add/remove asymmetry on remote** — `remoteJournal.encrypted=true` while `localJournal.secure=false` (or vice versa) is a strong signal of remote-side change but isn't tested.

### Test infrastructure improvements needed

The `InMemoryLocalStore` test helper has a `reencryptJournal` stub (line 230-232) that does nothing. To realistically test password change flows, this needs to actually re-encrypt pages with the new key (matching the real `local.ts` behavior).

The `createInMemoryLocalStore` doesn't model the bug scenario well because both "devices" share the same encryption layer (same `createMockEncryption()` instance can decrypt anything). For multi-device scenarios where each device has its own derived key, we need a key-aware mock encryption that fails when keys differ — similar to what `gdrive-sync-encryption.test.ts` does with `keyTag`.

## Proposed changes

### canto-data — NO changes needed

`lastKnownRemoteSalt` is per-device sync state, not journal data. It belongs in the SyncManager's local AsyncStorage, not in the `Journal`/`JournalContent` types. The journal data model stays clean.

If we wanted a more robust signal (`passwordChangedAt` timestamp), that WOULD require canto-data changes — but it's not necessary; the local `lastKnownRemoteSalt` is sufficient.

### Engine signature change

`SyncEngine.sync()` gains an optional `previousRemoteSalt?: string` parameter. The engine uses it to refine the `keyChanged` decision:

```typescript
if (saltMismatch) {
  if (previousRemoteSalt != null && localJournal.salt === previousRemoteSalt) {
    // Local hasn't changed since last sync; remote was changed by another device.
    throw new Error('Sync aborted: password was changed on another device. ...');
  }
  // Either no previous sync (first sync) or local salt changed → push.
  keyChanged = true;
}
```

Same logic applies to the encrypted-flag mismatch (password add/remove on remote).

### Manager — store and pass `lastKnownRemoteSalt`

`SyncManager`:

- New AsyncStorage prefix `canto:lastRemoteSalt:`
- Read before calling `engine.sync()`, pass as `previousRemoteSalt`
- After successful sync, write the post-sync remote salt
- On `deleteJournal`, clean up the entry
- Also write the salt after a successful cloud import (NewJournalModal) — otherwise the next sync looks like "first sync" and could re-introduce the corruption window

### NewJournalModal — set `lastKnownRemoteSalt` after cloud import

Cloud import already saves the journal locally. It must also call into SyncManager to record the imported salt as `lastKnownRemoteSalt`, so the next sync correctly identifies that local matches remote.

### Test additions (TDD — write before implementing)

#### In `gdrive-sync-encryption.test.ts` (engine-level)

1. `aborts when remote salt changed externally (no local change)` — local salt = previousRemoteSalt, remote salt differs → throw
2. `pushes when local salt changed (previousRemoteSalt matches old remote)` — current behavior, now explicit
3. `aborts on encrypted-flag mismatch when local unchanged` — local secure=false, remote encrypted=true, previousRemoteSalt = local salt → throw
4. `first sync (no previousRemoteSalt) with salt mismatch — pushes` — preserves current "no history → push" behavior
5. `bidirectional change (both changed since last sync) — aborts` — local salt != previousRemoteSalt AND remote salt != previousRemoteSalt
6. `successful sync where salts match — no-op` — happy path

#### In `sync-manager.test.ts` (manager-level)

7. `stores remote salt after successful sync` — verify AsyncStorage write
8. `passes stored salt to engine on subsequent sync` — verify engine receives correct previousRemoteSalt
9. `does not store salt on failed sync` — error path doesn't pollute state
10. `cleans up stored salt on journal delete` — no orphan entries
11. `passes undefined on first sync (no stored salt)` — explicit first-sync semantics

#### In `gdrive-sync-e2e-web.test.ts` (cloud import recovery)

12. `sync then password change on second device then re-sync on first — does not corrupt remote` — full E2E using two `InMemoryLocalStore` instances + key-aware encryption. This is the user's exact scenario.
13. `cloud import after wipe recovers correctly when remote is consistent` — wipe local, re-import, verify pages load
14. `setting lastKnownRemoteSalt during cloud import prevents next-sync from aborting` — test the integration

#### Test helper improvements

15. **Make `InMemoryLocalStore.reencryptJournal` actually re-encrypt** — currently a no-op; needs to mimic `local.ts:391-462` (filter non-deleted pages, re-write with new key, write metadata). Without this, password-change tests don't exercise the real flow.
16. **Add a key-aware encryption mock for cross-device tests** — copy the `keyTag` pattern from `gdrive-sync-encryption.test.ts` into a shared helper so cross-platform/web tests can verify "wrong key cannot decrypt".

## What this does NOT solve

- **UX for receiving a remote password change**: after a successful "abort", the user sees an error but no clear path forward. A future iteration should detect this state and prompt the user to delete + re-import, ideally automated (e.g., a "password updated on another device — re-enter password" flow that re-derives the key without losing local data). For now, the error message tells them to manually delete and re-import.
- **True bidirectional conflict resolution** (both devices changed independently). Currently we abort; no merge. This is an inherent limitation without a CRDT-style log.
