# Plan 19.2.3 — web sync crypto memory high-water fix

**Status:** Approved — includes batch checkpoint safety amendment
**Release:** unreleased v0.19.2 patch

## Problem and evidence

The first Google Drive sync of a large, newly imported journal can push the Web
renderer past 5 GB of memory and crash. This is reproducible in the supplied
archive without retaining that private archive in the repository:

- `/home/pedro/Downloads/journey-1787092752627.canto.zip` contains 384
  attachments, 225,321,227 raw attachment bytes, and approximately 707
  512-KiB chunk transfers after import.
- The chunked `SyncEngine` path itself is bounded: it processes one chunk at a
  time per attachment and at most two attachment workers. `SyncResult`, queues,
  and the Drive file-ID cache do not retain attachment payloads.
- `src/lib/encryption/utils.ts` calls `sealed.combined('base64')` for every
  sync-encrypted payload. On Web, Expo Crypto implements that request with
  `uint8ArrayToBase64`, which constructs one JavaScript string by concatenating
  one character per byte (`expo-crypto/build/aes/web-utils.js`).
- `uint8ToBase64` in Canto has the same byte-by-byte concatenation algorithm,
  so the fallback currently preserves the defect.
- A deterministic 96 × 512-KiB encoder run raised RSS from 42 MiB to 208 MiB
  and remained at 182 MiB after forced GC. Browser allocator behavior is more
  severe and matches the reported multi-GB high-water growth.

This is primarily an **allocation/high-water amplification** defect, not proof
that completed synced objects are strongly retained. It is still a release
blocker because the allocator behavior makes the first sync unsafe.

## Goal

Make Web AES-GCM base64 output use a bounded-part encoder and ensure every
remote-sync chunk avoids Expo Crypto's byte-by-byte base64 path. A first sync
of this archive must have a per-active-chunk memory bound rather than
allocation growth proportional to all completed chunks.

## Scope

- `src/lib/encryption/utils.ts`
- `src/lib/storage/attachment-content.ts` (only if its duplicate encoder is
  consolidated with the shared safe primitive)
- `src/lib/__tests__/encryption.test.ts`
- `src/lib/__tests__/sync-memory.test.ts`
- `src/lib/__tests__/localStorageWeb.test.ts`
- A small, checked-in deterministic memory harness only if it is reliable in
  CI; otherwise retain it as a documented local verification command.

## Non-goals

- Do not change the chunk format, chunk size, authenticated frames, Drive
  object names, or journal schema.
- Do not reintroduce whole-file attachment reads, base64 strings, or multipart
  bodies for sync.
- Do not add the supplied private archive or any personal journal content to
  the repository.
- Do not use RSS as a CI pass/fail requirement: it varies across Node, Chrome,
  Hermes, and operating systems. Correctness tests must instead prove the
  vulnerable API route is not called and that the encoder works in bounded
  pieces.

## Design

### 1. One safe byte-to-base64 primitive

Replace `uint8ToBase64` with an encoder that:

1. processes at most a small fixed byte block at a time (for example 8,190
   bytes, divisible by three);
2. creates a short binary string for each block, encodes that block with
   `btoa`, and joins the resulting base64 parts once;
3. preserves valid padding and exact output compatibility with the current
   encoder; and
4. documents why byte-by-byte concatenation is forbidden.

The fixed temporary block, not the input length, bounds intermediate binary
strings. The final base64 string is necessarily present because the existing
sync/Drive protocol carries a string, but it must not be constructed through a
quadratic rope/flattening pattern.

`attachment-content.ts` already has a similar safe block encoder. Consolidate
on the shared encryption utility if that avoids duplicate implementations
without introducing an import cycle; otherwise make both implementations share
the same documented bounded algorithm and add equivalent tests.

### 2. Avoid Expo Crypto's unsafe Web encoder

Update `aesGcmEncrypt` to:

1. call `sealed.combined()` with no encoding argument, obtaining the raw
   `Uint8Array` on both Web and native;
2. encode those bytes through Canto's bounded `uint8ToBase64`; and
3. retain the existing yielding, key-length validation, ciphertext wire format,
   and `aesGcmDecrypt` compatibility.

Do not call `sealed.combined('base64')` anywhere in Canto's sync-encryption
path. This is critical: fixing only Canto's fallback leaves current Web
runtimes on Expo Crypto's unsafe implementation.

`aesGcmEncryptBytes` already uses raw `sealed.combined()` and remains the
binary-storage path. Verify that the revised string API produces identical
base64 framing for decryption and cross-platform sync.

### 3. Make IndexedDB write timeout single-settlement

As a separate defensive correction, align `idbPut` with the existing
single-settlement/abort pattern in `idbGet`:

1. on timeout, reject once and attempt to abort the write transaction;
2. clear the timeout and event handlers on every completion/error/abort path;
3. ignore a late transaction completion after timeout; and
4. keep the existing 10-second write budget unless a tested product need
   requires a different value.

This is not the source of the 5-GB upload high-water, but it prevents a
stalled IndexedDB write from retaining its payload and handlers beyond the
operation's declared lifetime.

## Implementation sequence

1. **Characterize the unsafe route.** Add a focused encryption test with a
   mock `AESSealedData` whose `combined('base64')` throws and whose raw
   `combined()` returns bytes. Assert `aesGcmEncrypt` requests raw bytes,
   produces decryptable base64, and preserves the expected ciphertext layout.
2. **Implement the bounded encoder.** Replace the byte-at-a-time
   `uint8ToBase64` loop; test empty input, one/two/three-byte padding edges,
   random bytes, and a 512-KiB chunk against a trusted base64 result.
3. **Route AES string encryption through it.** Change only the encoding step
   in `aesGcmEncrypt`; preserve its public signature and all callers.
4. **Consolidate attachment encoding deliberately.** Reuse the new primitive
   from `attachment-content.ts` where dependency direction permits, then
   re-run framing/chunk-count tests at exact 512-KiB boundaries.
5. **Repair `idbPut` settlement.** Implement timeout abort/handler cleanup and
   a deterministic fake-IndexedDB test for timeout followed by a late
   completion/abort.
6. **Strengthen sync memory coverage.** Keep the existing reference-retention
   test, but add a non-mocked crypto-route test or separate utility test proving
   a 512-KiB sync-sized value cannot call `combined('base64')` or the former
   byte-wise encoder. Do not make a flaky heap threshold the sole regression
   signal.

### Manual Web verification

Use a fresh browser profile and mocked/test Drive endpoint or a disposable
Drive account. Import a synthetic journal with the same shape as the reported
archive (384 attachments / approximately 707 chunks; generated bytes only),
then perform its first sync.

Capture before/during/after values using:

- `performance.measureUserAgentSpecificMemory()` when supported;
- `performance.memory.usedJSHeapSize`;
- Chrome heap snapshots with a forced GC before and after sync.

Pass condition: after forced GC, completed attachment chunk/body strings have
no retaining path and JS heap remains near its pre-sync baseline plus the
journal metadata/thumbnail footprint. A renderer RSS high-water that remains
while the JS heap returns to baseline is allocator behavior to document, not a
logical sync leak; continued post-GC JS-heap growth per completed chunk blocks
release.

## Acceptance criteria

- Web sync never calls Expo Crypto's `combined('base64')` path.
- Canto's shared base64 encoder has no byte-by-byte full-input string
  concatenation and preserves correct output for all padding cases.
- Chunked Drive upload retains the existing one-chunk/two-worker bound and
  does not strongly retain completed payloads.
- `idbPut` settles once and aborts its transaction on timeout.
- A synthetic archive matching the reported journal's chunk count completes a
  first Web sync without monotonically increasing post-GC JS heap.
- Focused tests, the complete Jest suite, formatting, lint, typecheck, and
  `make check` pass.
- The supplied archive is used only for local/manual validation and is never
  committed.

## Approved safety amendment — bounded web batches

The controlled Chrome harness established that both WebCrypto and successful
1.24-MB `fetch` uploads grow renderer-native RSS while V8 remains nearly flat.
Changing multipart body representation or using an HTTP/2 stream did not bound
that growth. Web sync must therefore avoid processing an entire large initial
upload in one renderer lifetime.

### Contract

- On web only, a non-key-rotation sync has a conservative **new-chunk upload**
  budget, not a page budget: a single page can contain hundreds of chunks. It
  stops immediately after the budget is consumed, before reading/decrypting
  further local chunks, in a distinct `checkpointed` state.
- Before a retry reads local chunk data, it lists the exact immutable remote
  generation and treats present chunk indexes as complete. Those indexes are
  skipped without local IndexedDB reads or WebCrypto work. The generation-bound
  authenticated frame makes reuse safe; a partial generation remains invisible
  because no page/index row references it yet.
- A page is published only after all of its immutable chunk indexes exist and
  its encrypted page upload succeeds. The remote sync index is checkpointed
  after each such completed page; an interruption before this point can leave
  only unreferenced generation chunks, which the next process resumes.
- It then stops in a distinct `checkpointed` state. The UI must say that the
  user needs to **close the Canto tab completely**, reopen it, unlock the
  journal if necessary, and start sync again. A normal reload is explicitly
  insufficient because Chrome may reuse the renderer process.
- The next process reads the remote index and skips completed pages. A crash
  before a checkpoint can re-upload at most the current batch; it must never
  make a partial page/attachment visible through the index.
- Key/password-rotation syncs remain all-or-nothing and do not emit batch
  checkpoints: publishing an index encrypted with a new key before the remote
  registry salt would strand peers.
- The feature must not claim that a same-tab continuation is memory-safe, must
  not persist a password/derived key, and must preserve existing cancellation,
  stale-run, and last-sync semantics.

### Required tests

1. Engine interruption after every chunk-budget boundary: restart enumerates
   the immutable generation, skips present chunks _without local reads or
   WebCrypto calls_, uploads only the next missing chunk budget, and neither
   indexes nor downloads a partial attachment generation.
2. Crash before page/index publication: a restart resumes only missing chunks;
   remote readers retain the prior indexed state. After a complete page, the
   next restart skips it through the checkpointed sync index.
3. Key-rotation sync never emits a checkpoint or updates the remote index
   early.
4. Manager/UI state exposes the checkpoint distinctly from error/cancellation,
   never persists a successful `lastSync` for it, suppresses auto-resume in
   the same renderer, and localizes the close/reopen instructions in every
   supported dictionary.
5. Manual browser verification with generated data: close the tab at a batch
   boundary, reopen in a new tab, resume, and verify completed remote pages
   are skipped with bounded renderer memory. This is a release gate, not a
   simulated-Jest substitute.
