# Plan 0.19.2.6 — catalog-based no-op sync

**Status:** Proposed release plan  
**Release:** `0.19.2.6`  
**Primary objective:** Make an already-synchronized large journal cheap to check
on Android and Web by comparing encrypted page-catalog metadata first, then
opening full page records only when a page actually needs transfer.

## 1. Problem and evidence

After both devices hold the same large journal, a manual sync check still takes
about two minutes on Android. Browser network capture shows only a small number
of Drive registry, index, and metadata requests—not a download of every page.

The local cause is explicit in the current call chain:

```text
SyncEngine.sync()
  -> LocalStore.getJournal()
    -> readJournalPages()
      -> for every page: file read -> device decrypt -> password decrypt -> JSON parse
```

`readJournalPages()` awaits each page serially. The Android filesystem/native
bridge makes hundreds of small reads materially slower than Web IndexedDB. This
full snapshot is loaded before the engine has compared the local page revisions
with the remote `SyncIndex`, so an otherwise no-op sync pays the cost of all
page bodies.

The encrypted, rebuildable `page-catalog.json` already contains the data needed
for the first comparison: each page ID, `modified` timestamp, and deletion
state. Its `ListPagePreview` entries preserve those sync fields explicitly.

## 2. Scope

This release contains exactly two changes:

1. **Catalog-based sync comparison:** load journal metadata and the page catalog
   to construct the local timestamp/deletion view; do not call `getJournal()`
   for the initial comparison.
2. **Lazy page loading:** open a full page only when its comparison outcome
   requires its contents—for a local upload, conflict or deletion propagation
   that needs local details, attachment transfer, or the existing one-page
   remote key-verification canary. Remote downloads do not open an unrelated
   local page first.

Out of scope: native crypto replacement, a new native module, wider filesystem
batch APIs, changing the Drive protocol/index format, changing sync conflict
semantics, parallel page reads, and attachment-chunk format changes.

## 3. Product contract

- A normal no-change sync reads one encrypted local metadata record and one
  encrypted page catalog, and reads **zero local page JSON files**.
- It retains the existing remote registry/index reads, one-page remote key
  canary, password-rotation safeguards, immutable index publication, and
  cancellation behavior.
- A page that is local-only or newer locally is opened exactly once before its
  attachment and page upload work begins.
- A remote-only or newer-remote page is downloaded and saved without first
  opening an unrelated local page.
- Timestamp-equal pages remain unopened locally. Soft-deleted catalog entries
  retain their current propagation behavior.
- A missing, malformed, or inconsistent catalog is never treated as proof that
  pages are absent. Storage rebuilds and validates the catalog from authoritative
  page records first; that exceptional legacy-recovery sync may perform the
  existing full scan.
- The full page files remain authoritative. The catalog is an encrypted,
  rebuildable optimization, not a new source of truth.

## 4. Target interface and ownership

Add a small storage seam for the sync engine rather than exposing catalog file
paths or preview-specific details to it:

```ts
interface JournalSyncSnapshot {
  metadata: Omit<JournalContent, 'pages'>;
  pages: ReadonlyMap<string, { modified: number; deleted?: boolean }>;
}

interface LocalStore {
  getJournalSyncSnapshot?(id: string, derivedKey?: Uint8Array): Promise<JournalSyncSnapshot | null>;
  getPage(journalId: string, pageId: string, derivedKey?: Uint8Array): Promise<Page | null>;
}
```

The exact type names may differ, but these ownership rules are required:

- The storage module owns metadata/catalog decryption, catalog validation, and
  one-time legacy rebuild. Callers never parse `page-catalog.json` directly.
- The sync engine owns the comparison with the remote `SyncIndex` and decides
  which page IDs require a full record.
- The existing `getPage` seam owns page-body decryption. The engine must not
  recreate a full journal merely to access a single changed page.
- `getJournal()` remains available for export, password rotation, and other
  explicit full-data workflows; it is not used by normal sync setup.

This is a deep module boundary: the engine asks for one compact comparison
snapshot and individual changed pages, while catalog migration/recovery stays
inside storage.

## 5. Implementation sequence

1. **Characterize the regression.** Add a deterministic large-catalog sync
   test with page-body reads instrumented. It must prove a no-change sync can
   fail if any local `getPage`/`getJournal` body read occurs, while preserving
   existing remote index and key-canary behavior.
2. **Add the storage snapshot.** Implement the sync snapshot in native and Web
   local stores using encrypted metadata plus the validated page catalog. For
   legacy or invalid catalogs, reuse the current authoritative rebuild path,
   publish the repaired catalog, then return the snapshot.
3. **Refactor sync planning.** Replace the eager `getJournal()` snapshot with
   the compact snapshot. Build the local revision map from catalog entries and
   preserve all current comparison and key-rotation checks.
4. **Load pages at transfer time.** For each action that needs page content,
   call `getPage` once and carry that loaded page through attachment upload,
   encryption, publication, and result accounting. Handle a page disappearing
   between catalog read and body read safely: cancel/skip it without publishing
   an index entry that claims an unuploaded payload.
5. **Keep full workflows intact.** Verify password rotation/remote-key repair
   still intentionally load all local pages, but do so through per-page lazy
   reads under their existing atomic publication rules.
6. **Measure and document.** Extend the existing sync debug trace with a
   `local-sync-snapshot-loaded` phase (and optional count fields if needed) so
   a physical-device trace distinguishes catalog read time from Drive time.

## 6. Tests and verification

### Automated

- Local storage tests, native and Web:
  - valid catalog yields metadata plus ID/revision/deletion snapshot without
    opening page files;
  - missing/corrupt catalog rebuilds from pages and then yields a valid snapshot;
  - password-protected catalog works with the derived key and rejects a wrong
    key without silently claiming an empty journal.
- Sync engine tests:
  - 351 timestamp-equal pages perform zero full local page reads and no page
    upload/download;
  - one locally newer page opens and uploads only that page;
  - one remote-newer page does not open unrelated local pages;
  - local/remote deletions, conflicts, cancellation, and page disappearance
    preserve current index correctness;
  - password change and historical remote-key repair still re-encrypt every
    required local page and do not publish a mixed-key snapshot.
- Existing Drive, cross-device password, local storage, and sync manager suites
  remain green.

Run the focused suite first, then the repository checks:

```bash
npm test -- --runInBand \

```

### Manual Android verification

With the reported approximately 351-page journal already synchronized on both
devices:

1. enable the sync debug trace;
2. perform a manual sync with no edits;
3. confirm the trace reaches `local-sync-snapshot-loaded` without page-read
   events and Drive shows only normal registry/index/metadata traffic;
4. edit one page and sync again; confirm that only that page is opened and
   uploaded;
5. repeat on the other device and confirm only the changed page is downloaded.

## 7. Acceptance criteria

- An in-sync 351-page Android journal no longer decrypts/parses all page bodies
  during a sync check.
- No-change sync time is governed by one local catalog read plus ordinary Drive
  metadata latency, rather than page count.
- A single-page edit causes one local full-page load and one page transfer, not
  a journal-wide scan.
- Catalog recovery is safe and explicit; corrupt optimization data cannot cause
  page loss or a false successful sync.
- Current encryption, password-change, repair, conflict, cancellation, and
  transactional/index-publication contracts remain covered by tests.
