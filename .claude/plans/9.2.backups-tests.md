# 9.2 — Comprehensive Backup/Import End-to-End Test Suite

## Goal

Replace fragile manual QA of backup data handling with a comprehensive, end-to-end test suite that exercises every conditional flow — so manual QA only needs to verify UI behavior.

## Context

The existing `src/lib/__tests__/backup.test.ts` (48 tests) already tests export, import, inspect, and round-trip flows. However, it has gaps:

1. **Attachments through round-trips** — existing round-trip tests either have no attachments or only test encryption flags, not actual binary data survival
2. **File-type attachments** — all tests use `type: 'image'`; `type: 'file'` is never tested
3. **Mixed attachment scenarios** — pages with both images and files simultaneously
4. **Multiple pages with attachments** — attachment dedup across pages in import flow
5. **Encrypted round-trip with attachments** — encrypting + decrypting actual attachment data end-to-end
6. **Unencrypted export of secure journal round-trip** — the "canProvidePassword" flow with actual data
7. **Import without key for secure journal** — verifying attachment encryption flags are cleared
8. **Edge cases** — empty page text, pages with only deleted attachments, unicode titles, large page counts, thumbnail/modified fields preservation

## Approach

Create a **new test file** `src/lib/__tests__/backup-e2e.test.ts` focused exclusively on end-to-end round-trip scenarios. This keeps the existing unit-level tests intact while adding the missing coverage.

The new file will reuse the same mocking infrastructure (in-memory filesystem, passthrough encryption service) but focus on **export → import → verify equivalence** flows.

## Test Plan

### File: `src/lib/__tests__/backup-e2e.test.ts`

Reuse the same mock setup as `backup.test.ts` (in-memory filesystem, mock encryption service, mock expo-sharing).

### Test Groups

#### 1. Unencrypted round-trip with attachments

- **Test: image attachments survive round-trip** — export journal with image attachments, import, verify binary data matches
- **Test: file-type attachments survive round-trip** — same but with `type: 'file'` (PDF, etc.)
- **Test: mixed images and files on same page** — page has both `.images[]` and `.files[]`, verify both survive
- **Test: multiple pages each with attachments** — 3 pages, each with different attachments, verify all data matches correct pages
- **Test: shared attachment across pages** — two pages reference same attachment path, verify dedup in export and correct restoration on import

#### 2. Encrypted round-trip with attachments

- **Test: encrypted export/import preserves image data** — full cycle with AES key, verify decrypted binary matches original
- **Test: encrypted export/import preserves file data** — same for `type: 'file'`
- **Test: encrypted round-trip with mixed encrypted/plain attachments** — secure journal where some attachments are password-encrypted and some aren't, verify each flag and data

#### 3. Unencrypted export of secure journal (canProvidePassword flow)

- **Test: import with key preserves encryption flags and data** — secure journal exported unencrypted, imported with key → encrypted attachments stay encrypted, data intact
- **Test: import without key clears encryption flags** — same export, imported without key → `encrypted` flag is `false` on all attachments, data still accessible
- **Test: import with key preserves `secure: true` and salt/kdf** — metadata fields preserved

#### 4. Data equivalence validation (comprehensive field checks)

- **Test: all page fields survive round-trip** — text, date, tags, location (all subfields), comments (multiple), thumbnail, modified timestamp, deleted=false
- **Test: all journal metadata fields survive** — id (new), title, icon, date (new), secure, salt, kdfIterations, version
- **Test: all settings fields survive** — every field in JournalSettings individually checked
- **Test: attachment metadata fields survive** — id (new), path (new), name (original), type, encrypted, size, deleted

#### 5. Edge cases

- **Test: empty page text and no attachments** — page with `text: ''`, no images/files
- **Test: page with only deleted attachments** — all attachments have `deleted: true`, verify none appear in export/import
- **Test: unicode/emoji in journal title and page text** — special characters preserved through cycle
- **Test: journal with many pages (20+)** — stress test that ordering/completeness is maintained
- **Test: page with empty tags array** — `tags: []` preserved (not omitted)
- **Test: page with no comments** — `comments: []` preserved
- **Test: attachment with no extension** — `name: 'README'` → extension falls back to `bin`
- **Test: multiple comments on single page** — order and content preserved
- **Test: location with all optional fields** — latitude, longitude, altitude, accuracy all present and preserved
- **Test: re-import same backup produces independent copies** — import twice, modify one, verify other is unaffected

#### 6. Error and boundary conditions

- **Test: import encrypted backup without key throws** — clear error message
- **Test: import encrypted backup with wrong key throws** — GCM auth failure
- **Test: import corrupted ZIP throws** — invalid binary data
- **Test: export then import with different title** — title in result matches provided title, not original

## Implementation Notes

- Helper function `assertJournalEquivalence(original, imported, opts)` to compare journals field-by-field, accounting for expected differences (new IDs, new date, possibly new title)
- Helper function `assertPageEquivalence(original, imported)` for deep page comparison
- Helper function `assertAttachmentDataEquals(store, journalId, pageId, attachment, expectedBase64, key?)` to read back stored attachment and compare
- All helpers should produce clear assertion messages showing which field diverged
- Keep `modified` timestamp comparison as "exists and is a number" (import may update it)
- For attachment binary comparison: store known base64 in mock filesystem, export, import, read back and compare
