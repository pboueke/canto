# Plan 16: Canto Data Model Library & Documentation

**Requirement:** `.claude/requirements/16.data.md`
**Branch:** `master`
**Version:** 0.15.0 → 0.16.0

## Problem Statement

Canto journals contain deeply personal data. As the app evolves, schema changes are inevitable—but data loss or silent corruption is unacceptable. Today the data model lives embedded in the app with no formal versioning, no migration system, and no way for users to programmatically interact with their exported journals outside the app. This plan extracts the data layer into a self-contained, documented, versioned module that the app itself uses—and that any TypeScript user can use to read, validate, and manipulate Canto journals.

## Goals

1. **Data portability**: A Canto user can `npm install` and write a TS script to read/manipulate their exported `.canto.zip` journals
2. **Schema documentation**: `DATA.md` describes the exact journal structure, filesystem layout, encryption scheme, and export format
3. **Versioned models**: Journal schema is versioned with semver semantics (MAJOR = migration needed, MINOR/PATCH = backward-compatible)
4. **Migration framework**: The data module owns forward migrations between schema versions
5. **App dogfoods the library**: The Canto app imports all types and validation from this module—no parallel definitions

### Data Flow: Export/Import with the Data Module

```
EXPORT (app → .canto.zip):
  JournalContent (in memory, decrypted)
    → data/validation.ts: validateJournalContent()    [structural check]
    → data/format.ts: buildExportManifest()            [manifest with SCHEMA_VERSION]
    → data/format.ts: serializePages()                 [JSON serialization]
    → lib/backup/export.ts: encrypt + ZIP + share      [platform-specific]

IMPORT (.canto.zip → app):
  .canto.zip
    → lib/backup/import.ts: unzip + decrypt            [platform-specific]
    → data/format.ts: parseManifest()                  [extract + validate manifest]
    → data/migration.ts: migrateIfNeeded()             [version check + migrate]
    → data/validation.ts: validateJournalContent()     [structural check]
    → lib/backup/import.ts: save to local store        [platform-specific]

EXTERNAL USAGE (user TS script → .canto.zip):
  import { readCantoZip, validateJournalContent } from '@/data';
  // or from 'canto-data' when published as npm package

  const zip = await readCantoZip(buffer);        // parse ZIP, extract manifest
  const journal = zip.journal;                     // decrypted JournalContent
  validateJournalContent(journal);                 // throws on invalid
  console.log(journal.pages[0].text);              // access entries
```

## Schema Versioning Strategy

```
SCHEMA_VERSION = "1.0.0"  (semver string, stored in data/version.ts)

ExportManifest.schemaVersion: string   ← NEW field (replaces numeric `version: 1`)
ExportManifest.version: 1              ← KEPT for backward compat (always 1 for manifest format)

JournalContent.schemaVersion: string   ← NEW field
JournalContent.version: number         ← KEPT for backward compat (deprecated, always 1)

Versioning rules:
  MAJOR bump (1.0.0 → 2.0.0): Breaking schema change. Migration required.
    Examples: removing a field, changing a field's type, restructuring nested objects
  MINOR bump (1.0.0 → 1.1.0): New optional fields. No migration needed.
    Examples: adding a new optional field to Page, new attachment type
  PATCH bump (1.0.0 → 1.0.1): Documentation-only or validation fix. No migration.

Migration direction: FORWARD ONLY (old → new). No downgrades.
```

### Migration Framework

```
data/migration.ts:

  Migration {
    from: string;          // e.g. "1.0.0"
    to: string;            // e.g. "2.0.0"
    description: string;
    migrate(data: unknown): unknown;  // transforms raw JSON
  }

  MIGRATIONS: Migration[] = [];  // empty at launch—v1 is baseline

  migrateIfNeeded(data: unknown, fromVersion: string): { data: unknown; migrated: boolean }
    - Compares fromVersion to SCHEMA_VERSION
    - If equal: return as-is
    - If fromVersion < SCHEMA_VERSION: apply migrations in sequence
    - If fromVersion > SCHEMA_VERSION: throw (can't downgrade)
    - If no fromVersion (legacy v1 export): treat as "1.0.0"
```

## Validation Layer

```
data/validation.ts:

  Type guards (runtime checks):
    isGeoLocation(v: unknown): v is GeoLocation
    isComment(v: unknown): v is Comment
    isAttachment(v: unknown): v is Attachment
    isPage(v: unknown): v is Page
    isJournal(v: unknown): v is Journal
    isJournalContent(v: unknown): v is JournalContent
    isExportManifest(v: unknown): v is ExportManifest

  Structural validators (throw with details):
    validatePage(v: unknown): Page                    — validates + returns typed
    validateJournalContent(v: unknown): JournalContent — validates all pages recursively
    validateExportManifest(v: unknown): ExportManifest

  Implementation: hand-written type guards (no zod/ajv dependency).
  Each guard checks: required fields present, correct types, enum values valid,
  arrays contain correct element types. Returns boolean for guards, throws
  ValidationError with field path for validators.

  ValidationError extends Error {
    field: string;       // e.g. "pages[3].images[0].type"
    expected: string;    // e.g. "'image' | 'file'"
    received: string;    // e.g. "'video'"
  }
```

**Details:**

`src/data/migration.ts`:

```ts
export interface Migration {
  from: string;
  to: string;
  description: string;
  migrate(data: unknown): unknown;
}

export function migrateIfNeeded(
  data: unknown,
  fromVersion?: string,
): { data: unknown; migrated: boolean; fromVersion: string; toVersion: string };
```

- If `fromVersion` is undefined/missing, defaults to `"1.0.0"` (legacy)
- Migrations apply in sequence: 1.0.0 → 2.0.0 → 3.0.0
- Each migration receives raw JSON (not typed) to handle schema drift
- Returns migrated data + metadata about what happened

**Tests (~12 cases):**

- No migration needed (same version) → passthrough
- Missing version → treated as 1.0.0
- Future version → throws clear error
- Migration chain applies in order (mock migrations for testing)
- Migration failure → throws with context (which migration, which step)
- Empty migration registry → only version check

## Risks & Mitigations

| Risk                                              | Mitigation                                                                     |
| ------------------------------------------------- | ------------------------------------------------------------------------------ |
| Import path changes break something               | Run full test suite after Phase 4; TypeScript compiler catches missing imports |
| Legacy exports without schemaVersion              | `parseManifest()` defaults to "1.0.0"; tested explicitly                       |
| SyncProvider circular dependency                  | Move `SyncProvider` type to `src/data/types.ts`                                |
| Migration framework untested with real migrations | Phase 2 tests use mock migrations; first real migration will add its own tests |
| DATA.md goes stale                                | Mention in CONTRIBUTING.md that data model changes require DATA.md update      |

## NOT building

- **npm package publishing**: The module lives in `src/data/` for now. Publishing to npm as `canto-data` is a follow-up when there are external users.
- **Zod/Ajv dependency**: Hand-written validators avoid adding a dependency for ~200 lines of validation code.
- **Backward migrations (downgrade)**: Forward-only. Users on newer versions can't export for older versions.
- **JSON Schema generation**: DATA.md serves as the human-readable spec; machine-readable schema is a follow-up.
- **Runtime schema auto-detection**: Version is explicit in the manifest, not inferred from structure.
