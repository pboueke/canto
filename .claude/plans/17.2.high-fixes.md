# Plan: Requirement 17.2 — High Priority Fixes

## Context

Canto is at v0.17.0. A codebase audit (`.claude/notes/2026-03-20-6.md`) identified 40 issues. Plan 17.1 addresses the 5 CRITICAL issues. This plan covers all 9 HIGH priority issues: 4 data-corruption edge cases, 1 security vulnerability, and 4 bugs. Ordered by risk and dependency.

**Test:** `src/components/home/__tests__/NewJournalModal.test.tsx` — render with `existingIds` containing a known ID, trigger cloud import, assert that journal with that ID shows "already local" indicator.

#### Issue #11 — Fix auto-lock interval leak

**File:** `src/contexts/JournalKeyContext.tsx`

The `clearAll` callback is in the useEffect dependency array. When `clearAll` changes identity (it's a `useCallback` that depends on state), the effect re-runs, creating a new interval. The old interval's cleanup runs, but the rapid churn wastes resources and can trigger redundant erasures.

**Fix:** Use a ref for `clearAll` so the interval never re-registers:

```typescript
const clearAllRef = useRef(clearAll);
clearAllRef.current = clearAll;

useEffect(() => {
  const interval = setInterval(async () => {
    if (keysRef.current.size === 0) return;
    const timeout = await getAutoLockTimeout();
    if (timeout > 0 && Date.now() - lastActivityRef.current >= timeout) {
      clearAllRef.current();
    }
  }, 30_000);
  return () => clearInterval(interval);
}, []); // stable — no deps
```

**Test:** `src/contexts/__tests__/JournalKeyContext.test.tsx` — mount the provider, verify only one interval is active after multiple state changes (spy on `setInterval`/`clearInterval` counts).

#### Issue #14 — Track scheduleSyncDebounced promise

**File:** `src/contexts/SyncManagerContext.tsx`

The untracked `.then()` can run after unmount with a stale manager ref.

**Fix:** Add an abort flag via useEffect cleanup:

```typescript
const scheduleSyncDebounced = useCallback(
  (journalId: string, derivedKey?: Uint8Array) => {
    if (!accessToken || !managerRef.current) return;
    const manager = managerRef.current;
    getAccessToken()
      .then((token) => {
        if (token && managerRef.current === manager) {
          manager.scheduleSyncDebounced(journalId, token, derivedKey);
        }
      })
      .catch((err) => {
        console.error('[Canto] Failed to get access token for sync:', err);
      });
  },
  [accessToken, getAccessToken],
);
```

The key change: capture `managerRef.current` at call time and check it hasn't changed by resolution time. Also add `.catch()` for OAuth failures.

**Test:** `src/contexts/__tests__/SyncManagerContext.test.tsx` — trigger scheduleSyncDebounced, unmount provider, resolve the token promise, assert `scheduleSyncDebounced` on manager is NOT called.

### Phase 2: Data Integrity Fixes (Issues #13, #8, #12)

#### Issue #13 — Validate deserializePages output

**File:** `packages/canto-data/src/format.ts`

`deserializePages()` does `JSON.parse(json) as Page` with no validation. The `canto-data` package already exports `validatePage()`.

**Fix:** Validate each parsed page:

```typescript
export function deserializePages(entries: Map<string, string>): Page[] {
  const pages: Page[] = [];
  for (const [filename, json] of entries) {
    const parsed = JSON.parse(json);
    validatePage(parsed); // throws ValidationError if invalid
    pages.push(parsed as Page);
  }
  return pages;
}
```

Callers that handle import/sync already have try-catch, so validation errors will surface naturally.

**Test:** `packages/canto-data/src/__tests__/format.test.ts` — pass a map with invalid JSON (missing `id`, wrong `type`, etc.), assert `deserializePages` throws `ValidationError`.

#### Issue #8 — Report skipped ZIP attachments

**Files:** `src/lib/backup/import.ts`, `src/lib/backup/import.web.ts`

Currently, when an attachment filename doesn't match the expected pattern `{type}-{id}.{ext}`, it's silently skipped with `continue`. Users get no warning that attachments were lost.

**Fix:** Collect skipped filenames and include them in the import result:

```typescript
const skippedAttachments: string[] = [];

// ...in the attachment loop:
if (!match) {
  skippedAttachments.push(zipFilename);
  continue;
}
```

Extend `ImportResult` (or the return value) to include `skippedAttachments`. The UI caller can then show a warning toast if any attachments were skipped.

Note: Plan 17.1 Issue #4 already extends ImportResult with `attachmentErrors`. This adds `skippedAttachments` alongside it.

**Test:** `src/lib/backup/__tests__/import.test.ts` — create a ZIP with a malformed attachment filename, assert import completes and returns the filename in `skippedAttachments`.

#### Issue #12 — Fail on null attachment download

**File:** `src/lib/sync/engine.ts`

When `downloadAttachment()` returns null, the page's `att.path` stays as the stale remote path. The page is saved with a broken reference.

**Fix:** Throw an error when download returns null so the sync engine's error handling can report it:

```typescript
const data = await this.remote.downloadAttachment(remotePath);
if (!data) {
  throw new Error(`[Sync] Attachment not found on remote: ${remotePath} (page ${page.id})`);
}
const localPath = await this.local.saveAttachment(journalId, page.id, att, data);
att.path = localPath;
```

This makes attachment download failures explicit. The sync engine already handles errors at the page level and reports them.

**Test:** `src/lib/sync/__tests__/engine.test.ts` — mock `downloadAttachment` to return null, assert sync throws with the expected error message.

### Phase 3: Re-encryption Safety (Issues #7, #6)

These two issues are related — both involve re-encryption operations that can leave data in a mixed-key state.

#### Issue #7 — Try-catch around reencryptJournal

**File:** `src/components/journal/JournalSettings.tsx`

`reencryptJournal()` at line 202 has no error handling. If it fails partway, the journal metadata may already be updated (new salt, new secure flag) while pages remain encrypted with the old key.

**Fix:** Wrap the reencrypt call in try-catch. On failure, restore the original key in the key cache and re-throw so the UI modal displays the error:

```typescript
try {
  await store.reencryptJournal(
    updatedJournal,
    derivedKey ?? undefined,
    newKey,
    (current, total) => {
      setPasswordProgress(
        t.journalSettings.reencryptProgress
          .replace('{current}', String(current))
          .replace('{total}', String(total)),
      );
    },
  );
} catch (err) {
  // Restore the original key so user can still access their data
  if (derivedKey) {
    setKey(journal.id, derivedKey);
  } else {
    clearKey(journal.id);
  }
  setPasswordProgress('');
  throw new Error(
    `Re-encryption failed: ${err instanceof Error ? err.message : String(err)}. ` +
      `Your journal data is unchanged — the original password still works.`,
  );
}
```

Also need to verify that `store.reencryptJournal` itself is transactional — if it isn't, the error message should reflect that and we should investigate making it so.

**Test:** `src/components/journal/__tests__/JournalSettings.test.tsx` — mock `reencryptJournal` to throw, assert that the original derived key is restored and error is shown.

#### Issue #6 — Transactional key rotation

**File:** `src/components/home/SecuritySettingsModal.tsx`

The current flow:

1. `rotateKey()` — generates new key AND persists it immediately
2. `reencryptAll()` — re-encrypts all data with new key
3. If step 2 fails, the new key is already active but data is still encrypted with old key

**Fix:** Split `rotateKey()` into generate + persist:

1. Generate the new key without persisting: `const { oldKey, newKey } = generateNewKey()`
2. Re-encrypt all data: `await store.reencryptAll(oldDecrypt, oldEncrypt, newEncrypt)`
3. Only after success, persist the new key: `await persistDeviceKey(newKey)`
4. Clear the singleton cache: `encryption.clearSession()`

This requires refactoring `rotateKey()` in both `device.ts` and `device.web.ts` to expose a two-phase API:

```typescript
// New exports:
export async function prepareKeyRotation(): Promise<{ oldKey: Uint8Array; newKey: Uint8Array }> {
  const oldKey = await getOrCreateDeviceKey();
  const newKey = getRandomBytes(32);
  return { oldKey, newKey };
}

export async function commitKeyRotation(newKey: Uint8Array): Promise<void> {
  // native: SecureStore.setItemAsync(DEVICE_KEY_ALIAS, bytesToHex(newKey))
  // web: localStorage.setItem(DEVICE_KEY_ALIAS, bytesToHex(newKey))
}
```

Then in SecuritySettingsModal:

```typescript
const { oldKey, newKey } = await prepareKeyRotation();
// ... build decrypt/encrypt functions ...
await store.reencryptAll(oldDecrypt, oldEncrypt, newEncrypt);
await commitKeyRotation(newKey); // only on success
encryption.clearSession();
```

The old `rotateKey()` function can be kept as a convenience wrapper that calls both, or deprecated.

**Files to change:** `device.ts`, `device.web.ts`, `SecuritySettingsModal.tsx`

**Test:** `src/lib/encryption/__tests__/device.test.ts` — mock `reencryptAll` to throw after `prepareKeyRotation`, assert that the old key is still in SecureStore (not the new one). `src/components/home/__tests__/SecuritySettingsModal.test.tsx` — same scenario end-to-end.

### Phase 4: Web Security (Issue #10)

#### Issue #10 — Protect device key with Web Crypto

**File:** `src/lib/encryption/device.web.ts`

Currently the device key is stored as plaintext hex in localStorage. Any XSS attack can read it.

**Fix:** Use the Web Crypto API to wrap the device key with a non-extractable CryptoKey stored in IndexedDB:

1. On first run, generate a non-extractable AES-KW wrapping key via `crypto.subtle.generateKey()` and store it in IndexedDB (IndexedDB CryptoKey entries survive storage but aren't accessible to `localStorage`-reading scripts)
2. Wrap the device key with the wrapping key via `crypto.subtle.wrapKey()`
3. Store the wrapped (encrypted) device key in localStorage
4. To unwrap, retrieve the CryptoKey from IndexedDB and call `crypto.subtle.unwrapKey()`

```typescript
const WRAPPING_KEY_DB = 'canto-keys';
const WRAPPING_KEY_STORE = 'wrapping';
const WRAPPING_KEY_ID = 'device-wrapper';

async function getOrCreateWrappingKey(): Promise<CryptoKey> {
  // Try to load from IndexedDB
  const db = await openDB();
  const existing = await db.get(WRAPPING_KEY_STORE, WRAPPING_KEY_ID);
  if (existing) return existing;

  // Generate non-extractable wrapping key
  const key = await crypto.subtle.generateKey(
    { name: 'AES-KW', length: 256 },
    false, // non-extractable
    ['wrapKey', 'unwrapKey'],
  );
  await db.put(WRAPPING_KEY_STORE, key, WRAPPING_KEY_ID);
  return key;
}
```

**Migration:** On first access after upgrade, detect the old plaintext hex format in localStorage, wrap it with the new wrapping key, and replace the localStorage entry with the wrapped version. This is transparent to the user.

**Limitation:** This is defense-in-depth, not bulletproof. A sufficiently sophisticated XSS attack could still access IndexedDB. But it raises the bar significantly — the key is no longer a simple `localStorage.getItem()` away.

**Test:** `src/lib/encryption/__tests__/device.web.test.ts` — mock Web Crypto and IndexedDB, verify that:

- Key is stored wrapped (not plaintext hex) in localStorage
- Key can be unwrapped and used for encryption/decryption
- Migration from plaintext to wrapped format works
- Non-extractable flag is set on wrapping key

## Risk Assessment

- **Phase 1 (bugs):** Low risk — prop wiring, ref pattern, catch handler. All additive.
- **Phase 2 (data integrity):** Medium risk — Issue #12 changes silent skip to throw; callers must handle. Issue #13 adds validation that could reject previously-accepted data from malformed imports.
- **Phase 3 (re-encryption):** Medium risk — changes the key rotation flow. Must test thoroughly to avoid introducing new data-loss paths. The two-phase API is a breaking change for `rotateKey()` callers.
- **Phase 4 (web security):** High risk — changes how the device key is stored on web. Migration must be bulletproof or web users lose access to encrypted data. Should be tested extensively including the migration path.

## Execution Order & Dependencies

- Phase 1 has no dependencies, can be done first
- Phase 2 depends on 17.1 Phase 5 (ImportResult type extension) for Issue #8
- Phase 3 Issue #6 depends on the two-phase API refactor in device.ts/device.web.ts
- Phase 4 is independent but should be done last due to highest risk

## Questions for Review

1. **Issue #10 (web key protection):** The Web Crypto approach adds significant complexity. An alternative is to simply document the limitation and recommend password-protected journals for sensitive data on web (which is already the console.warn message). Is the Web Crypto wrapping worth the complexity?

2. **Issue #12 (null attachments):** Should we throw and fail the entire page sync, or mark the attachment as missing and continue? Throwing is safer (no silent data loss) but harsher for users with intermittent connectivity.

3. **Issue #6 (key rotation):** The two-phase `prepareKeyRotation`/`commitKeyRotation` API is a breaking change. Should we keep the old `rotateKey()` as a wrapper, or remove it entirely?
