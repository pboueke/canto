# Plan 14.3: Cross-Platform Sync E2E Test Suites

## Context

The existing `gdrive-sync-e2e.test.ts` (15 tests) validates the sync lifecycle using a mock `LocalStore` with `jest.fn()` stubs. This means:

1. **No real storage behavior** — `savePage`, `saveAttachment`, etc. are no-ops, so platform-specific storage logic (encryption layers, path generation, timestamp mutation) is never exercised
2. **No cross-platform scenarios** — there's no test that verifies data written by web's IndexedDB store can be read after syncing to native's filesystem store (or vice versa)
3. **Silent bugs go undetected** — both `local.ts:288` and `local.web.ts:300` overwrite `page.modified` with `Date.now()` inside `savePage()`, destroying the remote timestamp during sync downloads. This breaks conflict resolution on subsequent syncs but the mock `savePage` never executes this logic.

### Platform Differences That Can Cause Sync Inconsistencies

| Aspect            | Native (`local.ts`)                                   | Web (`local.web.ts`)                                   |
| ----------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| Storage           | `expo-file-system` (real files)                       | IndexedDB (virtual key-value)                          |
| Device encryption | `expo-secure-store` (hardware-backed)                 | `localStorage` key                                     |
| Attachment paths  | Native file URI (`file:///data/.../img-p1-12345.png`) | Virtual path (`canto/j1/attachments/img-p1-12345.png`) |
| `savePage()`      | Overwrites `modified` with `Date.now()`               | Overwrites `modified` with `Date.now()`                |
| Atomic writes     | tmp file + rename                                     | Direct `idbPut` (IndexedDB transactions are atomic)    |

## Critical Bug: `savePage()` Timestamp Mutation

Both `local.ts` and `local.web.ts` do this in `savePage()`:

```typescript
const updated = { ...page, modified: Date.now() };
```

This is correct for user edits (the page was modified locally, so the timestamp should update). But the sync engine also calls `savePage()` when downloading remote pages (`engine.ts:119`):

```typescript
await this.local.savePage(journalId, downloaded, derivedKey);
```

This destroys the remote `modified` timestamp. On the next sync, the page appears locally modified (newer than remote), gets re-uploaded, and overwrites any remote changes made since the download.

**Fix**: The sync engine should preserve the original timestamp when saving downloaded pages. The cleanest approach is to add a `preserveTimestamp` parameter to `savePage()` (or have the engine set the timestamp explicitly after save). See Phase 1.

---

## Phase 1: Fix `savePage()` Timestamp Mutation

### 1.1 Update `LocalStore` interface (`src/lib/storage/types.ts`)

The `savePage` method needs to distinguish between local edits (where `modified` should be set to now) and sync downloads (where `modified` must be preserved). Rather than adding a flag parameter, we use the convention that if `page.modified` is already set and the caller passes the page as-is, the implementation should respect it. But since both implementations currently always overwrite, we need an opt-out.

Add an optional `preserveModified` parameter:

```typescript
savePage(
  journalId: string,
  page: Page,
  derivedKey?: Uint8Array,
  preserveModified?: boolean,
): Promise<void>;
```

### 1.2 Update native `savePage()` (`src/lib/storage/local.ts`)

```typescript
async savePage(journalId: string, page: Page, derivedKey?: Uint8Array, preserveModified?: boolean): Promise<void> {
  ensureDir(getPagesDir(journalId));
  const updated = preserveModified ? page : { ...page, modified: Date.now() };
  await writeEncrypted(
    getPageFile(journalId, page.id),
    JSON.stringify(updated),
    encryption,
    derivedKey,
  );
},
```

### 1.3 Update web `savePage()` (`src/lib/storage/local.web.ts`)

Same change as native.

### 1.4 Update `SyncEngine` to preserve timestamps (`src/lib/sync/engine.ts`)

Pass `true` for `preserveModified` when saving downloaded pages:

```typescript
// Line 119: downloading remote-only page
await this.local.savePage(journalId, downloaded, derivedKey, true);

// Line 148: downloading newer remote page
await this.local.savePage(journalId, downloaded, derivedKey, true);
```

### 1.5 Update existing mock `LocalStore` in tests

Update `createMockLocalStore` in `gdrive-sync-e2e.test.ts` to accept the new parameter signature (mock still a jest.fn, but signature must match).

Update any other test files that mock `savePage` to include the 4th parameter.

## Phase 2: In-Memory Platform-Realistic LocalStore Implementations

To properly test cross-platform sync, we need LocalStore implementations that behave like the real ones (including encryption layers, path generation, timestamp logic) but run in-memory for test speed and isolation.

### 2.1 Create test helper: `InMemoryLocalStore` (`src/lib/__tests__/helpers/in-memory-local-store.ts`)

A real `LocalStore` implementation backed by an in-memory `Map<string, string>` (simulating either filesystem or IndexedDB). This is NOT a mock — it executes real storage logic.

**Configuration options:**

- `platform: 'native' | 'web'` — controls path generation format
- `encryption: EncryptionService` — mock encryption that actually encrypts/decrypts (passthrough or simple XOR for test speed)

**Behavior:**

- `savePage()` — respects `preserveModified` parameter (overwrites `modified` only when false/undefined)
- `saveAttachment()` — returns platform-appropriate paths (native file URI format vs web virtual path)
- `getJournal()` — assembles journal from stored metadata + pages (like real implementations)
- `getAttachment()` / `saveAttachment()` — applies encryption layers as the real implementations do
- Exposes `_dump()` for test assertions (raw key-value contents)

### 2.2 Create test helper: `MockEncryptionService` (`src/lib/__tests__/helpers/mock-encryption.ts`)

A deterministic encryption service that actually transforms data (so we can verify encryption/decryption round-trips) but is fast and predictable:

- `encrypt(plaintext)` → `"enc:" + plaintext` (simple prefix)
- `decrypt(ciphertext)` → strips `"enc:"` prefix

This lets tests verify that encryption layers are applied/stripped correctly without the overhead of real AES-GCM.

## Phase 4: Cross-Platform Sync Tests

### 4.1 Create `cross-platform-sync-e2e.test.ts` (`src/lib/__tests__/cross-platform-sync-e2e.test.ts`)

Tests that use TWO `InMemoryLocalStore` instances (one configured for native, one for web) syncing through the SAME `InMemoryDrive` backend. This is the core of the cross-platform test suite.

**Setup pattern:**

```
Native LocalStore ↔ SyncEngine ↔ GDriveRemoteStore ↔ InMemoryDrive
Web LocalStore    ↔ SyncEngine ↔ GDriveRemoteStore ↔ InMemoryDrive (same instance)
```

Each test creates two local stores, two sync engines (sharing the same InMemoryDrive), and verifies data flows correctly between platforms.

#### 4.1.1 Native → Web Sync Flow

**Test group: "native creates, web receives"**

1. **Basic page sync** — Create page on native, sync to GDrive, sync on web → web has the page with identical content
2. **Page with attachments** — Create page with images on native (native file URI paths), sync → web receives page with web-format attachment paths, attachment data matches
3. **Multiple pages with mixed states** — Native has 5 pages (2 normal, 1 deleted, 1 with attachments, 1 encrypted), sync to GDrive, web syncs → web state matches (deleted page is absent, encrypted page readable with same derivedKey)
4. **Journal metadata preservation** — Native creates journal with all settings (sort order, 24h time, preview flags, theme override, etc.), syncs → web receives identical settings
5. **Encrypted journal round-trip** — Native creates encrypted journal (secure=true, salt, derivedKey), adds pages, syncs → web syncs with same derivedKey, can read all content
6. **Sequential edits** — Native creates page, syncs. Native edits page (new text, new timestamp), syncs again. Web syncs → web has the edited version, not the original

#### 4.1.2 Web → Native Sync Flow

**Test group: "web creates, native receives"**

7. **Basic page sync** — Create page on web, sync to GDrive, sync on native → native has the page with identical content
8. **Page with attachments** — Create page with images on web (web virtual paths), sync → native receives page with native-format attachment paths, attachment data matches
9. **Encrypted journal round-trip** — Web creates encrypted journal, syncs → native syncs with same derivedKey, can read all content
10. **Deletion propagation** — Web creates page, syncs. Web deletes page, syncs. Native syncs → page is deleted on native

#### 4.1.3 Bidirectional Sync Flow

**Test group: "both platforms active"**

11. **Concurrent edits, different pages** — Native adds page A, web adds page B. Both sync → both platforms have pages A and B
12. **Concurrent edits, same page, native newer** — Both edit page P. Native's timestamp is newer. Both sync → both platforms have native's version
13. **Concurrent edits, same page, web newer** — Both edit page P. Web's timestamp is newer. Both sync → both platforms have web's version
14. **Edit chain across platforms** — Native creates page → syncs → web syncs → web edits → syncs → native syncs → native has web's edit. Verify no data loss at any step.
15. **Delete on one, edit on other** — Native deletes page (timestamp T1), web edits same page (timestamp T2, T2 > T1). Both sync → page survives with web's edit (last-write-wins: edit is newer than delete). _Note: if current implementation doesn't handle this correctly, document as a known limitation._
16. **Attachment overwrite across platforms** — Native uploads attachment, syncs. Web downloads, modifies page text (not attachment), syncs. Native syncs → attachment is still intact, text is updated.
17. **Multiple journals, mixed encryption** — Journal A (plaintext) on native, Journal B (encrypted) on web. Both sync → both platforms have both journals with correct encryption states.

#### 4.1.4 Edge Cases & Regression Guards

18. **Empty journal sync** — Sync a journal with 0 pages from native → web receives the journal metadata with empty pages array
19. **Page with empty text** — Sync page with `text: ""` → content preserved as empty string, not null/undefined
20. **Page with unicode/emoji text** — Sync page with text containing emoji, CJK characters, RTL text → content preserved byte-for-byte
21. **Large page sync** — Sync page with 50KB+ text content → no truncation or corruption
22. **Attachment with special characters in name** — Attachment named `photo (1).png` or `résumé.pdf` → path handling works across platforms
23. **Rapid sequential syncs** — Sync 3 times in quick succession without changes → no errors, no duplicate uploads, idempotent
24. **Sync after journal settings change** — Change `sort`, `use24h`, `autoSync` on native, sync → web receives updated settings
